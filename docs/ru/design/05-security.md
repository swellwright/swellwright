# 05. Безопасность, секреты и права

Swellwright держит ключи ко всему парку нод Remnawave: это самая ценная цель. Цель раздела: компрометация любой одной части (ноды, панели, контейнера, зависимости, браузера) не раскрывает всё остальное.

## 1. Модель угроз
| Актив | Угроза | Основные меры |
|---|---|---|
| Хранилище секретов | кража базы, дампа, резервной копии | шифрование на уровне приложения (AES-256-GCM, обёрнутые ключи), мастер-ключ только в памяти, оффлайн-перебор затруднён (Argon2id) |
| SSH-доступ к нодам | утечка ключей, повтор пароля | короткоживущие SSH-сертификаты, ключи на сервер, закрепление ключей хоста, ограничение источника, аварийный ключ вне системы |
| Токены панели | утечка, избыточные права | scopes, сроки, раздельные токены (запись, чтение, зонды), отзыв, аудит использования |
| Учётные данные DNS | захват доменов | отдельные приложения и учётные записи с минимальными правами, зонально-ограниченные токены, подтверждение для массовых правок |
| Веб-интерфейс | взлом сессии, XSS, CSRF | TOTP/passkey, httpOnly-cookie, SameSite=strict, CSRF-токен, строгий CSP, повышенная аутентификация |
| Вывод нод | вредоносные управляющие последовательности, XSS | очистка вывода, рендер как текст, терминал только в xterm |
| Зависимости | подмена пакетов | замороженные lock-файлы, `--ignore-scripts`, SBOM, сканирование, ручной обзор обновлений |
| Сервер Swellwright | компрометация хоста | отдельная VM, minimal-образы, read-only FS, non-root, политика исходящих соединений |
| Владелец экземпляра и операторы | ошибочное действие | план, согласование, откат, окна, политики-ограничители |
| Плагины | чужой код с доступом к секретам | уровни доверия, изоляция процессом, права в манифесте, прокси сети, подпись, аудит; `community` только в контейнере (`13`) |

## 2. Хранилище секретов (vault)
- **Иерархия ключей:** пароль владельца экземпляра → Argon2id → KEK; KEK оборачивает ключи данных (DEK); каждый секрет шифруется своим DEK (AES-256-GCM, AAD = id секрета + версия + контекст). Параметры Argon2id подбираются под машину (порядка 256 МиБ, t=3).
- **Запечатано и распечатано:** после запуска сервис запечатан; запуск сценариев и показ секретов невозможны до ввода пароля (или файла ключа с другой машины как второй фактор). Исключение «автораспечатывание» (systemd-creds/TPM) допускается только по явной настройке и с пометкой меньшей надёжности.
- **В памяти:** расшифрованные значения живут только в процессе воркера на время шага и затираются; не пишутся в Redis, логи, события, дампы, переменные окружения шагов (только в файлы с правами 600 на ноде и после этого стираются).
- **Раскрытие:** значения «только для записи» в интерфейсе; просмотр требует права `vault:reveal`, повышенной аутентификации и фиксируется в аудите.
- **Ротация:** KEK (перешифрование обёрток без перешифрования данных), DEK, секреты по расписанию; мастера для токена панели, DNS, SSH-ключей.
- **Восстановление:** набор восстановления (recovery kit): Shamir 3 из 5 или распечатанный ключ; потеря пароля и набора = потеря хранилища (описано в `09-ops-docker.md`).
- **Редактирование:** любое значение секрета регистрируется в «списке редактирования» процесса; вывод, ошибки и события проверяются перед записью (запись с секретом отклоняется).
- **Реализовано в фазе 1 (ADR 0018):** случайный ключ шифрования ключей (KEK), хранится обёрнутым дважды: ключом из парольной фразы через Argon2id (по умолчанию 256 МиБ, 3 прохода, `SW_VAULT_KDF_MEMORY_MIB` и `SW_VAULT_KDF_PASSES`; параметры хранятся вместе с хранилищем и могут быть повышены) и случайным 256-битным ключом восстановления, который показывается один раз и нигде не хранится (это уточняет проект: фраза не даёт KEK напрямую, поэтому её можно сменить без перешифрования); ключ данных на каждую версию секрета, AES-256-GCM, привязан к id секрета, версии и типу, так что блок, перенесённый в другое место, не открывается; процесс стартует запечатанным, распечатывание (фраза или ключ восстановления) держит KEK только в памяти, запечатывание его стирает; неудачные попытки открыть записываются и ограничены: десять неудачных попыток за пятнадцать минут блокируют все следующие для всех; раскрытие требует `vault:reveal` и повышения и записывается до того, как значение уходит; в остальном значения только для записи, а заменённое значение не сохраняется; имена, типы и даты это метаданные и видны в списке при запечатанном хранилище; запечатанное хранилище отвечает 423 `vault_sealed`. **Ротация (ADR 0024):** смена парольной фразы (KEK заворачивается заново с новой солью и текущей стоимостью, ничего не перешифровывается, работает при запечатанном хранилище), выпуск нового ключа восстановления (старый перестаёт работать), замена KEK (ключ данных каждого секрета заворачивается новым ключом, версия растёт, выпускается новый ключ восстановления; всё или ничего) и перешифрование каждого секрета новым ключом данных; каждая операция требует `vault:manage`, подтверждения кодом, а первые три ещё и парольную фразу повторно; всё идёт через одну очередь процесса вместе с ключом, поэтому ротация не выполняется посреди записи; в лимит попадают только неудачные попытки; в статусе видно, когда каждая часть менялась в последний раз. Пока нет: доли ключа восстановления (Shamir), ключевой файл как второй фактор, ротация секретов по расписанию, набор редактирования, записи об использовании, экспорт.
- **Срок действия (ADR 0042):** секрет, у которого `expiresAt` наступил или прошёл, просрочен, и хранилище не отдаёт его ничему, что им пользуется (вход на сервер, плагин, токен панели, запуск): 409 `secret_expired` с названием секрета, после ответа «запечатано» и до расшифровки и до отправки чего-либо; решает одно место. Уже начатый запуск доводится до конца (срок проверяется, когда использование начинается). Человек по-прежнему может показать просроченный секрет (в ответе `expired: true`), продлить или заменить его; ничего не удаляется. Отказ записывается не чаще раза в десять минут на секрет (`secret.use_refused`).
- **Секреты для запуска (ADR 0042):** запуску можно передать секреты хранилища тех типов, что читает скрипт (не `ssh_key`, не `ssh_ca`), как файлы: `<каталог шага>/secrets/NAME` (каталог 0700, файл 0600, пишется со стандартного ввода запуска), `NAME_FILE` для скрипта, удаляются, когда скрипт закончился любым способом (обёртка, отмена, чтение потерянного шага, удаление); никогда не попадают в командную строку, окружение SSH, текст скрипта, сохранённый запуск и журнал. По сути это показ секрета (скрипт может его напечатать): нужны `servers:exec`, `vault:reveal` и свежее подтверждение, API-токен не подходит никогда; запись `secret.used_in_run` делается в транзакции запуска. Сохранённый вывод очищается от буквального значения (`[secret NAME]`, в том числе через границу чтений), по мере возможностей: скрипт, который преобразует значение, не отслеживается. Секрет, переданный идущему запуску, нельзя заменить или удалить.

## 3. Вход и авторизация
- Пароль (Argon2id), TOTP обязателен, WebAuthn (passkey), OIDC опционально; блокировка при переборе, IP-ограничения.
- Сессии: httpOnly, Secure, SameSite=strict; короткая жизнь, продление при активности; фиксация новой сессии при повышении прав.
- **Реализовано в фазе 1 (ADR 0014):** хеши Argon2id (64 МиБ, 3 прохода) в формате PHC; TOTP (RFC 6238: SHA-1, 6 цифр, 30 с, один шаг допуска, каждый код работает один раз), секрет запечатан AES-256-GCM ключом `SW_AUTH_KEY` независимо от хранилища, поэтому вход работает при запечатанном хранилище; десять одноразовых кодов восстановления, хранятся хешами; вход в два шага: сессия после одного пароля годится только для завершения входа и при завершении заменяется, а не повышается; блокировка на 15 минут после 5 неудач подряд; токены сессий хранятся хешами, с сроком простоя и абсолютным сроком; первый запуск защищён одноразовым токеном из журнала сервера; защита от CSRF: `SameSite=Strict` и проверка `Origin`. WebAuthn, OIDC, IP-ограничения и step-up позже.
- **Повышенная аутентификация (step-up)** для: терминала, раскрытия секретов, создания токенов, одобрения запусков высокого риска, опасных операций панели (`DELETE`, массовые, `restart-all`), смены политик.
- **Реализовано в фазе 1 (ADR 0017), step-up:** `sessions.elevated_until`; вход повышает сессию (второй фактор только что подтверждён), а `POST /auth/step-up` продлевает повышение кодом аутентификатора или кодом восстановления (одноразовым; уже использованный код повторить нельзя; неверные коды идут в счётчик блокировки); окно пять минут (`SW_STEP_UP_MINUTES`, от 1 до 30), оно не переживает сессию. Маршрут объявляет `stepUp: true` в реестре (в OpenAPI `x-sw-step-up`); охранник после проверки разрешения отвечает 403 с кодом ошибки `step_up_required`, а консоль отвечает диалогом с кодом и повтором. `users:write`, `vault:manage`, `vault:reveal` и `terminal:use` требуют его всегда (тест роняет сборку, если маршрут с одним из них его не объявил). Сейчас это создание и изменение пользователей, сброс учётных данных и смена своего пароля. Повышение принадлежит одной сессии; cookie при этом не заменяется. В журнале `auth.step_up.succeeded` и `auth.step_up.failed`. Пока нет: WebAuthn как подтверждения, запроса на каждое отдельное опасное действие, привязки к адресу или устройству.
- **Роли:** `owner`, `operator` (запуски без секретов и терминала), `observer` (только чтение), `terminal` (право на терминал), `auditor`. Разрешения мелкие (`servers:read`, `runs:execute:deploy`, `panel:write`, `vault:reveal`, `terminal:use`), роли это наборы.
- **Реализовано в фазе 1 (ADR 0015):** один закрытый каталог разрешений вида `ресурс:действие` в `packages/contracts`, его читают сервер, консоль и описание OpenAPI (`x-sw-permission`); пять ролей как фиксированные наборы (владелец имеет все разрешения, это вычисляется; право менять подразумевает право видеть, это проверяет тест); каждый маршрут для вошедшего называет своё разрешение в реестре маршрутов, а тест роняет сборку, если не называет; охранник отвечает 403 и записывает отказ; роль читается из строки пользователя на каждом запросе, поэтому изменение действует сразу; `GET /auth/me` отдаёт разрешения, чтобы консоль показывала или прятала страницы (сервер проверяет заново). Свои роли придут вместе с управлением пользователями. Разрешения ещё не построенных функций уже есть в каталоге, чтобы роли оставались стабильными.
- **Реализовано в фазе 1 (ADR 0016), пользователи:** владелец приглашает пользователя с ролью и получает одноразовое приглашение (256 бит, хранится только хеш, 72 часа, одно на пользователя); приглашённый сам выбирает пароль и подключает аутентификатор, поэтому пароля не знает никто другой. Сброс учётных данных сразу удаляет пароль, аутентификатор, коды восстановления и сессии и выдаёт новое приглашение. Серверная команда `node dist/admin.js reset-credentials <логин>` делает то же с хоста на случай, когда войти не может никто; ей доверяют так же, как базе данных, а запись в журнале без субъекта (`via: cli`). Смена своего пароля требует текущий и завершает остальные сессии. Активный владелец есть всегда; никто не меняет через API свою роль и статус и не сбрасывает свои учётные данные; изменения пользователей пишутся в журнал в той же транзакции. Пока нет доставки по e-mail и самообслуживаемого «забыл пароль».

**Плагины (ADR 0027):** в каталог добавлены `plugins:read` (все роли) и `plugins:manage` (владелец, подтверждение кодом); одобрение привязано к контрольной сумме всех файлов плагина (`GET /plugins`, `POST /plugins/{id}/enable` с показанной суммой, `.../disable`); плагин, который пропал, непригоден или имеет другие файлы, выключается при следующем чтении или при запуске, а страница показывает разницу в разрешениях; пишутся `plugin.enabled` и `plugin.disabled`.

**Запуск плагинов (ADR 0028):** одобренный плагин работает в собственном процессе под моделью разрешений Node (читается только его каталог, нет сети, дочерних процессов и воркеров, нет генерации кода из строк, есть предел кучи, окружение без всего, что принадлежит ядру, и срок на каждый вызов) и выходит в сеть только через ядро, к одобренным парам `host:port` и только по публичным адресам. Перед каждым запуском и вызовом он сверяется с одобрением, а при выключении останавливается сразу. Это не песочница против враждебного кода (процесс всё же может послать сигнал ядру); см. ADR.

**Настройки, секреты и хранилище плагина (ADR 0029):** плагин объявляет свои настройки в небольшом закрытом подмножестве JSON Schema; администратор заполняет их (`plugins:manage`, подтверждение кодом), и каждое изменение пишется по именам полей, а не по значениям. Поле-секрет хранит идентификатор секрета хранилища; значение плагин получает, спросив ядро (`context.secret`), а ядро сверяет сохранённое одобрение, открытость хранилища и тип секрета и пишет `plugin.secret.used`. У плагина есть и собственное хранилище с ограничениями размера.

**Декларативные драйверы (ADR 0030):** плагин для REST-сервиса может быть YAML-описанием, которое исполняет ядро: чужой код не запускается. Значения берутся только из объявленных параметров, настроек, привязанных секретов (только в запросах) и прежних шагов; то, что подставляется в URL, кодируется; хост каждого URL прописан явно; каждый запрос подчиняется шлюзу и сохранённому одобрению, а драйвер, который обращается к не запрошенному в манифесте хосту, делает плагин недействительным.

**Контейнеры-спутники (ADR 0031):** ответ на предел из ADR 0028. Плагин от других (доверие `community`) исполняет код в контейнере, который администратор запускает по сгенерированному фрагменту compose: внутренняя сеть без выхода, только чтение, без возможностей, не root, с пределами, из образа с закреплённым дайджестом. В сеть, к секрету и к своему хранилищу он выходит только через шлюз, который доверяет лишь токену плагина в том виде, как он одобрен (HMAC от идентификатора и дайджеста его файлов, ключ из `SW_AUTH_KEY`), считает неверные токены по адресам и перестаёт отвечать в тот момент, когда плагин отключён или изменён. Во фрагменте лежит токен: обращайтесь с ним как с секретом.

**Удаление пользователей и свой язык (ADR 0026):** `DELETE /users/{id}` (`users:write`, подтверждение кодом) удаляет *отключённую* учётную запись (409, пока она активна или если это ваша) вместе с паролем, аутентификатором, кодами восстановления, сессиями, токенами и приглашением; журнал аудита хранит то, что сделала эта запись, под её именем, и записывает `user.deleted`. `users.language` пуст, пока человек не выберет язык (`PATCH /auth/preferences`, `null` возвращает «как в браузере»); консоль применяет сохранённый язык один раз после входа.
- **Построено в фазе 1 (ADR 0022), сессии:** каждый пользователь видит и завершает свои остальные сессии (`GET /auth/sessions`, `DELETE /auth/sessions/{id}`, `POST /auth/sessions/revoke-others`); `sessions:read` показывает сессии всех, `sessions:revoke` (с подтверждением кодом) завершает одну или все сессии пользователя; используемую сессию запрос не завершает (409, выйти через «Выйти»); каждое завершение пишется как `session.revoked`. Каталог разрешений вырос на шесть: `sessions:read`, `sessions:revoke`, `tokens:create`, `tokens:read`, `tokens:revoke`, `audit:export`.
- **Построено в фазе 1 (ADR 0023), токены API:** `Authorization: Bearer swt_...` (256 случайных бит, хранится только SHA-256, показывается один раз); токен несёт подмножество разрешений владельца, никогда не те, что требуют подтверждения кодом, и на каждом запросе действует в пределах того, что роль владельца ещё разрешает; срок от 1 до 365 дней, не больше 20 действующих на пользователя, необязательное ограничение адресами и CIDR; создание требует `tokens:create` и подтверждения кодом, свои токены видеть и отзывать может каждый, `tokens:read` и `tokens:revoke` охватывают чужие; маршруты подключаются уровнем `any` (сейчас маршруты чтения), маршруты только для браузера и требующие подтверждения кодом токен не принимают; неверные токены ограничиваются по адресу; в журнале `token.created`, `token.revoked`, `auth.token.denied`.
- **Токены Swellwright** (CLI, интеграции, зонды): scopes `sw:<ресурс>:<действие>`, срок, IP-ограничения, хранятся хешем.
- Для опасных запусков опционально «двойное согласование» (второй подтверждающий).

## 4. Доступ к нодам по SSH (способы настраиваются)
Поддерживаются пароли, сертификаты и ключи в любых сочетаниях; ничего не навязывается. Выбор делается на уровне сервера, группы или по умолчанию; можно задать порядок попыток.
| Способ | Описание | Заметки |
|---|---|---|
| Пароль (и пароль sudo) | секреты в хранилище | простейший вариант, как у нового сервера (root); политика предупреждает о риске, но не блокирует |
| Ключ | отдельный ключ ed25519 на сервер (или общий), в хранилище | ротация вручную или сценарием N15 |
| Сертификат | центр сертификатов Swellwright (опционально): пользователь `swellwright`, короткий срок, `principals`, `from=` | включается по желанию; требует подготовки нод |
Общие правила (не зависят от способа): закрепление ключа хоста (подтверждение при первом входе, тревога при смене; переустановка ОС подтверждается явно в N04); первый вход на новый сервер по паролю root, затем создаётся доступ Swellwright и учётная запись администратора, root закрывается только после проверки входа и sudo; таймер страховки на ноде; адрес Swellwright в `ignoreip` fail2ban; для `sudo` пароль передаётся через stdin; **аварийный ключ вне Swellwright** остаётся (оффлайн у владельца экземпляра, вне сервера Swellwright); политики P-005 и P-013 остаются.

**Сделано в фазе 2 (ADR 0034):** реестр хранит способы доступа `password` и `key` как ссылки на секреты хранилища (вид проверяется: `ssh_password`, `ssh_key`, а для sudo `ssh_password`; секрет, который используется, удалить нельзя, и хранилище называет серверы, которые его используют) и закрепляет ключи хоста вручную: человек вводит алгоритм и отпечаток SHA-256, который проверил сам (`SHA256:` и 43 символа base64; отпечаток, который не может быть дайджестом, отклоняется); повторное закрепление ничего не меняет; отзыв ключа это способ, которым обрабатывают переустановленный сервер. Каждое изменение записывается (`server.host_key.pinned`, `server.host_key.revoked`, `server.access.added`, `server.access.updated`, `server.access.removed`) в той же транзакции и без значений. **Сделано в фазе 2 (ADR 0037):** сценарий первого подключения из этого раздела. Сканирование читает ключ, который показывает сервер, не отправляя никаких учётных данных (`POST /servers/{id}/host-keys/scan`: `new`, `pinned` или `differs`); человек сверяет отпечаток с другим источником и подтверждает его, после чего API читает ключ ещё раз и закрепляет его, только если он в точности совпал с подтверждённым (`.../accept`, источник `scan`). Ключ, отличающийся от закреплённого, ожидаем после переустановки операционной системы и выглядит так же, как человек посередине, поэтому для него нужен явный `replace`, который отзывает старые ключи в той же транзакции. Каждое подключение идёт к закреплённому ключу, который проверяется до отправки любых учётных данных, а несовпадение это отдельная ошибка с обоими отпечатками (`host_key_mismatch`); оповещение и есть эта ошибка, показанная там, где операцию запустили, и записанная в цепочку аудита. Политика исходящих подключений из раздела 7 применяется к сохранённому адресу перед каждым соединением (`SW_SSH_ALLOW_LOOPBACK`, `SW_SSH_ALLOW_PRIVATE`, `SW_SSH_ALLOW_HOSTNAMES`), соединение из пула не переживает доверие, под которым открыто, а число операций SSH в минуту у человека ограничено (`SW_SSH_RATE_LIMIT_PER_MINUTE`). Проверка записи доступа (`.../access/{accessId}/verify`) и сбор фактов (`.../facts/refresh`) берут сохранённые секреты только на время вызова и записываются (`server.access.verified`, `server.facts.refreshed`, `server.host_key.scanned`) без значений; всё, что подключается, требует `servers:write`. Фоновая проверка, которая находит сменившийся ключ между операциями, не сделана.

## 5. Веб-терминал (N27)
- Терминал по умолчанию доступен только пользователям с правом `terminal:use` и повышенной аутентификацией на каждую сессию; он работает **только с реальными данными SSH, которые пользователь вводит на каждую сессию**: хост (из инвентаря или произвольный), пользователь, пароль или приватный ключ (вставка или загрузка файла, парольная фраза), при необходимости ответ второго фактора сервера. Swellwright **не подставляет** сохранённые секреты в терминал: данные живут в памяти сессии и стираются при закрытии, в БД, журналы и записи не попадают.
- Следствие: чужая сессия Swellwright или утрата хранилища не даёт готового корневого доступа через терминал; терминал так же годится для серверов вне инвентаря.
- Дополнительные меры: тайм-аут простоя и максимальная длительность, закрепление ключа хоста с подтверждением, запрет широковещательного ввода по умолчанию, подтверждение вставки многострочного текста, список активных сессий и принудительное закрытие.
- **Запись сессий по выбору** (по умолчанию выключена, потому что вывод может содержать секреты); при включении запись шифруется и маскируется по списку известных секретов.
- Отличие: разовые команды (N25) и сценарии используют **сохранённые** доступы и проходят через политику и аудит; терминал это отдельный интерактивный клиент.
- **Сделано в фазе 2 (ADR 0038):** разовые команды и библиотека скриптов. `servers:exec` (владелец и оператор) это разрешение со step-up, так что каждый запуск, отмена и запись скрипта требуют свежего кода аутентификатора, а API-токен не может его иметь; чтение истории и вывода это `servers:read`, и **вывод может содержать секреты**, поэтому его читает каждый, кто может читать серверы (консоль об этом говорит). Скрипт это код, который выполняется на серверах, обычно от root: встроенные это файлы только для чтения с заголовком и сохранённым хешем, собственные скрипты администратора пишутся только с `servers:exec` и кодом, а запуск хранит неизменяемый снимок текста и его хеш (в журнале аудита хеш, но никогда текст или значения параметров). Параметры типизированы, проверяются на сервере до постановки запуска в очередь и доставляются только переменными окружения через экранирование слоя шагов, никогда не внутри текста скрипта. Запуск не уровня `read` нужно подтвердить прямым текстом, это записывается; до согласований движка (фаза 4) это единственная проверка. Закреплённый ключ хоста обязателен, действует политика адресов, неверный пароль пробуют один раз и больше никогда, а каждый сервер запуска это отдельная цель. Пределы: `SW_COMMAND_CONCURRENCY`, `SW_COMMAND_OUTPUT_LIMIT_KIB`, `SW_COMMAND_POLL_MS`, `SW_COMMAND_LOST_AFTER_MINUTES`, `SW_COMMAND_RATE_LIMIT_PER_MINUTE`, не больше пятидесяти серверов в запуске.

## 6. Веб-безопасность
CSP без `unsafe-inline`, `X-Frame-Options`/`frame-ancestors`, HSTS, `Referrer-Policy`, `Permissions-Policy`; CSRF для cookie-аутентификации; ограничение размеров; rate limiting по IP и пользователю; проверка `Origin` у WebSocket; загрузка файлов с проверкой типа и размера; ответы без раскрытия внутренних ошибок.

## 7. Исходящие соединения (SSRF)
Allowlist: хосты серверов инвентаря, панели, DNS-драйверов, провайдеров, GitHub (если включено), Telegram. Блокировка адресов метаданных облака, loopback и внутренних диапазонов для пользовательских URL; защита от DNS-rebinding (закрепление разрешённого IP).
**Сделано в фазе 3 (ADR 0041), панель:** адрес панели проходит ту же политику, что и цель SSH (`SW_PANEL_ALLOW_LOOPBACK`, `SW_PANEL_ALLOW_PRIVATE`, `SW_PANEL_ALLOW_HOSTNAMES`; link-local и адреса метаданных никогда), когда его вводят, и ещё раз на каждый адрес, в который имя разрешается, в момент открытия сокета, поэтому имя нельзя перенаправить на внутреннюю службу после проверки. TLS проверяется (свой удостоверяющий центр для одного подключения, `SW_PANEL_ALLOW_INSECURE_TLS` по умолчанию выключен); обычный `http:` только для адреса loopback или частного и только с `SW_PANEL_ALLOW_HTTP`; ни одно перенаправление не уходит с источника панели. Токен живёт в хранилище (вид `panel_token`, удаление запрещено), читается на время одной работы, отправляется одним заголовком на источник панели и никуда больше, и его нет ни в ответе, ни в записи, ни в ошибке, ни в журнале, ни в кэше (тесты ищут его в каждом). Всё, что читается из панели, проходит маскирование из ADR 0041 (ключи REALITY, короткие id, пароли, идентификаторы клиентов, учётные данные в URL, ключи PEM, JWT), прежде чем покинет API, с ключевым отпечатком, чтобы поворот был виден, а значение нет; подключение проверяется в фоне и сообщает в цепочке аудита только о смене состояния. **Снимки (ADR 0043)** хранят только замаскированный вид: ни одно незамаскированное значение панели не попадает в снимок, экспорт или запись цепочки аудита, поэтому снимок (и резервная копия базы с ним) не хранилище секретов; каждый снимок помнит идентификатор ключа своих отпечатков, и сравнение через смену этого ключа говорит, что не отличит ротацию. Читать, сравнивать и экспортировать можно с `panel:read`; делать и удалять нужно `panel:write` и только из сессии, а для удаления нужен свежий код.

**Сделано в фазе 3 (ADR 0046), консоль API:** право `panel:console` (владелец, оператор; подразумевает `panel:read`) позволяет сессии отправлять запросы на чтение к подключённой панели с сохранённым токеном; токен API Swellwright не может (маршрут только для сессии). Запрос называет операцию каталога и её параметры, а не адрес и не заголовок, и каждое значение проверяется по типу, который ему даёт описание API самой панели (в сегменте пути нет разделителя, экранирования, `..`, `@` и `:`; в значении запроса нет управляющих символов); транспорт отвергает любой путь, который выходит за источник и префикс панели. Отправляются только операции GET; то, что создаёт что-то на панели или возвращает ключ или ссылку, работающую как пароль, закрыто, а то, что меняет панель, показано и не отправляется никогда. Операции о людях, которые пользуются панелью (пользователи, устройства, подписки, запросы, расход), выключены, пока не задано `SW_PANEL_CONSOLE_USER_DATA=true`; тогда нужны `vault:reveal` и свежий второй фактор (проверяется в обработчике, чтобы остальные операции не просили код), а вызов записывается **до** того, как вернуть ответ. Каждый ответ маскируется до выхода с сервера (чёрный список маскированных видов, доступ пользователей, сам токен везде, где он встретился; ответы о людях скрывают ещё имена, почту, идентификаторы мессенджеров, идентификаторы устройств, адреса и все UUID) и обрезается до `SW_PANEL_CONSOLE_MAX_BODY_KIB`; маскирование делается по мере возможности, и консоль об этом говорит. Ограничение на пользователя. Пишется как `panel.console.request`: операция, путь с подстановками, названия параметров запроса, статус, время и сколько значений скрыто, но не значения, не тело и не токен; отказы это `denied` с тем же потолком, что у `authz.denied`. История и образцы живут только в браузере.

## 8. Аудит
Неизменяемый журнал с цепочкой хешей (каждая запись содержит хеш предыдущей), экспорт и проверка целостности; фиксируются вход, запуск, согласование, раскрытие секрета, терминал, изменения политик, токены. Хранение без удаления.

**Реализовано в фазе 1 (ADR 0015):** таблица `audit_events` с триггерами базы, которые отказывают в `UPDATE`, `DELETE` и `TRUNCATE`; номера выдаются под рекомендательной блокировкой, поэтому пропусков нет; SHA-256 от канонических полей и предыдущего хеша; субъект хранится как id и имя на тот момент, без внешнего ключа, поэтому запись переживает пользователя; подробности это плоский объект из коротких значений, без секретов, кодов и текста, введённого неаутентифицированным вызывающим; запись об изменении пишется строго (создание владельца и его запись одна транзакция), запись об отказе по возможности; записи, которые может спровоцировать кто угодно, ограничены (неизвестные учётные записи на адрес, отказы на пользователя), потому что журнал не чистится. `GET /audit` читает его (право `audit:read`), `POST /audit/verify-chain` проходит по нему и сообщает первую проблему и голову (`audit:verify`). Цепочка выдаёт правку, удаление и перестановку тому, кто не может пересчитать её целиком; кто может писать в базу, перепишет все хеши, поэтому голову нужно записать вне базы (см. ниже).

**Экспорт и контрольные точки (ADR 0025):** `GET /audit/export` (`audit:export`, с подтверждением кодом; каждая страница записывается) отдаёт страницы событий с полями, которые покрывают их хеши; файл из них проверяется без сервера командой `node dist/admin.js audit-verify <файл>` (номера, связи, хеши; первая проблема и её место). `POST /audit/checkpoints` (`audit:verify`, это может делать и токен) возвращает голову цепочки с HMAC, сделанным ключом, который выводится из `SW_AUTH_KEY` и не лежит в базе; сохранённая в другом месте, контрольная точка потом докажет, что история не переписана (даже согласованно) и хвост не отрезан: проверка отвечает `not_ours`, `event_missing`, `hash_differs` или `chain_broken`, либо `ok` с числом событий после неё. `node dist/admin.js audit-checkpoint` фиксирует голову с хоста (для задания cron). Пока нет: подписанные файлы выгрузки, внешняя метка времени, контрольные точки по расписанию внутри сервера.

## 9. Цепочка поставок (политика P-007)
Замороженные lock-файлы (`pnpm install --frozen-lockfile --ignore-scripts`), ручной обзор обновлений (без автоматических PR на проде), SBOM (CycloneDX), сканирование образов и зависимостей (Trivy, `pnpm audit`), проверка лицензий (AGPL для кода, скопированного из панели), закрепление версий базовых образов по дайджесту, подписанные релизы (опционально cosign), обязательный чек-лист ревью стороннего кода перед подключением.

## 10. Конфиденциальность
Нет телеметрии наружу; персональные данные пользователей Remnawave маскируются по умолчанию (стабильные псевдонимы), раскрытие по праву; журналы хранят минимум.

## 11. Резервные копии и аварийное восстановление Swellwright
Ежедневная зашифрованная копия базы (CMS: открытый ключ на сервере, приватный только у владельца экземпляра) и экспорт хранилища; копии вне сервера Swellwright (внешнее хранилище); ежемесячная проверка восстановления. Сценарий «Swellwright утрачен»: парк работает; доступ через аварийный ключ и ручное администрирование (SSH, API панели); восстановление из копии. Сценарий «Swellwright скомпрометирован»: отзыв токенов панели, смена CA SSH и ключей, смена DNS-доступа, аудит использования, перевыпуск секретов (мастер N28).

## 13. Решения по ранее открытым вопросам безопасности
Автораспечатывание хранилища по умолчанию выключено и включается явно как менее безопасный режим с записью в аудит, не на общем хосте с панелью (ADR 0006). Двойное согласование опасных операций входит в 1.0 как опциональная политика. Предупреждение при токене `*` показывается при выдаче и постоянным баннером (`00-index.md`, §6).

## 14. Безопасность плагинов
Плагин это чужой код с доступом к секретам: уровни доверия, права в манифесте с показом при включении, сетевой доступ только по списку хостов, выдача секретов на время вызова и только заявленного типа, запрет `postinstall`, подпись, аудит каждого вызова, немедленное отключение. `builtin` и `official` работают в процессе воркера под ограничениями, **`community` только контейнерами-сайдкарами** (без `docker.sock`, сетевая политика, лимиты) и декларативные драйверы без исполнения кода. Согласования через Telegram допускаются только для низкого и среднего риска. Подробно в `13-plugins-and-opensource.md`.
