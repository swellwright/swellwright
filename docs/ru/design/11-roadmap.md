# 11. Дорожная карта и фазы

Оценки ориентировочные (±50%), для одного сопровождающего (как в `docs/en/roadmap.md`); считаются в календарных неделях при регулярной работе. Общий объём порядка **42-53 недели** (с системой плагинов, контейнерным запуском сторонних плагинов и подготовкой публикации) до версии 1.0; работоспособный срез для развёртывания появляется после фазы 4 (около недели 12-16).

Принцип порядка: сначала основа и безопасность, затем **чтение** (панель, серверы), затем **запись с откатом** (развёртывание), затем масштаб (парк, Remnawave, мониторинг), терминал и самое рискованное после того, как безопасность отлажена.

## Фаза 0. Подготовка, решения и репозиторий (1-2 нед)
**Состав:** git-репозиторий с чистой историей и публичной структурой (`apps/`, `packages/`, `plugins/official/`, `docs/en|ru`, `deploy/`, `examples/`); лицензия AGPL-3.0-only, SPDX-заголовки, DCO, шаблоны CONTRIBUTING, SECURITY, CODE_OF_CONDUCT; каркас CI на GitHub Actions (линтеры, типы, тесты, gitleaks, лицензии, проверка отсутствия данных экземпляров); ADR по принятым решениям; **тестовый сервер** (отдельный VPS для полных циклов) и лабораторная панель в Docker.
**Приёмка:** пустой каркас собирается, CI зелёный, gitleaks чист, лаборатория поднимается, тестовый сервер доступен по SSH, панель 3.4.x принимает тестовую ноду вручную.

## Фаза 1. Каркас и среда плагинов (4-5 нед)
**Состав:** монорепо и Docker-среда разработки; API на NestJS с конвейером OpenAPI; аутентификация (пароль, TOTP, сессии, CSRF), роли; **хранилище секретов**; аудит с цепочкой хешей; **среда выполнения плагинов**: манифест, обнаружение, включение с правами, настройки по схеме, хранилище плагина, декларативные вклады интерфейса, декларативные драйверы, исполнение `builtin/official` в процессе воркера под ограничениями и **контейнерные сайдкары для `community`** (протокол связи, сетевая политика, генерация фрагмента compose, без `docker.sock`); контракты `plugin-api`; ручной режим DNS и хостинга и локальный вход как часть ядра; каркас интерфейса, тема, i18n (en, ru); health, ready, metrics; compose-развёртывание.
**Приёмка:** вход с TOTP; секрет создаётся и расшифровывается после распечатывания, запечатанное хранилище не читается; тестовый плагин-сайдкар подключается, показывает права, не достаёт БД и секреты, не может обратиться к недозволенному хосту, отключается без перезапуска ядра; декларативный драйвер работает без исполнения кода; цепочка аудита проверяется.
**После фазы:** можно безопасно хранить и менять постоянные параметры (токены, DNS).

## Фаза 2. Инвентарь и SSH-ядро (3-4 нед)
**Состав:** серверы и доступы, закрепление ключей хоста, сбор фактов, SSH-слой (пул, шаги отдельным процессом, чтение журнала, возобновление, sudo через stdin), SFTP, разовые команды и библиотека скриптов (аудит и диагностика), артефакты (установщик узла, `node-engine`), доступ только на чтение к снимку и проверке, интерфейс серверов.
**Приёмка:** сервер добавляется, показывается отпечаток, факты собираются; запуск команды на 3 нодах с выводом по нодам; обрыв SSH не убивает шаг и вывод дочитывается; хеши артефактов проверяются.
**После фазы:** доступны запуск команд и сбор фактов на серверах парка из интерфейса и API.

## Фаза 3. Интеграция с панелью (3-4 нед)
**Состав:** мастер подключения панели (токены со scopes, выброс JWT), типизированный клиент и адаптеры, чтение всех объектов, снимки и дифф, **линтер конвенций** и сверка хостов с нодами, **калькулятор влияния**, консоль API (чтение), эталонные проверки узла через SSH (только чтение; сделано, ADR 0045), дашборд v1 (сделано, ADR 0047), расчёт срока токенов.
**Приёмка:** панель подключена, объекты видны, сухой прогон правки профиля показывает влияние «рестарт N нод», сверка находит дрейф `address`, снимок и дифф работают, токен без прав не может писать.
**После фазы:** доступны проверка согласованности хостов и адресов нод (режим «только проверка») и аудит парка.

## Фаза 4. Движок и первые сценарии (4-6 нед)
**Состав:** долговечный движок (контрольные точки, возобновление, блокировки), согласования, политики P-001…P-016, события и WebSocket, интерфейс запуска (шкала, живой вывод, оценка, откат), сценарии **Усыновление (N01), Проверка (N12), Развёртывание (N03), Переразвёртывание (N04), Откат**, сквозные сценарные (золотые) тесты поведения, инъекция сбоев, первые запуски в лаборатории по чек-листу.
**Приёмка:** развёртывание в лаборатории проходит, откат даёт эквивалентность со снимком, убитый воркер подхватывается, политики блокируют общий профиль без согласования; повторный запуск ничего не меняет.
**После фазы (веха M4):** рабочие запуски идут из Swellwright.

## Фаза 5. DNS, сертификаты, переименование и жизненный цикл (3-4 нед)
**Состав:** DNS-плагины (`dns-rucenter` первым: OAuth по паролю, XML, commit/rollback, ожидание на авторитативных NS; затем `dns-cloudflare`, `dns-rfc2136`, декларативный драйвер), шаги и проверки DNS в ядре, управление распространением сертификатов (через плагины распространения сертификатов), **Переименование (N05) и финализация**, **Вывод (N06)**, **Замена заблокированной (N07)**, **Смена IP (N08)**, перенос между профилями (N09).
**Приёмка:** переименование на тестовом сервере с хоп-профилем, откат и финализация; замена ноды с понижением TTL; вывод без остатков; ядро без плагина DNS работает в ручном режиме.

## Фаза 6. Эксплуатация парка (4-5 нед)
**Состав:** обновление образа ноды и Xray (канарейка, волны, ворота), обновление ОС и ядра, перезагрузки по одной ноде, исправление дрейфа эталона, ACL порта API, UFW/fail2ban/SSH-политики с таймером страховки, ротация SSH-ключей (и центр сертификатов, если включён), каркас групповых операций, расписания и окна, уведомления (**плагин `notify-telegram` первым**: тревоги, итоги, согласования кнопками для низкого и среднего риска; затем вебхук и почта), канал уязвимостей (USN, GitHub), управление сертификатами узлов через `CertDistributor`.
**Приёмка:** волновое обновление образа на 5 тестовых нодах с остановкой на сбое ворот и откатом; ротация ключей без потери доступа; изменение списка адресов, которым открыт порт API нод, раскатывается на ноды; тревога и согласование приходят в Telegram.

## Фаза 7. Возможности Remnawave (5-7 нед)
**Состав:** редактор профилей (Monaco, конструктор инбаунда, песочница `xray -test`), ротация REALITY, синхронизация конвенций хостов, шаблоны подписок и правила SRR (раскатка, матрица клиентов), **цепочки хопов** (мастер, граф, проверка, служебные объекты, режим «прямой с резервом» экспериментально), плагины и сниппеты, биллинг, модуль пользователей (опционально), резервные копии панели и планировщик обновлений (через хост панели), снимки и GitOps-экспорт, запись через консоль API.
**Приёмка:** хоп вход → выход создаётся и удаляется мастером; ротация ключей на лабораторной ноде; раскатка шаблона с откатом; снимки восстанавливают отдельный объект.

## Фаза 8. Зонды и мониторинг (3-4 нед; можно параллельно с 6-7)
**Состав:** probe-agent (Linux и Windows), тесты (TCP, TLS/SNI, VLESS через `xray` с тестовым пользователем, заморозка 16-20 КБ, `mtr -T`), планировщик, матрица и суточные графики, алерты и подавление, журнал инцидентов, рекомендации (с согласованием), SLO.
**Приёмка:** агент на отдельной машине присылает результаты, матрица показывает периодическую недоступность в определённые часы суток, тревога на блок узла на транзите, рекомендация «заменить IP» без автодействия.

## Фаза 9. Безопасность и терминал (3-4 нед)
**Состав:** веб-терминал (xterm, запись, step-up, тайм-ауты), доработка центра сертификатов, инструмент проверки цепочки аудита, мастера инцидентов, ротации секретов, пентест-чеклист и исправления, учения по восстановлению (потеря хранилища, потеря сервера), политика исходящих соединений.
**Приёмка:** терминал недоступен без step-up, запись воспроизводится, учение «потеряли Swellwright» завершается доступом по аварийному ключу и восстановлением из копии.

## Фаза 10. Завершение, публикация и расширения (4-5 нед)
**Состав:** MCP-сервер, вебхуки, CLI `sw`, отчёты, полная локализация, драйверы API хостеров, модуль ACME (плагином, опционально), мультипанельность; **подготовка публикации:** чистка репозитория и истории, README и документация на английском (русская копия), демо-режим (фейковая панель и ноды), релизный конвейер (GHCR, SBOM, cosign), SECURITY.md, реестр плагинов (`registry/index.json` в репозитории), руководство автора плагинов, публичная дорожная карта.
**Приёмка:** все сценарии каталога покрыты тестами; чистый клон поднимается по README за 15 минут; в репозитории нет данных экземпляров (проверка автоматическая); OpenAPI и документация полные.

## Параллельность
Фаза 8 не зависит от 5-7 и может идти параллельно с ними (нужны только инвентарь и панель). Фаза 9 (терминал) начинается только после фазы 6 (центр сертификатов, политики доступа готовы).
