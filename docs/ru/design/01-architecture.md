# 01. Архитектура

## 1. Стек (согласован со стеком Remnawave; версии сверены с Remnawave 3.4.x)
| Слой | Выбор | Примечание |
|---|---|---|
| Бэкенд | NestJS 12 (в панели 11), TypeScript 6.0 (в панели 5.9, см. ADR 0009), Zod 4 (реестр маршрутов, ADR 0012), CQRS, `@nestjs/schedule`, `@nestjs/terminus`, `@willsoto/nestjs-prometheus` | как у панели |

| Монорепо | pnpm workspaces, Turborepo, строгие ESLint и TS | `--frozen-lockfile --ignore-scripts` |
| Контейнеры | Docker, multi-stage, non-root | как у панели |

## 2. Компоненты
```
 браузер ──HTTPS──> nginx (прокси) ─> swellwright-api  ──> PostgreSQL
    ^  WS/SSE (события, терминал)       │  ^             Valkey (готовность)
    └───────────────────────────────────┘  │
                                swellwright-worker ──SSH──> серверы / ноды
                                       │  └──HTTPS──> Remnawave API, DNS API, провайдеры, GitHub (релизы)
                              swellwright-probe (опц., на машинах-наблюдателях) ──HTTPS──> api
```
- **api**: REST и OpenAPI, WebSocket/SSE, раздача интерфейса, аутентификация, авторизация, создание запусков. В первом срезе движка он же держит цикл, который их исполняет, потому что ключ хранилища есть только в его памяти (ADR 0048).
- **worker** (планируется): тот же цикл в отдельном процессе, SSH, вызовы панели и DNS, зонды; масштабируется горизонтально (код без состояния в памяти), когда будет решено, как он получает секреты.
- **web**: статический интерфейс, собирается в образ api.
- **probe-agent** (опц.): лёгкий агент для машин в других сетях (разные операторы связи, разные площадки), только исходящий HTTPS к api, токен только на запись результатов.
- **cli** `sw`: тонкая оболочка над SDK.
- **mcp** (опц.): MCP-сервер поверх того же API (сначала чтение).

## 4. Процессная модель выполнения
- Запуск = запись в базе (ADR 0048): воркер берёт её из PostgreSQL с lease и fence-токеном, берёт блокировки на ресурсы (нода, зона DNS, панель, сервер панели) и выполняет этапы по описанию сценария.
- Состояние (этапы, шаги, события, записи отката, согласования) хранится в Postgres после каждого шага (контрольные точки). Падение воркера: запуск подхватывается другим воркером с последней точки; шаг, который шёл на ноде отдельным процессом, дочитывается по его журналу и коду возврата.
- События запуска транслируются в интерфейс (WebSocket/SSE) и сохраняются; вывод шагов хранится чанками с редактированием секретов.
- Согласования (approval gates) приостанавливают запуск до решения человека (подробно в `08-engine.md`).

## 5. SSH-слой
- **Закрепление ключа хоста**: первый вход показывает отпечаток для явного подтверждения, далее проверка; смена ключа блокирует операцию и поднимает тревогу (сценарий переустановки ОС подтверждается явно).
- **Режимы доступа**: пароль (для нового сервера, root), ключ, **SSH-сертификат** от собственного центра (рекомендуется, `05-security.md`), прыжковый хост (опционально).
- **Выполнение шагов**: запуск через `setsid` с журналом и файлом кода возврата в `<baseDir>/<id>/` (`/var/lib/swellwright/steps` для root, `~/.swellwright/steps` для остальных пользователей; ADR 0035), чтение журнала опросом через одно мультиплексированное соединение; обрыв связи не убивает шаг; повторное подключение продолжает чтение с прежнего смещения.
- **sudo**: пароль подаётся только через stdin, не в аргументах; для сертификатного входа sudo без пароля по ограниченному списку (варианты в `05`).
- **Терминал**: PTY через `ssh2`, XTerm в браузере, запись сессий, отдельное право и повышенная аутентификация (`05`).
- **Файлы**: SFTP (просмотр, загрузка, скачивание с контрольной суммой), массовая раздача.
- **Тайм-ауты и тревога**: keepalive, ограничения времени, отмена через сигнал на ноде.
- **Артефакты на ноде**: `/var/lib/swellwright/` (артефакты, снимки, журналы шагов, `node-engine.py`), права 700; после запуска секретные файлы удаляются (`shred`). Сделано (ADR 0039): копии, которые отправил Swellwright, лежат в `~/.swellwright/artifacts/<name>/<version>/` пользователя (права 700) или, от root, в `/var/lib/swellwright/artifacts/<name>/<version>/` (0755).

## 6. Узловой движок (на самой ноде)
Узловая часть реализована как Python-движок (команды `snap`, `undo-plan`, `undo`, `safety-arm`, `safety-restore`), загружается как артефакт и вызывается по SSH. Требует `python3` (есть на Ubuntu 22.04/24.04; иначе сценарий ставит `python3-minimal`). Версионируется вместе с `install.sh`; Swellwright сверяет хеш перед запуском.

## 7. Интеграции (исходящие)
Remnawave API (токены со scopes), DNS-провайдеры (по драйверам), API хостеров (по драйверам), GitHub releases и рекомендации по безопасности Ubuntu (USN) для каналов обновлений, Telegram и вебхуки (уведомления). Всё остальное закрыто политикой исходящего трафика (allowlist).

## 8. Топологии развёртывания
1. **Отдельный сервер (рекомендуется):** малая VM или машина; Swellwright работает отдельно от панели, без общего ядра и хоста с ней.
2. **На одном хосте с панелью:** отдельный пользователь без sudo, отдельная docker-сеть, **свои** Postgres и Valkey (не панели), лимиты ресурсов (cpus, memory, pids), firewall с ограничением исходящих соединений, без `docker.sock`, без чтения базы панели; отдельные бэкапы и отдельный vhost. Остаточный риск: общее ядро и хост (меры в `05`, `09`).
3. **Раннер в другой сети** (опционально): воркер-исполнитель с исходящим подключением к api для задач, которым нужен определённый сетевой путь.
4. **Агент на ноде** (опционально, позже): исходящий WSS к api для серверов без доступного SSH; по умолчанию не используется.

## 9. Наблюдаемость самого Swellwright
JSON-логи с редактированием секретов, `/health` и `/ready`, метрики Prometheus (запуски, длительность этапов, ошибки SSH, запуски в ожидании воркера, возраст блокировок, остаток срока токенов), трассировка OpenTelemetry (опционально).

## 10. Почему TypeScript
- Один стек с панелью (проще сопровождать: типы `@remnawave/backend-contract`, общие Zod-схемы между сервером, интерфейсом и CLI).
- Долговечное выполнение, очереди, события и блокировки удобнее строить в одном рантайме.
- Логика развёртывания (этапы, журнал, откат, DNS, переименование) реализуется в ядре на TypeScript и проверяется сквозными сценарными (золотыми) тестами поведения, которые выполняются автоматически.
- Узловая часть остаётся на sh и python: ноде нужен POSIX sh и минимум зависимостей.

## 11. Ядро и плагины
Ядро универсально (инвентарь, SSH, хранилище, движок, политики, клиент панели, терминал), а специфику провайдеров DNS и хостеров, внешний вход, уведомления, пакеты узла, конвенции и тесты зондов подключают плагины с манифестом, правами и изоляцией процессом. Встроенные поставщики пишутся плагинами с первой фазы. Контракты в `packages/plugin-api`, подробности и список плагинов в `13-plugins-and-opensource.md`.
