# 04. Интеграция с Remnawave

Источники: спецификация OpenAPI Remnawave (218 операций, 28 групп; сверено с Remnawave 3.4.x), репозитории `remnawave/backend` и `remnawave/frontend` (3.4.x).

## 1. Совместимость и версии
- Клиент строится на `@remnawave/backend-contract` с закреплённой версией под версию панели (Remnawave 3.4.x). Слой адаптеров по мажорным версиям: при смене контракта меняется один пакет `packages/remnawave`.
- Определение возможностей: `GET /api/system/metadata` (версия), `GET /api/system/configuration`, `GET /api/system/health`.
- **Контрактные тесты:** замороженная спека хранится в репозитории; задача CI сверяет её с новым релизом (`oasdiff`), показывает несовместимости. Поддержка окна «текущая и предыдущая минорная».
- Запись только через контракт с Zod-валидацией до отправки.
- **Сделано в фазе 3 (ADR 0041):** типизированный клиент `packages/remnawave` построен только на чтение (каждый эндпоинт объявлен с методом `GET`, в его типе нет метода записи) и работает поверх `node:https` со своими пределами: срок на запрос, предел размера ответа, повторы только для GET и только для сбоев, которые могут пройти, `Retry-After` соблюдается, число одновременных запросов ограничено, переход на другой источник не выполняется, TLS проверяется (свой удостоверяющий центр только для одного подключения, глобального выключателя по умолчанию нет), адрес проверяется в момент соединения по политике адресов SSH. Его схемы терпимые и свои, сняты с замороженного описания API 3.4.11 (`packages/remnawave/spec/`); `@remnawave/backend-contract` 3.4.11 панели это зависимость для разработки, используется как перекрёстная проверка, а не во время работы (он закрепляет вторую копию Zod и точен в каждом поле). Неизвестная форма это `PanelContractError` с названием эндпоинта и поля; версия вне окна (`3.4.x`) это `unsupported` с причиной. Адаптеры превращают объекты панели в нормализованные виды, маскируют в них каждый секрет одной функцией (чёрный список с ключевым отпечатком: поворот виден, а значение нет) и дают каждому объекту хеш его замаскированной конфигурации, который хранят и сравнивают снимки из ADR 0043.

## 2. Аутентификация и права панели
- **По умолчанию один токен** панели для Swellwright с правами `*`. Токен создаёт мастер подключения (P01) через админский JWT (токены API создавать и просматривать токеном нельзя), после чего JWT выбрасывается. Токен имеет срок жизни (`expiresInDays`): напоминание за 14 дней, ротация без простоя (выпустить новый, переключить, отозвать старый).
- **Опция «профиль наименьших прав»** (рекомендуется там, где доступ нужно ограничивать): токены со scopes. У токенов панели есть scopes (каталог `GET /api/tokens/scopes`, админский JWT, по ресурсам и признаку `read`/`write` на эндпоинт; `*` даёт всё); точные строки определяются при выполнении.
  | Профиль | Scopes | Для чего |
  |---|---|---|
  | `full` (по умолчанию) | `*` | всё |
  | `core` | запись: Nodes, Config Profiles, Hosts, Internal/External Squads, Subscription Templates/Settings/Page Configs, Infra Billing, Node Plugins, Snippets, Node Integrations, Metadata, Keygen, System (tools), Users и Bulk и HWID (если модуль включён); чтение: остальное | развёртывание и сопровождение без доступа к настройкам панели |
  | `readonly` | чтение всех ресурсов | зонды, отчёты, снимки, мониторинг |
  | `probe` | чтение нод и хостов; при необходимости Users для тестовых | агенты-зонды |
- Токен не передаётся на ноды и не покидает воркер; все операции с панелью идёт оркестратор.
- Контроль сроков: напоминания, аудит использования токена, предупреждение при `*` в публичном режиме («выдан полный доступ»).

## 4. Модель «панель как источник правды»
- Объекты панели читаются по расписанию и по событиям запусков; полный снимок раз в сутки (`PanelSnapshot`), частичные перед каждым изменением (для отката и диффа).
- **Сделано в фазе 3 (ADR 0043):** `POST /panel/snapshots` и фоновая задача (`SW_PANEL_SNAPSHOT_INTERVAL_HOURS`, 24) хранят замаскированную нормализованную конфигурацию каждого объекта, который токен вправе читать; если ничего не изменилось, снимок не делается. `GET /panel/snapshots/{id}/diff?against=live|<id>` сравнивает снимок с панелью сейчас или с другим снимком по объектам (сопоставление по uuid) и по полям (массивы сопоставляются по естественному ключу, множества без учёта порядка, списки клиентов только считаются, сменённый секрет показан как изменённый и скрытый, но не как значение). Снимки хранят только замаскированные значения: восстановлению объекта с секретами (фаза 7) нужен живой источник секретов, а не снимок. Частичный снимок перед изменением (`before_change`) зарезервирован для потока изменений.
- Намерения Swellwright (желаемые состояния) хранятся отдельно (`Convention`, `Blueprint`, `DnsIntent`); расхождение с панелью показывается как дрейф, а не перезаписывается молча.
- Запись выполняется схемой «прочитать, проверить хеш, изменить, записать, проверить»; конфликт (кто-то изменил в панели между чтением и записью) прерывает операцию.
- Идентификаторы: `uuid` узлов, хостов, профилей, сквадов; числовые `userId` у пользователей (с 3.x).
- Метаданные узла (`PUT /api/metadata/node/{uuid}`): связь с сервером Swellwright, версия эталона, окно обслуживания.

## 5. Правила влияния (наблюдаемое поведение Remnawave 3.4.x)
Эти факты зашиты в калькулятор влияния и в политики:
- Правка инбаунда **общего профиля** перезапускает Xray на **всех** нодах профиля (время перезапуска зависит от ноды и конфигурации).
- Изменение списка инбаундов во внутреннем скваде перезапускает только затронутую ноду.
- Нода держит один профиль и один активный инбаунд; теги инбаундов глобально уникальны.
- Хост подбирается по пересечению «сквад ∩ инбаунд»; хосты офлайн-нод попадают в подписку.
- `vlessRouteId` перезаписывает символы 14-17 UUID; номер маршрута цепочки (например `<N>`) резервируется за хопом; диапазон 0x4000-0x4FFF (16384-20479) и значение 0 избегаются (наблюдаемое поведение Remnawave 3.4.x; значение по умолчанию конвенции, настраивается); маршрут выбирает клиент, это не контроль доступа.
- Torrent Blocker в цепочке видит IP предыдущей ноды: на выходе цепочки по умолчанию не включать (настраивается).
- Служебный пользователь выхода хоп-цепочки по умолчанию не удалять и не отключать (политика, настраивается).
- Если порт API ноды открыт только для адреса панели, смена этого адреса делает ноды недоступными для панели (клиенты продолжают работать).
- REALITY-сервер в свежих версиях Xray отправляет на target клиентов без X25519MLKEM768: допустимы `chrome`, `firefox`, `safari` (наблюдаемое поведение; проверять по релизам Xray).

## 6. Конвенции именования (по умолчанию, настраиваются)
- По умолчанию: имена ноды `CC-NN`; домен `{cc}{n}.<база>`; remark хоста `🇳🇱 🎯 XX-01 - выборочная маршрутизация` и `🌐 ... - глобальный режим`; хоп-хосты вида `🇦🇦 🠢 🇧🇧 ...`.
- Хосты: `address` = IP ноды, `sni` = домен ноды (явно), порт 443, `fingerprint` по политике, типы подписок и шаблоны копируются с образца.
- Имена сквадов и профилей: буквы, цифры, пробел, `_`, `-`.
- По умолчанию тестовые объекты помечаются 🧪 (пометка настраивается) и защищены от массовых правок.

## 7. Расширение возможностей Remnawave (что получает администратор помимо автоматизации)
1. Линтер конвенций и сверка хостов с нодами в реальном времени.
2. Калькулятор влияния и «сухой прогон» для любой правки.
3. Канареечные и волновые раскатки профилей, шаблонов, образов.
4. Снимки, дифф и восстановление отдельных объектов, экспорт в YAML (GitOps).
5. Конструктор хопов и многозвенных цепочек, граф топологии.
6. Каталог scopes и выдача токенов с наименьшими правами, напоминания.
7. Консоль API с контрактной валидацией и журналом.
8. Мониторинг с зондами из разных сетей и суточные профили доступности.
9. Автоматизация переименования, замены и вывода нод целиком (панель, DNS, сервер).
10. Отчёты по стоимости и сроку оплаты (биллинг).
Эти возможности остаются внешними (Swellwright не патчит панель). Запросы на улучшение апстрима можно оформлять отдельно (например, шаблонные операции, события) после накопления опыта.

## 8. Взаимодействие с сервером панели по SSH
Часть сценариев не покрывается API панели: распространение сертификатов (cron-скрипты), резервные копии панели, обновление контейнеров, nginx. Swellwright может работать на отдельном хосте (основной вариант) или на одном хосте с панелью (возможный вариант); в обоих случаях для таких сценариев вводится «хост панели» как обычный сервер инвентаря со своим профилем доступа, ограниченным sudo и отдельными политиками: любые изменения на нём только по согласованию, без удаления данных; доступ к Docker-сокету не даётся, команды идут в `docker compose` в каталоге панели.

## 9. Чего Swellwright не делает с панелью
Не читает базу панели напрямую, не правит её файлы, не вмешивается в её обновление без явного сценария, не использует недокументированные эндпоинты.
