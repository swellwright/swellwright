# 08. Движок сценариев, политики и стратегии

Движок задаёт этапы, журнал, откат, ожидания и страховку, а также долговечное выполнение, согласования, стратегии раскатки и политики.

## 1. Жизненный цикл запуска
`planned` (сухой прогон, ничего не меняет) → `awaiting_approval` → `queued` → `running` (этапы по порядку) → `succeeded` | `failed` | `cancelled`; после сбоя: `rollback_requested` → `rolling_back` → `rolled_back` | `rollback_partial`. Состояния `paused` (по запросу или по политике) и `awaiting_input` (ожидание человека: DNS, ручной шаг у хостера).

## 2. Контракт шага
```ts
interface Step<P, R> {
  key: string;                       // например "node.install.nginx"
  title(ctx): string;
  estimateSeconds(ctx): number;      // по истории, иначе по умолчанию
  locks(ctx): ResourceRef[];         // ресурсы, которые блокируются
  plan(ctx, p: P): Promise<PlanItem[]>;   // что изменит (чтение)
  apply(ctx, p: P): Promise<R>;      // выполнение, идемпотентно
  verify?(ctx, r: R): Promise<void>; // проверка после
  undo?(ctx, r: R): Promise<UndoRecord[]>; // как отменить (данные без секретов)
}
```
Требования: идемпотентность, детерминированные параметры, секреты только по ссылке на хранилище, исключения с кодами из `06-api-openapi.md`.

## 3. Определение сценария
```ts
defineWorkflow('node.deploy', {
  params: DeployParamsSchema,                    // Zod, в интерфейсе строится форма
  risk: 'high',
  locks: (p) => [node(p.name), server(p.serverId), dnsZone(p.zone)],
  stages: (p) => [
    stage('connect', ssh.connect(p)),
    when(p.dns === 'driver', stage('dns', dns.ensureA(p))),
    stage('snapshot', node.snapshot(p)),
    stage('preflight', installer.run('preflight', p)),
    ...installer.steps(['base','firewall','docker','node'], p),   // состав задаёт вариант узла
    when(needsReboot, stage('reboot', ssh.rebootAndWait(p))),
    stage('panel', panel.createNodeObjects(p)),
    stage('online', panel.waitNodeOnline(p)),
    stage('verify', installer.run('verify', p)),
    stage('access', access.installAndVerify(p)),
    stage('ssh', ssh.hardening(p)),
    stage('cleanup', node.cleanup(p)),
  ],
  onFailure: 'ask',       // ask | rollback | keep
});
```
Те же шаги используют переразвёртывание, переименование, вывод и замена: общие «кирпичи», разные композиции.

## 4. Долговечность и возобновление
- Контрольная точка в БД после каждого шага: `RunStep` + записи отката + выходные значения (без секретов).
- Падение воркера: запуск переходит к другому воркеру, выполняется с первого незавершённого шага; шаг, уже идущий на ноде, **присоединяется** к существующему процессу по журналу и файлу кода возврата.
- **Возобновление по просьбе человека:** продолжить с упавшего этапа после исправления причины; повторный ввод секретов не требуется (секреты в хранилище).
- Отмена: кооперативная (между шагами) и жёсткая (сигнал шагу на ноде); отмена перед необратимыми шагами безопасна, после предлагается откат.
- Тайм-ауты шагов и «сердцебиение» длинных операций; повторы с экспоненциальной паузой для сетевых ошибок; не повторяются шаги, помеченные неидемпотентными без явного решения.

## 5. Журнал и откат
- `UndoRecord`: тип операции и данные без секретов; откат идёт в обратном порядке и выполняется по **текущему** состоянию мира (точечно): удалить созданное, вернуть прежнее значение, убрать инбаунд по тегу, вернуть строку cert-sync, вернуть DNS, откатить сервер по снимку (`node-engine undo`).
- Откат сервера защищён: ожидание окончания идущих шагов, проверка присутствия снимка, перечень «что не откатывается» заранее.
- Верификация отката: повторный расчёт расхождений со снимком; запуск считается `rolled_back`, только если расхождений нет; иначе `rollback_partial` со списком.
- Откат сам журналируется и может быть продолжен.

## 6. Согласования (approval gates)
- Автоматически создаются по риску, политике или параметрам (общий профиль, массовая операция, смена доступа, удаление).
- Содержат план, влияние, откат, блокировки, срок действия; одобряют роль `owner` или назначенные; высокий риск требует step-up и подтверждающей фразы.
- Запуск без одобрения не стартует; одобрение привязано к хешу плана (изменение параметров аннулирует).

## 7. Стратегии раскатки на несколько целей
| Стратегия | Поведение |
|---|---|
| `sequential` | по одной цели, остановка при первом сбое |
| `canary` | сначала одна цель, пауза и проверка, затем остальные |
| `waves` | пачки по N, между ними пауза и проверка, порог ошибок |
| `parallel(N)` | не более N одновременно (для безопасных операций) |

Проверки между целями (health gates): нода online, время Xray, пользователи online (не упали), задержка подписки, заданные пользователем проверки. Правила паузы и автоотката (`stopOnFailure`, `maxFailures`, `autoRollbackOnGateFail`). Окна обслуживания и «тихие часы».

## 8. Политики (guardrails)
Правила безопасной эксплуатации заданы кодом. Действия: `block`, `require-approval`, `warn`. Редактируются ролью `owner` (с аудитом), по умолчанию включены.

| Код | Правило |
|---|---|
| P-001 | по умолчанию только чтение; запись требует утверждённого плана |
| P-002 | бэкап текущего состояния (снимок объекта или дамп) до изменения, откат объявлен, проверка после |
| P-003 | правка общего профиля или любого инбаунда, затрагивающая несколько нод: показать список нод и время, согласование и окно; предпочесть клон профиля |
| P-004 | массовые операции (bulk, `restart-all`, перезагрузки, SSH/UFW/sysctl/ядро) только по одной ноде или малыми группами, сначала канарейка |
| P-005 | запрет ужесточения SSH (пароли, root), пока нет проверенного запасного входа |
| P-006 | fingerprint и транспорт: один параметр за раз, запись что и когда |
| P-007 | чужой код, расширения, пакеты: только после проверки и разрешения |
| P-008 | утверждения из интернета в рекомендациях помечаются «измерено / сообщество / предположение» |
| P-009 | изменения нод идут только через версионный артефакт; ручной шаг без артефакта запрещён |
| P-010 | Опциональная политика (пример в `examples/policies`): служебный пользователь выхода цепочки защищён; `vlessRoute` вне 0x4000-0x4FFF и не 0; Torrent Blocker на выходе цепочки запрещён |
| P-011 | тестовые объекты (по тегу или пометке в названии) не меняются массовыми операциями |
| P-012 | Опциональная политика (пример в `examples/policies`): хост панели выделен, если на нём работает и нода: операции с ним только по явному сценарию, без затрагивания стека панели |
| P-013 | перед запретом пароля SSH нужен проверенный вход ключом на каждой ноде |
| P-014 | удаление ноды, профиля, DNS-зоны, пользователя — только с подтверждающей фразой |
| P-015 | Опциональная политика (пример в `examples/policies`): смена внешнего адреса панели: сначала ACL нод, потом остальное |
| P-016 | **режим лаборатории:** запуск ограничивается объектами с тегом `sw-lab` (тестовый узел, профиль, сквад); изменение объектов вне набора блокируется; включается для проверок в лаборатории |

## 10. Типичные сбои, учитываемые шагами
Шаги и проверки заранее учитывают типичные сбои при работе с нодами:
- Временная блокировка менеджера пакетов (`dpkg`/`apt`, например фоновые автообновления): ожидание освобождения блокировки перед `apt` и `DPkg::Lock::Timeout`.
- Недоступность репозитория или ключа репозитория: получение ключа во временный файл с проверкой, повторы, запасной способ получения (https и http).
- Повтор получения внешних артефактов (пакеты, образы, файлы): повтор с паузой и проверка результата.
- Потеря SSH после изменения firewall: таймер страховки SSH/UFW с автоматическим возвратом, подтверждение нового входа.
- Перезагрузка посреди шага: ожидание возврата ноды и продолжение шага по журналу.
- `python3` на ноде как предусловие; установка при отсутствии.
- Шаги на ноде отдельным процессом (`setsid`), чтение журнала опросом, возобновление.
- Снимок до первого изменения и откат по снимку, файлы оставшихся пакетов не удаляются.
- Порядок «сначала DNS и сертификат, потом объекты панели», ожидание сертификата, ожидание online.
- Проверка авторитативных NS после правки DNS и учёт кэша резолвера.
- Удаление старых ключей хоста при переразвёртывании.

## 11. Расписания и окна
Cron-выражения, часовые пояса, окна обслуживания по нодам и группам, «квота одновременных изменений» по парку, исключения на праздники; расписания: проверка эталона (в фазе 3 сделана простым интервалом, `SW_CHECKS_INTERVAL_HOURS`, ADR 0045: со сдвигом, пропускается при запечатанном хранилище и просроченном секрете), проверка обновлений, снимки панели, бэкапы, проверка восстановления, ежедневный отчёт, зонды.

## 12. Наблюдаемость движка
Метрики: длительность этапов, ошибки по типам, число откатов, возраст блокировок, очередь, время согласований. Таймлайн запуска сохраняется для сравнения «как обычно» и поиска регрессий скорости.

## 13. Сквозные сценарные (золотые) тесты поведения
Сквозные сценарии (развёртывание, сбой на шаге с откатом, переразвёртывание, переименование и его финализация, откат по журналу, DNS-сценарии) оформляются как золотые тесты движка: фиксированный вход должен давать фиксированные записи отката и фиксированный порядок этапов.
