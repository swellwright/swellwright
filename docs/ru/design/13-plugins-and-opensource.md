# 13. Плагины и открытый проект (универсальное ядро)

Проект публикуется на GitHub для всех. Ядро универсально; всё, что относится к конкретной инфраструктуре (RU-CENTER, соглашения об именах, особая схема нод), это **подключаемые компоненты**, как варианты входа в Remnawave (OAuth2, passkey, Telegram). Лицензия AGPL-3.0-only.

## 1. Принципы
1. **Ядро знает про Remnawave и про SSH, но не знает про конкретного провайдера DNS, хостера, оператора связи, схему имён или собственную схему нод.**
2. **Всё индивидуальное убирается без правки ядра:** отключил плагин или пакет, ядро работает.
3. **Конфигурация вместо кода:** домены, IP, имена, токены, пароли, ключи и списки нод живут в данных экземпляра (БД Swellwright), а не в репозитории; код публичен и параметризован.
4. **Безопасные значения по умолчанию общие для всех;** дополнительные политики опциональны.
5. **Первые собственные провайдеры делаются плагинами** (RU-CENTER, Cloudflare и др.): так интерфейс расширений проверяется на практике с первого дня.
6. **Универсальность без потери функций:** схема узла «selfsteal» (HAProxy SNI → Xray → nginx SelfSNI, заглушка, регистрация в распространении сертификатов) поставляется как официальный «пакет узла» для всех, кому она нужна.

## 2a. Как решаем: ядро или плагин (всё публично)
- **Ядро**, если нужно любому администратору Remnawave или это общий механизм безопасности ОС (инвентарь, SSH, хранилище, движок, клиент панели, порт API ноды только для панели, fail2ban, sysctl, проверка сертификатов, цепочки хопов как возможность).
- **Официальный плагин**, если это конкретный сервис, протокол или готовая схема (DNS-провайдеры, уведомления, пакет узла `node-selfsteal`, распространение сертификатов, клиент Happ, адаптеры к внешним скриптам синхронизации).
- **Пример** (`examples/`), если это набор соглашений и шаблонов, которые каждый настраивает под себя (конвенции имён, шаблоны подписок, пресеты хопов, наборы политик).
- **Данные экземпляра** (не код, не публикуются): домены, IP, имена нод, токены, пароли, ключи, списки нод, результаты. Вводятся в Swellwright и хранятся в его БД.
Пограничные случаи:
| Что | Решение | Почему |
|---|---|---|
| **cert-sync** (внешний скрипт синхронизации сертификатов) | **плагин**: ядро знает интерфейс `CertDistributor`; обобщённая схема `certs-rsync`; адаптер к внешнему скрипту синхронизации сертификатов `certs-cron-script` (команда, список нод и пользователь задаются в настройках) | задача «доставить сертификат на ноды» универсальна, а способ задаётся настройками |
| Выпуск wildcard (внешний инструмент выпуска, DNS-01 через DNS-плагин, например RU-CENTER) | универсальный интерфейс `CertIssuer`, плагины `acme-*`, `dns-rucenter` | внешний источник описывается настройками плагина |
| Схема HAProxy SNI → Xray → nginx SelfSNI, заглушка | плагин `node-selfsteal` | зависит от выбранной маскировки |
| Порт API ноды только для панели (DOCKER-USER, UFW) | ядро (узел «стандарт») | нужно любому узлу Remnawave |
| Заголовки Happ (`providerid`, `socks-auth-mode`, ...) | плагин `client-happ` | зависит от клиента |
| Хопы | ядро (механика); номер маршрута, сервисный пользователь и пресет цепочки это данные экземпляра | возможность универсальна |
| Узел на одном хосте с панелью | поддерживается политикой, пример в `examples/policies` (параметры в настройках) | зависит от топологии установки |
| Соглашения об именах (`🇳🇱 🎯 XX-01 ...`) | пример `examples/conventions` | настраивается под себя |
| Шаблоны подписок (выборочная маршрутизация и «глобальный режим») | примеры `examples/templates/` без учётных данных и реальных доменов | полезны другим |

## 3. Точки расширения (контракты в `packages/plugin-api`)
```ts
interface DnsProvider {
  id: string; configSchema: ZodSchema; secretKinds: string[];
  listZones(ctx): Promise<Zone[]>;
  listRecords(ctx, zone): Promise<DnsRecord[]>;
  plan(ctx, intent: DnsIntent): Promise<DnsPlan>;           // чтение
  apply(ctx, plan: DnsPlan): Promise<DnsChange>;            // запись, с commit если нужен
  undo(ctx, change: DnsChange): Promise<void>;
  authoritativeServers?(ctx, zone): Promise<string[]>;      // для проверки видимости
}
interface NodeFlavor {                      // «как собирается и проверяется узел»
  id: string; params: ZodSchema; supportedOs: string[];
  artifacts: Artifact[];                    // sh, python, шаблоны конфигов, хеши
  steps(ctx): StepDef[];                    // установка
  checks(ctx): CheckDef[];                  // эталонные проверки узла
  rename?(ctx): StepDef[];                  // переименование
  facts?(ctx): FactCollector[];             // что собирать
}
```
```ts
interface CertDistributor {                 // как сертификат попадает на ноды
  id: string; configSchema: ZodSchema;
  registerNode(ctx, node): Promise<UndoRecord[]>;      // добавить ноду в схему распространения
  unregisterNode(ctx, node): Promise<UndoRecord[]>;
  syncNow(ctx, nodes: Node[]): Promise<SyncResult[]>;
  forgetHostKey?(ctx, node): Promise<void>;             // при переразвёртывании
  status(ctx, node): Promise<CertStatus>;
}
```
Остальные точки: `CertDistributor`, `CertIssuer` (ACME), `ClientProfile` (пакеты совместимости клиентов), `AuthProvider`, `HostingProvider`, `NotificationChannel`, `SecretBackend`, `AccessMethod`, `BaselinePack`, `ConventionPack`, `WorkflowPack`, `ProbeTest`, `ReportTemplate`, `PanelAdapter`, `UiContribution`. Для REST-сервисов (DNS, хостинг, уведомления) допускаются **декларативные драйверы** (YAML: аутентификация, запросы, отображение ответов), чтобы добавлять провайдеров без исполнения чужого кода.

## 4. Манифест плагина (`swellwright.plugin.json`)
```json
{
  "id": "dns-rucenter", "version": "1.0.0", "name": "RU-CENTER (NIC.RU) DNS",
  "engines": { "swellwright": ">=1.0 <2" },
  "provides": [{ "kind": "DnsProvider", "entry": "./dist/provider.js" }],
  "permissions": {
    "network": ["api.nic.ru:443"],
    "secrets": ["dns-oauth"],
    "panel": [], "ssh": false
  },
  "config": { "schema": "./config.schema.json" },
  "ui": { "settings": "./ui/settings.json" },
  "storage": { "namespace": "dns-rucenter" },
  "license": "AGPL-3.0-only", "signature": "..."
}
```
- **Права запрашиваются явно** и показываются при включении («плагин хочет обращаться к `api.nic.ru` и читать секреты типа `dns-oauth`»).
- **Хранилище плагина:** изолированное пространство имён (ключ-значение и JSON-таблицы), без собственных миграций БД и без доступа к схеме ядра.
- **Настройки:** схема из манифеста строит форму в интерфейсе; секреты сохраняются в хранилище, не в настройках плагина.
- **Правила, которые проверяет схема** (`packages/plugin-api`, ADR 0021): неизвестные ключи отвергаются; пути относительные и остаются внутри плагина; сетевые разрешения это публичные имена `host:port` (без подстановок, адресов и локальных имён); декларативный драйвер только для REST-видов; пространство хранилища равно id; каталог назван по id; в `package.json` нет скриптов установки; ссылки не разворачиваются. Обнаружение только описывает плагины (`available`, `incompatible`, `invalid` со всеми причинами) и ничего не загружает и не запускает.
- **Совместимость:** диапазон версий ядра; несовместимые плагины не загружаются и показываются в интерфейсе с причиной.

## 5. Жизненный цикл
Обнаружение (каталог `plugins/` смонтированный в контейнер, пакеты npm `@swellwright/plugin-*` и `swellwright-plugin-*`, локальные каталоги) → показ в интерфейсе («Настройки → Плагины») → включение с подтверждением прав → настройка → использование → обновление (без автоматической загрузки из сети; сначала дифф прав) → отключение → удаление (данные плагина по выбору). События плагина попадают в аудит.

**Реализовано в фазе 1 (ADR 0027):** включение. Одобрение относится к содержимому: SHA-256 по всем файлам плагина (ссылки внутри запрещены) показывается администратору и возвращается с запросом, поэтому одобрить можно только увиденные файлы. Одобрение, его разрешения и кто его дал сохраняются; плагин, который пропал, непригоден или имеет другие файлы, выключается при следующем чтении и при запуске с записью в журнале, а новое включение это новое одобрение с показом того, что изменилось. Маршруты защищены `plugins:read` и `plugins:manage` (подтверждение кодом); страница «Настройки → Плагины». Каталоги: `SW_PLUGINS_OFFICIAL_DIR`, `SW_PLUGINS_LOCAL_DIR`. 

**Реализовано в фазе 1 (ADR 0028):** хост. Каждый одобренный плагин при первом обращении запускается в собственном процессе под моделью разрешений Node, загружает модули, названные в манифесте, и отвечает на вызовы методов по каналу IPC. Модуль это `export default definePlugin({ methods: { name(params, context) { ... } } })` (из `@swellwright/plugin-api`); `context.fetch(url, init)` это единственный выход, он ведёт только к одобренным парам `host:port`, по https, на публичные адреса, через ядро (до 1 МиБ наружу и 4 МиБ обратно, без редиректов). Ограничения: предел кучи (`SW_PLUGIN_MEMORY_MIB`), срок на вызов (`SW_PLUGIN_CALL_TIMEOUT_SECONDS`), остановка простаивающего (`SW_PLUGIN_IDLE_MINUTES`), пауза после повторных сбоев. `POST /plugins/{id}/check` загружает плагин и перечисляет, что он предлагает; страница «Плагины» показывает состояние выполнения. У декларативных плагинов процесса нет. Секреты выдаются (ниже); панель и SSH можно одобрить, но пока не выдаются.

**Реализовано в фазе 1 (ADR 0031):** контейнеры-спутники, способ запуска кода плагинов от других. Манифест называет спутник и описывает контейнер (`image` с закреплённым дайджестом, `port`, память, процессоры); доверие `community` (`SW_PLUGINS_COMMUNITY_DIR`) допускает спутник или драйвер, но не код в процессе Swellwright. Swellwright сам контейнер не запускает: `GET /plugins/{id}/sidecar` отдаёт фрагмент compose (сеть `internal` без выхода, только чтение, без возможностей и привилегий, не root, пределы памяти, процессора и числа процессов, ничего не опубликовано), который применяет администратор. Ядро и контейнер подтверждают себя токеном из идентификатора плагина и дайджеста его файлов; в сеть, к секрету и к своему хранилищу контейнер выходит только через `POST /plugins/{id}/gateway`, который на всё, кроме токена одобренного, включённого и неизменённого плагина, отвечает 401. Протокол это два HTTP-вызова (`/describe`, `/call`); образец это `examples/sidecar-node`.

**Усилено после ревью 2026-11 ([ADR 0050](../../adr/0050-plugin-boundaries-and-vault-key-generations.md)):** дайджест одобрения включает `.git`, если каталог присутствует, но манифест должен указывать на файлы рабочего дерева. Символические ссылки и файлы с несколькими жёсткими ссылками не допускаются. Ядро проверяет тип и размер файла до чтения. Оно проверяет сообщения IPC и обслуживает не более 8 запросов плагина одновременно и 256 за вызов. Неверное сообщение завершает только процесс плагина. Вывод процесса и текст исключений при запуске не попадают в статус. Отключение или повторное одобрение завершает прежний процесс. Декларативные операции ограничены по времени и объёму вычислений; проверка IPv6 учитывает префиксы трансляции и туннелирования. Шлюз спутников проверяет токен до поиска плагинов; у каждого спутника в сгенерированном фрагменте своя внутренняя сеть. О ротации и восстановлении ключей см. [Безопасность](05-security.md).

**Реализовано в фазе 1 (ADR 0030):** декларативные драйверы. `provides[].driver` это YAML-файл, который ядро читает и исполняет как описание: операции с объявленными параметрами, до восьми шагов запросов `https` (следующий шаг может читать предыдущий) и форма результата; значения берутся только из `params`, `config`, `secret` (только в запросах), прежних `steps` и переменной `each`; всё, что подставляется в URL, кодируется; каждый запрос идёт через тот же шлюз и то же сохранённое одобрение, что и код плагина. Драйвер проверяется при обнаружении плагина: хосты, к которым он обращается, должны быть в `permissions.network`, настройки и секреты, которые он читает, объявлены. Первый официальный плагин, `plugins/official/notify-telegram`, это драйвер.

**Реализовано в фазе 1 (ADR 0029 и 0031):** проверяемые настройки, привязанные секреты vault, отдельное хранилище плагина и контейнеры-сайдкары. Процесс Node не является песочницей для недоверенного кода. Сайдкары используют аутентифицированный HTTP-шлюз: одобрите плагин перед экспортом фрагмента и повторите экспорт после переодобрения.

## 6. Безопасность плагинов
Плагин это сторонний код с доступом к секретам, поэтому:
- **Уровни доверия:** `official`, `community` и `local` определяются настроенными каталогами. За локальный плагин с исполняемым кодом отвечает администратор.
- **Изоляция:** плагин исполняется в отдельном процессе-воркере с ограничениями (модель разрешений Node, где доступна: ограничение файловой системы, дочерних процессов, сети); сетевой доступ только через прокси ядра по списку из манифеста; плагин не видит БД, Redis, чужие секреты и ключи, получает секрет только на время вызова и только заявленного типа; лимиты CPU, памяти и времени вызова.
- **Контейнерные плагины.** Плагины `community` могут быть сайдкарами (образ OCI и манифест) или декларативными драйверами. Сайдкар использует аутентифицированный HTTP-шлюз во внутренней сети и не имеет прямого доступа к БД. У ядра нет `docker.sock`: сгенерированный фрагмент Compose применяет администратор. Официальный и локальный код может выполняться в ограниченном дочернем процессе; разрешения Node не обеспечивают изоляцию враждебного кода.
- **Реализовано:** запрет скриптов установки, включая `postinstall`; SHA-256 связывает одобрение с файлами плагина, образы сайдкаров закреплены по дайджесту, обновления одобряются вручную. В аудит попадают события жизненного цикла, отказы и использование секретов, но не их значения.
- **Планируется:** проверка подписи, SBOM для плагинов и запись каждого вызова плагина в аудит.

При поиске плагинов и вычислении дайджеста ядро проверяет, что путь остаётся внутри разрешённого каталога, до обращения к файловой системе. Используйте относительные пути с прямыми слешами, без сегментов `..`, обратных слешей, NUL и обозначений дисков или потоков.

Шлюз сайдкаров резервирует слоты проверки для совпавших токенов и перед выполнением запроса проверяет актуальное одобрение. Он записывает каждую успешную выдачу секрета и ограничивает запросы до 120 в минуту на плагин и экземпляр API. Для процессов и декларативных драйверов запись делается по возможности, не чаще раза в десять минут на пару «плагин, секрет». Перед обновлением или сменой схемы настроек проверьте сохранённые привязки. Для одобрения плагина со значениями в секретных полях нужно `vault:reveal`. Плагин, который не удалось проверить, нельзя вызвать: три сбоя подряд, учитываемые не чаще раза в секунду, или файл с несколькими жёсткими ссылками останавливают локальный процесс и фиксируются как `plugin.unverifiable` без отзыва одобрения. Ограничения шлюза и рекомендации для Linux — в [ADR 0050](../../adr/0050-plugin-boundaries-and-vault-key-generations.md).

## 7. Официальные плагины и пакеты (первая партия)

| `certs-rsync`, `certs-push-ssh` | распространение сертификатов на ноды (обобщённый cert-sync: источник, получатель с `rrsync`, перезагрузка, список нод в конфигурации) или отправка по SFTP |

| `node-selfsteal` | пакет узла: HAProxy по SNI → Xray → nginx (self-steal), заглушка, регистрация в распространении сертификатов, эталонные проверки |

## 8. Специфичные компоненты: публичные плагины и примеры
**Публично всё, что является кодом**, включая интеграцию RU-CENTER и схему узла `selfsteal`; специфичные компоненты оформлены как плагины и примеры, которыми может пользоваться любой:
| Компонент | Где в публичном репозитории |
|---|---|
| Интеграция RU-CENTER (NIC.RU) | `plugins/official/dns-rucenter` |
| cert-sync (внешний скрипт синхронизации сертификатов) | `plugins/official/certs-cron-script`, `certs-rsync` |
| Схема HAProxy SNI → Xray → nginx SelfSNI, заглушка | `plugins/official/node-selfsteal` |
| Клиент Happ (заголовки SRR, проверки) | `plugins/official/client-happ` |
| Соглашения об именах и remark | `examples/conventions` |
| Политики хоп-службы, диапазона `vlessRoute`, «панель и нода на одном хосте», порядка смены адреса панели | `examples/policies/` (параметры в настройках) |
| Шаблоны подписок и пресеты хопов | `examples/templates/`, `examples/chains/` (без учётных данных и реальных доменов) |
**Не публикуются данные экземпляра:** домены, IP-адреса, имена нод и их список, токены, пароли, ключи, `.env`, резервные копии, результаты проверок и зондов, журналы аудита, данные пользователей. Они вводятся в Swellwright и хранятся в его БД (экспорт YAML и резервные копии), в репозиторий не попадают.
**Данные реальных установок** (домены, IP, топология, результаты аудита) в репозиторий не попадают: они раскрывают узлы.

## 9. Универсальность ядра: проверки
- В коде ядра нет упоминаний конкретного DNS-провайдера, а также доменов и IP конкретных установок (проверка в CI).
- Все имена, шаблоны и значения по умолчанию общие (`{cc}{n}.{base}`, пример `example.com`).
- Работает без плагинов: ручной DNS, ручной хостер, стандартный узел, локальный вход.
- Демо-режим: `docker compose` с фейковой панелью и фейковыми нодами для знакомства за 5 минут.
- Документация ориентирована на любого администратора Remnawave, примеры нейтральны.

## 10. Открытый проект: организация репозитория
```
swellwright/                     (GitHub, AGPL-3.0-only)
  apps/ api, worker, web, cli, probe-agent
  packages/ contracts, engine, steps, remnawave, ssh, vault, policy, plugin-api, ui, testing ...
  plugins/official/ dns-rucenter, dns-cloudflare, node-selfsteal, ...
  docs/ en/ (канонический), ru/
  deploy/ compose, nginx, systemd, kubernetes (позже)
  examples/ пакеты конвенций, декларативные драйверы, демо
  registry/ index.json реестра плагинов
  .github/ workflows, issue и PR шаблоны, CODEOWNERS
  LICENSE  THIRD_PARTY_NOTICES  CONTRIBUTING.md  CODE_OF_CONDUCT.md  SECURITY.md  CHANGELOG.md  README.md
```
- **Лицензия:** AGPL-3.0-only (совместима с кодом Remnawave, который тоже `AGPL-3.0-only`, это допускает перенос частей при необходимости); SPDX-заголовки в файлах; `THIRD_PARTY_NOTICES`; проверка совместимости лицензий зависимостей в CI (MIT, Apache-2.0, BSD допустимы; коммерческие, как Highcharts, нет).
- **Вклад:** DCO (`Signed-off-by`), правила стиля, шаблоны issues и PR, чек-лист для плагинов, `CODEOWNERS`.
- **Безопасность проекта:** `SECURITY.md` (ответственное раскрытие, контакты, сроки), публичная модель угроз, образец защищённой конфигурации, гайд по усилению.
- **Релизы:** семантические версии, CHANGELOG, образы в GHCR (закреплены по дайджесту), SBOM (CycloneDX), подписи cosign, политика поддержки (какие версии Remnawave и ОС).
- **CI на GitHub Actions:** линтеры, типы, тесты (модульные, контрактные), сборка образов, Trivy, gitleaks, проверка OpenAPI (`oasdiff`), проверка лицензий, проверка отсутствия данных экземпляров.
- **Документация:** английский канонический, русский полная копия, сайт документации позже; OpenAPI публикуется как артефакт релиза; руководство «Как написать плагин».
- **Реестр плагинов** живёт в том же репозитории (`registry/index.json`: ссылки, версии, хеши, уровень доверия); сторонние плагины попадают в него через PR. Swellwright **ничего не скачивает сам** без явного действия администратора.
- **Знаки и имя:** «Swellwright» неофициальный проект для Remnawave; в README и интерфейсе указано «not affiliated with Remnawave».
- **AGPL и публичные экземпляры:** сетевое использование требует предложить пользователям исходный код; в интерфейсе ссылка на исходники и версию.

## 11. Чистота публичного репозитория (чек-лист)
1. Репозиторий начинается с чистой истории, без секретов, IP, доменов и ключей реальных установок ни в одном коммите.
2. Pre-commit и CI: gitleaks, проверка запрещённых строк (реальные домены, IP и имена установок); сам список запрещённых строк в репозиторий не кладётся, он хранится в настройках CI как секрет.
3. Тестовые данные только синтетические или анонимизированные.
4. `.env.example` (планируется) без реальных значений; примеры используют `example.com` и документационные адреса (203.0.113.x).
5. **Публичный репозиторий один (`swellwright`)**; отдельного репозитория реестра нет. Данные реальных установок в репозиторий не попадают (раздел 8).
6. Данные экземпляра живут в Swellwright (раздел 8), а не в репозитории.
