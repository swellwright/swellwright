# 09. Docker, hosting, operations

> English translation of the [Russian design document](../../ru/design/09-ops-docker.md).

## 1. Containers (like the panel: application, PostgreSQL, Redis-compatible store)
| Service | Image | Role | Network |
|---|---|---|---|
| `swellwright` | own image (multi-stage, non-root; API and console in one) | api + UI serving | internal + published on 127.0.0.1 only, behind nginx |
| `migrate` | same image, another command | applies the database migrations once, before the server starts | internal only |
| `swellwright-worker` | same image, different command (planned; the first engine slice runs in the API process, ADR 0048) | workflow execution, SSH, probes | internal + outbound by allowlist |
| `postgres` | `postgres:17` (pinned by digest) | database | internal only |
| `valkey` | `valkey/valkey:8` (pinned by digest) | readiness check; rate limits and wake-ups later (runs and locks are in PostgreSQL, ADR 0048) | internal only |
| `swellwright-probe` | own, separate image (planned, optional) | probe agent on observer machines | outbound HTTPS to the api only |

The image is built by the `Dockerfile` at the repository root with `pnpm install --frozen-lockfile --ignore-scripts`; the base image, pnpm and the Prisma engine are pinned and checked (ADR 0019). Release images are tagged with the version (`swellwright:1.0.0`), never `latest`; CI builds and publishes them (section 10). Until then the image is built from a checkout by the compose file.

## 2. `docker-compose.yml`
The file is `deploy/compose/docker-compose.yml`; the secrets go into a `.env` next to it (`.env.example` explains each), then `docker compose up -d --build` (ADR 0019). What it sets:
- `migrate` runs `prisma migrate deploy` and exits; `swellwright` starts after it has finished successfully and after Postgres and Valkey are healthy.
- `swellwright`: non-root user, `read_only: true` with a memory `/tmp`, `cap_drop: [ALL]`, `no-new-privileges`, `init`, published on `127.0.0.1:3100` (`SW_LISTEN`). Compose requires a nonempty `SW_TRUSTED_PROXIES`. Use the reverse proxy's address as seen by the API or an exclusive proxy CIDR, not the private ranges or the plugin network. `false` is for direct access: behind a proxy it makes clients share the peer address for audits, limits and token allowlists. A forwarded header from an untrusted private peer produces a one-time warning and is still ignored.
- Networks: `backend` is `internal: true` (Postgres, Valkey, `migrate`, the server); `frontend` carries the published port and the outbound traffic of the server.
- Required secrets (`POSTGRES_PASSWORD`, `SW_AUTH_KEY`) are checked by Compose; a missing one stops the start with a message.
- Planned and not in the file yet: the worker, Docker secrets for the database password, resource limits.

Outbound traffic is restricted by the host firewall (allowed: inventory servers, the panel, DNS APIs, GitHub, Telegram), not by Docker alone.

## 3. Environment variables (main ones)
`SW_PUBLIC_URL`, `SW_VERSION`, `SW_DATABASE_URL`, `SW_VALKEY_URL`, `SW_AUTH_KEY` (base64 of 32 random bytes; seals the TOTP secrets, not a vault key, ADR 0014; required in production), `SW_SETUP_TOKEN` (optional fixed first-run token), `SW_COOKIE_SECURE`, `SW_ALLOWED_ORIGINS`, `SW_STEP_UP_MINUTES` (how long a session stays elevated after the second factor, 5 by default, 1 to 30; ADR 0017), `SW_VAULT_KDF_MEMORY_MIB` and `SW_VAULT_KDF_PASSES` (the Argon2id cost of a new vault passphrase, 256 MiB and 3 by default; ADR 0018), `SW_LOG_LEVEL`, `SW_EGRESS_ALLOWLIST` (a hint for the policy), `SW_UNSEAL_MODE` (`manual` by default, `file`, `systemd-creds`), `SW_METRICS_BASIC_AUTH` (for Prometheus), `SW_RETENTION_*`. Also: `SW_WEB_DIR` (the directory with the built console; the API serves it at `/`, set to `/app/web` in the image, and refuses to start if it has no `index.html`), `SW_PLUGINS_OFFICIAL_DIR` and `SW_PLUGINS_LOCAL_DIR` (directories whose sub-directories are plugins, trust `official` and `local`; neither set, no plugins; ADR 0027), `SW_PLUGINS_COMMUNITY_DIR` (plugins by others, trust `community`; sidecars and drivers only), `SW_PLUGIN_CORE_URL` (how a sidecar reaches Swellwright, `http://swellwright:3000`), `SW_PLUGIN_SIDECAR_URL` (how the core reaches a sidecar, `http://plugin-{id}:{port}`), `SW_PLUGIN_NETWORK` (the compose network of the sidecars, `plugins`) and `SW_PLUGIN_CORE_SERVICE` (the compose service of Swellwright, `swellwright`; ADR 0031), `SW_PLUGIN_MEMORY_MIB` (heap limit of a plugin process, 128 by default), `SW_PLUGIN_CALL_TIMEOUT_SECONDS` (10) and `SW_PLUGIN_IDLE_MINUTES` (10; ADR 0028), `SW_SSH_ALLOW_LOOPBACK` (false), `SW_SSH_ALLOW_PRIVATE` (true) and `SW_SSH_ALLOW_HOSTNAMES` (true) (which addresses Swellwright may connect to; link-local and cloud metadata addresses never), `SW_SSH_CONNECT_TIMEOUT_SECONDS` (15), `SW_SSH_COMMAND_TIMEOUT_SECONDS` (60) and `SW_SSH_RATE_LIMIT_PER_MINUTE` (20) (ADR 0037), `SW_COMMAND_CONCURRENCY` (5 servers of one run at a time), `SW_COMMAND_OUTPUT_LIMIT_KIB` (1024 per stream and server), `SW_COMMAND_POLL_MS` (1000), `SW_COMMAND_LOST_AFTER_MINUTES` (30) and `SW_COMMAND_RATE_LIMIT_PER_MINUTE` (10 runs per user) (ADR 0038), `SW_ENGINE_ENABLED` (true; false starts no run loop in this process), `SW_ENGINE_CONCURRENCY` (1 to 4 runs at once), `SW_ENGINE_POLL_MS` (1000), `SW_ENGINE_RENEW_MS` (10000; the lease lasts three times as long), `SW_ENGINE_WAIT_BACKOFF_MS` (15000; a run that waits for a lock or a sealed vault is tried again after it, twice as long after each sealed-vault wait up to eight times) and `SW_ENGINE_STOP_TIMEOUT_MS` (8000; how long closing waits for a step that does not give up) (ADR 0048) and `SW_TRUSTED_PROXIES` (which proxies may say who the client is through `X-Forwarded-For`: a number of hops, or addresses, CIDR ranges and `loopback`, `linklocal`, `uniquelocal`; not set, nobody is trusted; a typo is refused at start; ADR 0019). The update check: `SW_UPDATE_CHECK` (`on` by default, `off` switches it off), `SW_REPOSITORY` (`owner/name` of the GitHub repository, `swellwright/swellwright` by default, a fork sets its own) and `SW_UPDATE_API_BASE` (the GitHub API, `https://api.github.com`; for tests only, https or http on the same machine). What the image build recorded is passed as build arguments and read from `SW_BUILD_TIME`, `SW_BUILD_NUMBER`, `SW_GIT_BRANCH` and `SW_GIT_COMMIT` (all optional; the console's "Build info" shows what is there). **The vault master password is never passed through the environment.**

## 4. Reverse proxy (nginx, modeled on the panel)
- Domain `sw.<base>`, certificate (for example a wildcard for the base domain), `proxy_pass http://127.0.0.1:3100`. The API serves the console itself, so there is one upstream; the proxy keeps TLS and access restriction.
- Headers: `X-Forwarded-For`, `X-Forwarded-Proto: https`, no sub-path.
- WebSocket: `Upgrade`/`Connection`, `proxy_read_timeout` of at least 1 hour for the terminal.
- Access restriction: an address allowlist (trusted networks, VPN), optional mTLS; rate limiting; a separate `location` for `/ws`.
- `/metrics` and `/docs` are closed to external addresses.
- The console has real URLs (for example `/dashboard/security/users`). The proxy passes every path to the API, and the API answers a GET or HEAD of a path that is not under `/api`, has no file extension in its last segment and comes from a client that accepts HTML with the same `index.html` (never cached, with the console's content security policy), so a deep link or a reload opens the page. Unknown `/api/...` paths stay a JSON 404, and so does a missing file (`/assets/missing.js`, `/favicon.svg`).

## 5. Hosting (on the same host as the panel or on a separate one)
A separate server is recommended. Hosting on the panel host is acceptable with isolation measures: a dedicated system user without sudo; a separate docker network and **its own** Postgres and Valkey (not the panel's); no access to `docker.sock` or to the panel's volumes and network; limits (`cpus`, `memory`, `pids`) and `read_only`; a firewall that restricts outbound connections of the Swellwright containers; a separate vhost and separate backups; Swellwright does not read the panel database (API only); the panel host is in the Swellwright inventory as an ordinary server with a restricted user.
Resources: measure the spare CPU and RAM before launch; the baseline need of Swellwright is 2 vCPU and 2 GB RAM (it grows with probes and logs).
Residual risk on a shared host: the kernel and the host are shared, so a host compromise affects both systems.

## 6. First run
`cp .env.example .env`, fill in the three secrets, `docker compose up -d --build` (`deploy/compose`) → open the console and enter the setup token the server printed to its log → create the instance owner (password, TOTP, recovery codes) → create and **unseal** the vault (password + an optional key file) → connect the panel (P01) → import the fleet → adopt the nodes (N01) → set up notifications and schedules.

## 7. Operations
- **Swellwright updates:** new image version → the `migrate` service runs on `docker compose up` before the server → `ready` check → rollback: the previous image plus a database restore from the pre-migration backup (an automatic backup is taken before each update).
- **Backups:** daily `pg_dump` (encrypted in CMS format: the public key stays on the server, the private key is kept off the server by the administrator), export of the vault metadata (ciphertext), off-server copies (external storage), a monthly restore check into a disposable Postgres.
- **Monitoring:** `/health`, `/ready`, `/metrics` (Basic Auth), alerts on lock age, queue, token and certificate expiry, database size.
- **Logs:** JSON, Docker rotation (`max-size`, `max-file`), retention by policy, no secrets.
- **Update check:** for the version button and the project link of the console, the server asks `api.github.com` for the latest release and the star count of the repository (`GET /repos/<repository>/releases/latest` and `GET /repos/<repository>`), at most once a day (once an hour after a failure), keeps the answer in memory and does not call GitHub at start. It is a plain GET with `Accept`, `User-Agent: swellwright/<version>` and `X-GitHub-Api-Version`; it carries nothing that identifies the installation, a user or a browser, and the browser itself never calls GitHub. The console reads the result from `GET /api/v1/updates` (any signed-in user; nothing is written to the audit log). `SW_UPDATE_CHECK=off` switches it off: no request is ever sent and the console shows no update information. GitHub has to be on the egress allowlist for it to work.
- **Clock:** NTP is mandatory (SSH certificates and webhook signatures depend on time).

## 8. Disaster recovery (runbooks)
| Situation | Actions |
|---|---|
| Vault password lost | unseal with the recovery key shown at setup (the console offers it under the passphrase field); shares of the key (Shamir) come later; without the key the vault is lost: reissue all secrets and reconnect the panel and the servers (the nodes stay alive, access through the emergency key) |
| Nobody can sign in (the owner lost the password and the authenticator) | on the Swellwright host, with the environment of the server: `docker compose exec swellwright node apps/api/dist/admin.js reset-credentials <login name>` deletes the credentials of that account, ends its sessions and prints a one-time invitation; open the console with it, choose a password, set up the authenticator again. `... admin.js users` lists the accounts. Recorded in the audit chain as `user.credentials.reset` with `via: cli` (ADR 0016) |
| Swellwright server lost | bring up a new machine, restore the database from a backup, unseal the vault, recreate the agent tokens, verify access |
| Database corrupted | restore from the latest backup, resync the panel and the servers, mark the runs as "undetermined state" and reconcile them against snapshots |
| Swellwright compromised | revoke the panel tokens, rotate the SSH CA and keys, rotate the DNS secrets, audit, reissue (wizard N28) |
| Panel unavailable | runs that depend on the panel are paused; work with servers over SSH continues; "panel later" scenarios |

## 9. Host hardening checklist
OS updates, SSH by certificate, UFW (allow 22 from trusted addresses, 443 from allowed ones), fail2ban, swap disabled or encrypted, disk encryption, a dedicated user, integrity monitoring, database and queue ports closed, no `docker.sock` in containers, regular image rebuilds.

## 10. Releasing the project on GitHub
Image builds in GitHub Actions (multi-arch if needed), publishing to GHCR, version tags, digest pinning, SBOM (CycloneDX), cosign signatures, checks (linters, types, tests, gitleaks, Trivy, licenses, `oasdiff`, a check that no instance data is present), release notes from the CHANGELOG, OpenAPI published as an artifact. A local build is also acceptable for installation in your own infrastructure. Details are in `13-plugins-and-opensource.md`.

## 11. Node artifacts
What Swellwright runs on a node is a file from `artifacts/<name>/` of the repository: `install.sh`, `manifest.json` (name, semantic version, SHA-256, size, the steps with `readOnly`, `needsRoot`, `inFull`, `params`, `requires`, and the parameters with pattern or values, default, `secret`), its README and its tests (ADR 0036). The manifest is generated from the script by `scripts/artifact-manifest.mjs` and checked in CI. The hash is verified before the upload (against the bytes Swellwright holds) and after it (`sha256sum` on the node, against the manifest); nothing runs on a mismatch. A released version is never edited. The installer is `sh install.sh [action]` with parameters from the environment or `--env-file`, `--non-interactive` without a terminal, and a journal `/var/log/swellwright-node-installer.log`; `preflight` and `verify` change nothing and exit 2 when a check fails. It can be run by hand from the README of the artifact, which is also how it is tested before the server can ship it.

**Built in Phase 2 (ADR 0039):** the API serves the catalogue (`GET /artifacts`, `GET /artifacts/{name}`, `.../versions/{version}`, and the file itself with `Content-Disposition` and `X-Content-SHA256`) from `artifacts/` of the image (`SW_ARTIFACTS_DIR` moves it) and checks every file against its manifest (strict schema, plain file inside its directory, size, SHA-256) when the server starts and again whenever it is used: a file that is not what its manifest says is `broken` (listed with the reason, noted in the audit chain, never served or sent) and cannot stop the server from starting. `node apps/api/dist/admin.js artifacts` does the same check from outside and the CI image job runs it. `POST /servers/{id}/artifacts` hashes the file, uploads it over SFTP to a temporary name, has the server hash it (`sha256sum`), renames it into place only on a match, sets the mode (0755 for a script, 0644 for a data file) and has the server hash it once more; a failure leaves nothing at the place of the file, and a push that was cut off is swept by the next one. The default place is `~/.swellwright/artifacts/<name>/<version>/<file>` of the login (private to it); `destination: system` is `/var/lib/swellwright/artifacts/...` owned by root and written through the sudo path of the SSH layer. `POST /servers/{id}/artifacts/{name}/verify` hashes the copies on the server again (`ok`, `differs`, `missing`), `DELETE` removes one, `GET` lists what was pushed. One operation per server at a time, a per-user rate limit (`SW_ARTIFACT_RATE_LIMIT_PER_MINUTE`), a push holds the file in memory (`SW_ARTIFACT_MAX_BYTES`, 64 MiB), audit actions `artifact.pushed`, `artifact.verified`, `artifact.removed`, `artifact.broken`. The console has the Artifacts page (Operations) and an Artifacts card in the server drawer. Running an artifact is a later slice.

## 12. Sidecar plugins
A `community` sidecar ships as an OCI image with a manifest. Swellwright generates a Compose fragment for `plugin-<id>`, with resource limits, reduced privileges, and an internal network named `<SW_PLUGIN_NETWORK>-<id>` shared only with the core. Swellwright does not use `docker.sock`; the administrator applies the fragment. The sidecar uses the authenticated HTTP gateway for approved outbound requests, bound secrets, and its own storage. Regenerate and reapply older fragments to move sidecars off the shared network. See [ADR 0050](../../adr/0050-plugin-boundaries-and-vault-key-generations.md).

Enable the plugin before exporting the fragment. An upgrade from the earlier gateway token format or reapproval invalidates the old token. Export and apply a fresh fragment; do not carry the old token forward.
