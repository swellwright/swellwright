# 05. Security, secrets and permissions

> English translation of the [Russian design document](../../ru/design/05-security.md).

Swellwright holds the keys to the whole Remnawave node fleet: it is the most valuable target. The goal of this section: compromise of any single part (a node, the panel, a container, a dependency, a browser) does not reveal everything else.

## 1. Threat model
| Asset | Threat | Main controls |
|---|---|---|
| Vault | theft of the database, a dump or a backup | application-level encryption (AES-256-GCM, wrapped keys), master key only in memory, offline brute force made harder (Argon2id) |
| SSH access to nodes | key leak, password reuse | short-lived SSH certificates, per-server keys, host key pinning, source restriction, break-glass key outside the system |
| Panel tokens | leak, excess privileges | scopes, expiry, separate tokens (write, read, probes), revocation, usage audit |
| DNS credentials | domain takeover | separate applications and accounts with minimal permissions, zone-restricted tokens, confirmation for bulk edits |
| Web UI | session hijacking, XSS, CSRF | TOTP/passkey, httpOnly cookies, SameSite=strict, CSRF token, strict CSP, step-up authentication |
| Node output | malicious control sequences, XSS | output sanitization, rendered as text, terminal only in xterm |
| Dependencies | package substitution | frozen lockfiles, `--ignore-scripts`, SBOM, scanning, manual review of updates |
| Swellwright server | host compromise | dedicated VM, minimal images, read-only FS, non-root, egress policy |
| Instance owner and operators | a mistaken action | plan, approval, rollback, windows, guardrail policies |
| Plugins | third-party code with access to secrets | trust levels, process isolation, permissions in the manifest, network proxy, signature, audit; `community` only in a container (`13`) |

## 2. Vault
- **Key hierarchy:** the instance owner's passphrase -> Argon2id -> KEK; the KEK wraps the data keys (DEK); each secret is encrypted with its own DEK (AES-256-GCM, AAD = secret id + version + context). Argon2id parameters are tuned to the machine (about 256 MiB, t=3).
- **Sealed and unsealed:** after start the service is sealed; running workflows and showing secrets are impossible until the passphrase is entered (or a key file from another machine as a second factor). The exception, "auto-unseal" (systemd-creds/TPM), is allowed only by explicit configuration and is marked as less secure.
- **In memory:** decrypted values live only in the worker process for the duration of a step and are zeroed; they are not written to Redis, logs, events, dumps or step environment variables (only to mode-600 files on the node, which are erased afterward).
- **Reveal:** values are write-only in the UI; viewing requires the `vault:reveal` permission and step-up authentication and is recorded in the audit log.
- **Rotation:** KEK (re-wrapping without re-encrypting the data), DEK, secrets on a schedule; wizards for the panel token, DNS and SSH keys.
- **Recovery:** a recovery kit: Shamir 3-of-5 or a printed key; losing the passphrase and the kit means losing the vault (described in `09-ops-docker.md`).
- **Redaction:** every secret value is registered in the process's "redaction list"; output, errors and events are checked before being written (a write that contains a secret is rejected).
- **Built in Phase 1 (ADR 0018):** a random key-encryption key (KEK) stored wrapped twice, under a key derived from the passphrase with Argon2id (256 MiB, 3 passes by default, `SW_VAULT_KDF_MEMORY_MIB` and `SW_VAULT_KDF_PASSES`; stored with the vault so it can be raised) and under a random 256-bit recovery key that is shown once and never stored (this refines the design: the passphrase does not produce the KEK, so it can change without re-encrypting); a data key per secret version, AES-256-GCM, bound to the secret id, version and type so a blob moved elsewhere fails to open; the process starts sealed and unsealing (passphrase or recovery key) keeps the KEK in memory only, sealing wipes it; failed unsealing is audited and ten failed tries in fifteen minutes block every further one for everyone; reveal needs `vault:reveal` and a step-up and is recorded before the value leaves; values are otherwise write-only and a replaced value is not kept; names, types and dates are metadata and list while sealed; a sealed vault answers 423 `vault_sealed`. **Rotation (ADR 0024):** change the passphrase (the KEK is wrapped again under a new salt and the current cost; nothing is re-encrypted; works while sealed), issue a new recovery key (the old one dies), replace the KEK (every data key is wrapped under the new key, the version moves forward, a new recovery key is issued; all or nothing) and encrypt every secret under a fresh data key; each needs `vault:manage`, a step-up, and for the first three the passphrase again; they run through one in-process queue with the key, so a rotation never runs in the middle of a write; only failed passphrase tries count towards the limit; the status shows when each part was last rotated. Not yet: Shamir shares of the recovery key, a key file as a second factor, scheduled rotation of secrets, the redaction set, usage records, export.
- **Expiry (ADR 0042):** a secret whose `expiresAt` is now or past is expired, and the vault refuses to give it to anything that uses it (a server login, a plugin, a panel token, a run): 409 `secret_expired` naming the secret, after the sealed-vault answer and before anything is decrypted or sent; one place decides. A run that has started is followed to its end (the expiry is checked when a use begins). A person may still reveal an expired secret (it says `expired: true`), renew or replace it; nothing is deleted. A refused use is recorded once per secret per ten minutes (`secret.use_refused`).
- **Secrets for a run (ADR 0042):** a run may be handed vault secrets of the kinds a script reads (not `ssh_key`, not `ssh_ca`) as files: `<step dir>/secrets/NAME` (0700 directory, 0600 file, written from the standard input of the launch), `NAME_FILE` for the script, removed when the script ends by any route (the wrapper, cancel, the read of a lost step, removal); never in a command line, the SSH environment, the script text, the stored run or a log. It is a reveal in effect (a script can print it): it needs `servers:exec` and `vault:reveal` and a fresh step-up, never an API token, and is audited as `secret.used_in_run` in the transaction of the run. The stored output is scrubbed of the literal value (`[secret NAME]`, across reads), best effort: a script that transforms the value is not caught. A secret that a running run was handed cannot be replaced or deleted.

**Vault rotation across API instances ([ADR 0050](../../adr/0050-plugin-boundaries-and-vault-key-generations.md)).** Equivalent NFKC passphrases do not count as a change. An instance cannot write a secret under an old KEK; when it detects a replacement, including on a status check, it wipes its key and seals itself. If a KEK rotation cannot be confirmed, the response is 503 and the process seals itself. If a crash or a lost response hid the new recovery key, unlock with the current passphrase and issue a replacement recovery key. Do not assume the previous recovery key still works.

## 3. Sign-in and authorization
- Password (Argon2id), TOTP required, WebAuthn (passkey), OIDC optional; lockout on brute force, IP restrictions.
- Sessions: httpOnly, Secure, SameSite=strict; short lifetime, extended on activity; a new session is issued when privileges are elevated.
- **Built in Phase 1 (ADR 0014):** Argon2id hashes (64 MiB, 3 passes) in PHC format; TOTP (RFC 6238: SHA-1, 6 digits, 30 s, one step of drift, every code works once) whose secret is sealed with AES-256-GCM under `SW_AUTH_KEY`, independent of the vault so sign-in works while the vault is sealed; ten single-use recovery codes, stored as hashes; sign-in in two steps, where a password-only session can only finish the sign-in and is replaced, never upgraded, when it does; a lockout of 15 minutes after 5 consecutive failures; session tokens kept as hashes, with an idle and an absolute expiry; first-run setup guarded by a one-time token printed to the server log; CSRF defence by `SameSite=Strict` plus an `Origin` check. WebAuthn, OIDC, IP restrictions and step-up come later.
- **Step-up authentication** for: the terminal, secret reveal, token creation, approval of high-risk runs, dangerous panel operations (`DELETE`, bulk, `restart-all`), policy changes.
- **Built in Phase 1 (ADR 0017), step-up:** `sessions.elevated_until`; signing in elevates the session (the second factor was just proved) and `POST /auth/step-up` renews it with an authenticator code or a recovery code (single use; a code that was already used cannot be replayed; wrong codes count towards the lockout); the window is five minutes (`SW_STEP_UP_MINUTES`, 1 to 30) and never outlives the session. A route declares `stepUp: true` in the registry (OpenAPI `x-sw-step-up`); a guard after the permission guard answers 403 with the error code `step_up_required`, which the console answers with a code dialog and a retry. `users:write`, `vault:manage`, `vault:reveal` and `terminal:use` always need it (a test fails the build for a route that holds one without declaring it). Today it covers creating and changing users, resetting credentials and changing your own password. The elevation belongs to one session; the cookie is not replaced when it is granted. Recorded as `auth.step_up.succeeded` and `auth.step_up.failed`. Not yet: WebAuthn as the proof, a per-action prompt for one high-risk operation, binding to an address or device.
- **Roles:** `owner`, `operator` (runs without secrets and without the terminal), `observer` (read-only), `terminal` (the terminal permission), `auditor`. Permissions are fine-grained (`servers:read`, `runs:execute:deploy`, `panel:write`, `vault:reveal`, `terminal:use`); roles are sets of them.
- **Built in Phase 1 (ADR 0015):** one closed catalogue of `resource:action` permissions in `packages/contracts`, read by the server, the console and the OpenAPI document (`x-sw-permission`); the five roles as fixed sets (the owner holds every permission, computed; writing a thing implies reading it, and a test checks that); every signed-in route names its permission in the route registry, and a test fails the build for one that does not; a guard answers 403 and records the refusal; the role is read from the user row on each request, so a change applies at once; `GET /auth/me` carries the permissions for the console to show or hide pages (the server checks again). Custom roles come with user management. Permissions of features that do not exist yet are in the catalogue so the roles stay stable.
- **Built in Phase 1 (ADR 0016), users:** an owner invites a user with a role and gets a one-time invitation (256-bit, only its hash is stored, 72 hours, one per user); the invitee chooses their own password and sets up the authenticator, so nobody else ever knows the password. Resetting credentials deletes the password, authenticator, recovery codes and sessions at once and issues a new invitation. The server command `node dist/admin.js reset-credentials <login name>` does the same from the host for the case where nobody can sign in; it trusts whoever can run it as much as the database does and leaves a record without an actor (`via: cli`). Own password change needs the current password and ends the other sessions. There is always an active owner; nobody changes their own role or status or resets their own credentials through the API; user changes are recorded in the same transaction as the change. No e-mail delivery and no self-service "forgot password".

**Plugins (ADR 0027):** `plugins:read` (every role) and `plugins:manage` (owner, step-up) join the catalogue; an approval is tied to the digest of every file of the plugin (`GET /plugins`, `POST /plugins/{id}/enable` with the digest that was shown, `.../disable`); a plugin that is gone, unusable or has other files is switched off on the next read or at start and the page shows the permission difference; `plugin.enabled` and `plugin.disabled` are recorded.

**Running plugins (ADR 0028):** an approved plugin runs in a process of its own under the Node permission model (its own directory readable, no network, no child processes, no workers, no code generation from strings, a heap limit, an environment without anything of the core's, a deadline per call) and reaches the network only through the core, to the `host:port` pairs that were approved and public addresses only. It is checked against the approval before every start and call, and stopped at once when switched off. This is not a sandbox against hostile code (a process can still signal the core); see the ADR.

**Plugin settings, secrets and storage (ADR 0029):** a plugin declares its settings in a small closed subset of JSON Schema; the administrator fills them in (`plugins:manage`, step-up) and each change is recorded by field name, never by value. A secret field holds the id of a vault secret; the plugin receives the value by asking the core (`context.secret`), which checks the stored approval, that the vault is unsealed and that the secret is of the declared type, and records `plugin.secret.used`. A plugin also has a storage of its own with size limits.

**Declarative drivers (ADR 0030):** a plugin for a REST service can be a YAML description that the core interprets: no code runs. Values come only from declared parameters, settings, bound secrets (requests only), earlier steps; what goes into a URL is encoded; the host of every URL is written out; every request is subject to the gateway and the stored approval, and a driver that calls a host the manifest does not ask for makes the plugin invalid.

**Sidecar containers (ADR 0031):** the answer to the limit of ADR 0028. A plugin by others (trust `community`) runs its code in a container the administrator starts from a generated compose fragment: an internal network with no way out, read-only, no capabilities, not root, bounded, from an image pinned by digest. It reaches the network, a secret and its storage only through a gateway that trusts only the token of the plugin as approved (HMAC over the id and the digest of its files, key from `SW_AUTH_KEY`), counts wrong tokens per address and stops answering the moment the plugin is disabled or changes. The fragment holds the token: treat it as a secret.

**User deletion and personal language (ADR 0026):** `DELETE /users/{id}` (`users:write`, step-up) removes a *disabled* account (409 while it is active or when it is your own) with its password, authenticator, recovery codes, sessions, tokens and invitation; the audit log keeps what the account did under its name and records `user.deleted`. `users.language` is empty until a person picks one (`PATCH /auth/preferences`, `null` goes back to following the browser); the console applies a saved language once after sign-in.
- **Built in Phase 1 (ADR 0022), sessions:** every user lists and ends their own other sessions (`GET /auth/sessions`, `DELETE /auth/sessions/{id}`, `POST /auth/sessions/revoke-others`); `sessions:read` lists the sessions of everyone and `sessions:revoke` (with a step-up) ends one or all of a user; the session in use is never ended by a request (409, sign out instead); each ending is recorded as `session.revoked`. The permission catalogue grew by six: `sessions:read`, `sessions:revoke`, `tokens:create`, `tokens:read`, `tokens:revoke`, `audit:export`.
- **Swellwright tokens** (CLI, integrations, probes): scopes `sw:<resource>:<action>`, expiry, IP restrictions; stored as hashes.
- **Built in Phase 1 (ADR 0023), API tokens:** `Authorization: Bearer swt_...` (256 random bits, only the SHA-256 hash stored, shown once); a token carries a subset of its owner's permissions, never one that needs a step-up, and works with what the owner's role still allows on every request; expiry 1 to 365 days, at most 20 active per user, optional address and CIDR restriction; creating needs `tokens:create` and a step-up, listing and revoking your own tokens is open to everyone, `tokens:read` and `tokens:revoke` cover other users; routes opt in with the authentication level `any` (the read routes today), browser-only routes and routes that need a step-up never accept a token; wrong tokens are rate limited per address; recorded as `token.created`, `token.revoked`, `auth.token.denied`.
- For dangerous runs, optional "dual approval" (a second approver).

## 4. SSH access to nodes (methods are configurable)
Passwords, certificates and keys are supported in any combination; nothing is imposed. The choice is made per server, per group or as a default; the order of attempts can be set.
| Method | Description | Notes |
|---|---|---|
| Password (and sudo password) | secrets in the vault | the simplest option, matches a fresh server (root); policy warns about the risk but does not block |
| Key | a separate ed25519 key per server (or a shared one), in the vault | rotation manually or by scenario N15 |
| Certificate | Swellwright certificate authority (optional): user `swellwright`, short lifetime, `principals`, `from=` | enabled on request; requires node preparation |
General rules (independent of the method): host key pinning (confirmation on first connection, alert on change; an OS reinstall is confirmed explicitly in N04); the first login to a new server is by the root password, then Swellwright access and an administrator account are created, and root is closed only after the login and sudo are verified; a safety timer on the node; the Swellwright address in fail2ban `ignoreip`; for `sudo` the password is passed through stdin; the **break-glass key outside Swellwright** remains (offline with the instance owner, off the Swellwright server); policies P-005 and P-013 remain in force.

**Built in Phase 2 (ADR 0034):** the inventory stores the access methods `password` and `key` as references to vault secrets (the kind is checked: `ssh_password`, `ssh_key`, and `ssh_password` for sudo; a secret in use cannot be deleted, and the vault names the servers that use it), and pins host keys by hand: a person enters the algorithm and the SHA-256 fingerprint they checked (`SHA256:` and 43 base64 characters, refused if it cannot be a digest); pinning it again changes nothing; revoking a key is how a reinstalled server is handled. Every change is recorded (`server.host_key.pinned`, `server.host_key.revoked`, `server.access.added`, `server.access.updated`, `server.access.removed`) in the same transaction, without a value. **Built in Phase 2 (ADR 0037):** the first-use flow of this section. A scan reads the key a server shows without sending any credential (`POST /servers/{id}/host-keys/scan`: `new`, `pinned` or `differs`); a person checks the fingerprint against another source and confirms it, and the API reads the key again and pins it only if it is exactly the confirmed one (`.../accept`, source `scan`). A key that differs from the pinned one is expected after an operating system was reinstalled and is what a man in the middle looks like, so it needs an explicit `replace`, which revokes the old keys in the same transaction. Every connection is made to a pinned key, checked before any credential is sent, and a mismatch is a distinct error with both fingerprints (`host_key_mismatch`); the alert is that error, shown where the operation was started and recorded in the audit chain. The outbound policy of section 7 is applied to the stored address before every connection (`SW_SSH_ALLOW_LOOPBACK`, `SW_SSH_ALLOW_PRIVATE`, `SW_SSH_ALLOW_HOSTNAMES`), a pooled connection does not outlive the trust it was opened under, and a person may start a limited number of SSH operations a minute (`SW_SSH_RATE_LIMIT_PER_MINUTE`). Trying an access entry (`.../access/{accessId}/verify`) and collecting facts (`.../facts/refresh`) use the stored secrets for the length of the call only and are recorded (`server.access.verified`, `server.facts.refreshed`, `server.host_key.scanned`) without a value; the permission is `servers:write` for everything that connects. A background check that finds a changed key between operations is not built.

## 5. Web terminal (N27)
- By default the terminal is available only to users with the `terminal:use` permission and step-up authentication for every session; it works **only with real SSH data that the user enters for every session**: host (from the inventory or arbitrary), user, password or private key (paste or file upload, passphrase), and, if needed, a response to the server's second factor. Swellwright **does not inject** stored secrets into the terminal: the data lives in session memory and is erased on close; it never reaches the database, logs or recordings.
- Consequence: a hijacked Swellwright session or a lost vault does not give ready-made root access through the terminal; the terminal is also suitable for servers outside the inventory.
- Additional measures: idle timeout and maximum duration, host key pinning with confirmation, broadcast input disabled by default, confirmation for pasting multi-line text, a list of active sessions and forced close.
- **Session recording is optional** (off by default, because output can contain secrets); when enabled, the recording is encrypted and masked against the list of known secrets.
- Difference: ad-hoc commands (N25) and workflows use **stored** access and go through policy and audit; the terminal is a separate interactive client.
- **Built in Phase 2 (ADR 0038):** ad-hoc commands and the script library. `servers:exec` (owner and operator) is a step-up permission, so every run, cancel and script write needs a fresh authenticator code and an API token can never hold it; reading the history and the output is `servers:read`, and **the output can contain secrets**, so who may read servers may read it (the console says so). A script is code that runs on servers, usually as root: the built-in ones are read-only files with a header and a stored hash, the administrator's own need `servers:exec` and a code to write, and a run stores an immutable snapshot of the text and its hash (the audit log holds the hash, never the text or the parameter values). Parameters are typed, checked on the server before the run is queued and delivered only as environment variables through the step layer's quoting, never inside the script text. A run that is not `read` has to be confirmed in so many words, which is recorded; until the approvals of the engine (phase 4) it is the only check. The pinned host key is required, the address policy applies, a wrong password is tried once and never again, and every server of a run is a separate target. Limits: `SW_COMMAND_CONCURRENCY`, `SW_COMMAND_OUTPUT_LIMIT_KIB`, `SW_COMMAND_POLL_MS`, `SW_COMMAND_LOST_AFTER_MINUTES`, `SW_COMMAND_RATE_LIMIT_PER_MINUTE`, at most fifty servers per run.

## 6. Web security
CSP without `unsafe-inline`, `X-Frame-Options`/`frame-ancestors`, HSTS, `Referrer-Policy`, `Permissions-Policy`; CSRF protection for cookie authentication; size limits; rate limiting per IP and per user; `Origin` check for WebSocket; file uploads with type and size validation; responses that do not disclose internal errors.

## 7. Outbound connections (SSRF)
Allowlist: inventory server hosts, the panel, DNS drivers, providers, GitHub (if enabled), Telegram. Cloud metadata addresses, loopback and internal ranges are blocked for user-supplied URLs; protection against DNS rebinding (pinning the resolved IP).
**Built in Phase 3 (ADR 0041), the panel:** the panel's address goes through the same policy as an SSH target (`SW_PANEL_ALLOW_LOOPBACK`, `SW_PANEL_ALLOW_PRIVATE`, `SW_PANEL_ALLOW_HOSTNAMES`; link-local and metadata addresses never) when it is typed, and again on every address a name resolves to at the moment the socket is opened, so a name cannot be pointed at an internal service after the check. TLS is verified (an authority of its own for one connection, `SW_PANEL_ALLOW_INSECURE_TLS` off by default); plain `http:` only for a loopback or private address and only with `SW_PANEL_ALLOW_HTTP`; no redirect leaves the panel's origin. The token lives in the vault (kind `panel_token`, restrict on delete), is read for one piece of work, sent in one header to the origin of the panel and nowhere else, and is in no response, record, error, log or cache (tests look for it in each). Everything read from the panel passes the masking of ADR 0041 (REALITY keys, short ids, passwords, client ids, credentials in URLs, PEM keys, JWTs) before it leaves the API, with a keyed fingerprint so that a rotation is visible and the value is not; a connection is checked in the background and says in the audit chain only when its state changed. **Snapshots (ADR 0043)** keep the masked form only: no unmasked value of the panel is read into a snapshot, an export or a record of the audit chain, so a snapshot (and a backup of the database that holds it) is not a secret store; each snapshot keeps the identifier of the key behind its fingerprints, and a comparison across a change of that key says it cannot tell a rotation. Reading, comparing and exporting need `panel:read`; taking and deleting are `panel:write` and session-only, and deleting needs a fresh code.

**Built in Phase 3 (ADR 0046), the API console:** the permission `panel:console` (owner, operator; implies `panel:read`) lets a session send read requests to the connected panel with the stored token; a Swellwright API token cannot (the route is a session only). The request names a catalogue operation and its parameters, never a URL or a header, and every value is checked against the type the panel's own API description gives it (a path segment holds no separator, escape, `..`, `@` or `:`; a query value no control character); the transport refuses any path that leaves the panel's origin and prefix. Only GET operations are sent; what creates something on the panel, or returns a key or a link that works as a credential, is blocked, and what changes the panel is listed and never sent. Operations about the people who use the panel (users, devices, subscriptions, requests, usage) are off unless `SW_PANEL_CONSOLE_USER_DATA=true`; then they need `vault:reveal` and a fresh second factor (checked in the handler, so the other operations do not ask for a code), and the call is recorded **before** the answer is returned. Every answer is masked before it leaves the server (the deny-list of the masked views, the access material of users, the exact token wherever it occurs; answers about people also hide names, mail, messenger ids, device ids, addresses and every UUID) and cut to `SW_PANEL_CONSOLE_MAX_BODY_KIB`; a text answer that is not one clean YAML or JSON document (malformed, a repeated key, over 64 KiB or 300 anchors and aliases), and a subscription template body of that kind, is shown fully masked as `[masked: unreadable document]`; masking is best effort and the console says so. Rate limited per user. Recorded as `panel.console.request`: the operation, the path with its placeholders, the names of the query parameters, the status, the time and how many values were masked, never a value, the body or the token; refusals are `denied` and capped like `authz.denied`. The history and the samples live in the browser only.

## 8. Audit
An immutable log with a hash chain (each record contains the hash of the previous one), export and integrity verification; it records sign-in, runs, approvals, secret reveal, the terminal, policy changes, tokens. Retention without deletion.

**Built in Phase 1 (ADR 0015):** the table `audit_events` with database triggers that refuse `UPDATE`, `DELETE` and `TRUNCATE`; numbers assigned under an advisory lock, so there are no gaps; SHA-256 over the canonical fields and the previous hash; the actor kept as an id plus the name at the time, with no foreign key, so a record outlives its user; details are a flat object of short values, never a secret, a code or text an unauthenticated caller typed; a record of a change is written strictly (the owner's creation and its record are one transaction) and a record of a refusal on a best-effort basis; records that anyone can provoke are capped (unknown accounts per address, refusals per user) because the log is never pruned. `GET /audit` reads it (permission `audit:read`), `POST /audit/verify-chain` walks it and reports the first problem and the head (`audit:verify`). The chain shows edits, removals and reordering to anyone who cannot recompute it; someone who can write to the database can rewrite every hash, so the head must be noted outside the database.

**Export and checkpoints (ADR 0025):** `GET /audit/export` (`audit:export`, with a step-up; every page is recorded) hands over pages of events with the fields their hashes cover; a file of them is verified without the server by `node dist/admin.js audit-verify <file>` (numbers, links, hashes; the first problem and its place). `POST /audit/checkpoints` (`audit:verify`, a token may do it) returns the head of the chain with an HMAC made with a key derived from `SW_AUTH_KEY`, which is not in the database; stored elsewhere, it proves later that no history was rewritten (even consistently) and no tail cut off: the check reports `not_ours`, `event_missing`, `hash_differs` or `chain_broken`, or `ok` with the number of events since. `node dist/admin.js audit-checkpoint` notes the head from the host (for a cron job). Not yet: signed export files, an external timestamp, scheduled checkpoints inside the server.

## 9. Supply chain (policy P-007)
Frozen lockfiles (`pnpm install --frozen-lockfile --ignore-scripts`), manual review of updates (no automatic PRs in production), SBOM (CycloneDX), scanning of images and dependencies (Trivy, `pnpm audit`), license checks (AGPL for code copied from the panel), base image versions pinned by digest, signed releases (optional cosign), a mandatory review checklist for third-party code before it is connected.

## 10. Privacy
No outbound telemetry; personal data of Remnawave users is masked by default (stable pseudonyms), reveal by permission; logs keep the minimum.

## 11. Swellwright backup and disaster recovery
A daily encrypted database backup (CMS: the public key on the server, the private key only with the instance owner) and a vault export; copies outside the Swellwright server (external storage); a monthly restore test. The "Swellwright lost" scenario: the fleet keeps running; access through the break-glass key and manual administration (SSH, panel API); restore from a backup. The "Swellwright compromised" scenario: revoke panel tokens, replace the SSH CA and keys, replace DNS access, audit usage, reissue secrets (wizard N28).

## 12. Permission matrix for external systems
| System | Access | Purpose | Minimal form | Rotation |
|---|---|---|---|---|
| Remnawave panel | tokens with scopes | deployment, maintenance | `core` (write on the listed resources), `readonly`, `probe`; `*` is allowed by explicit configuration | 90 days, reminder 14 days before |
| Nodes | SSH `swellwright` (certificate), sudo | installation, maintenance | certificate valid for 5-15 minutes, `from=` the Swellwright address, `principals` | automatic (short lifetime) |
| Panel server | SSH user with sudo for `docker compose` in the panel directory, read of the backup directory, write to the cert-sync directory (the path is set in settings) | cert-sync, backups, updates | no access to docker.sock, no database read | as for nodes |
| DNS RU-CENTER (plugin `dns-rucenter`) | OAuth application (ID and secret) and account login/password (the API's "password" scheme) | A records | a separate account with minimal permissions is recommended if the provider's API allows it; otherwise the permissions equal those of the account, so the plugin requests only the needed scope (`dns-master`), and the secrets are kept in the vault | per instance policy |
| Other DNS | zone token | A records | limited to specific zones and record types | 90 days |
| Server providers | API token | creation, reinstall, power | only the needed project and permissions | 90 days |
| GitHub | public read (or a read-only PAT) | releases and recommendations | no write access | as needed |
| Telegram | bot token | notifications | `sendMessage` only | on leak |
| SMTP | login | e-mail | send only | 180 days |

## 13. Decisions on previously open security questions
Auto-unseal of the vault is off by default and is enabled explicitly as a less secure mode with an audit entry, not on a host shared with the panel (ADR 0006). Dual approval of dangerous operations is part of 1.0 as an optional policy. The warning about a `*` token is shown at issuance and as a persistent banner (`00-index.md`, §6).

## 14. Plugin security
A plugin is third-party code with access to secrets: trust levels, permissions in the manifest shown when a plugin is enabled, network access only by host list, secrets issued for the duration of a call and only of the declared type, `postinstall` forbidden, signature, audit of every call, immediate disable. `builtin` and `official` run in the worker process under restrictions, **`community` only as sidecar containers** (no `docker.sock`, network policy, limits) and declarative drivers that execute no code. Approvals through Telegram are allowed only for low and medium risk. Details in `13-plugins-and-opensource.md`.
