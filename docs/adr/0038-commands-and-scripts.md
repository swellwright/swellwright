# ADR 0038: Commands and the script library: run a script or a command on several servers

Status: accepted

## Context
The inventory (ADR 0034), the SSH layer with its detached steps (ADR 0035) and servers over SSH (ADR 0037) are in place. This slice is scenario N25 of the design: run a script or a command on selected servers, see the output of each server, keep a library of scripts (the audit and diagnostics that ship with Swellwright, and the administrator's own) and a history of runs. The design says that ad-hoc commands use **stored** access and go through policy and audit, that the terminal is a separate interactive client (`05-security.md`), and that the full engine (approvals, policies, durable runs, resumable plans) arrives in phase 4 (`08-engine.md`). What is built here is a deliberately small precursor of that engine: it must be safe on its own and must not pretend to be the engine.

## Decision

### One new permission, and it needs a fresh code
`servers:exec` ("Run scripts and commands on servers, stop a run, and write the scripts of the library") is held by the owner and the operator. It is a **step-up permission** (`STEP_UP_PERMISSIONS`, ADR 0017): the routes that need it are session-only (`auth: session`), answer 403 `step_up_required` until the session has a freshly verified authenticator code, and an API token can never hold it (the token catalogue excludes step-up permissions). It implies `servers:read`. Writing a script is writing code that will run on servers, usually as root, so creating, changing and deleting scripts need `servers:exec` and the code too, not `servers:write`.

Reading is `servers:read` (and an API token may have it): the library, the history, one run with its servers, and the output. **The output of a run can contain whatever the script printed, secrets included, and whoever may read servers (observer, terminal, auditor) can read it.** The console says so on every run and the API description says so. A run stores the text that ran and the parameter values in plain text: do not put a secret in a command or in a parameter (use the vault and a script that does not print it).

### The routes
`GET/POST /scripts`, `GET/PATCH/DELETE /scripts/{id}` (a built-in script cannot be changed or deleted: 409), `POST /command-runs` (queues a run and answers at once, 201), `GET /command-runs` (newest first, filters `state`, `serverId`, paging), `GET /command-runs/{id}`, `GET /command-runs/{id}/targets/{targetId}/output?stream&offset&limit` and `POST /command-runs/{id}/cancel`. One to fifty servers per run; each becomes a target with a state of its own.

### Built-in scripts
Thirteen read-only diagnostics (system summary, disk usage, memory and load, listening ports, failed systemd units, Docker containers, firewall status, fail2ban status, effective sshd settings, pending reboot and updates, time synchronisation, recent errors, top processes) are POSIX `sh` files under `apps/api/src/commands/builtin/`, each with a header that names the script and its version and promises what a read-only script promises (writes nothing, changes no setting, starts and stops nothing, installs nothing, no network from the node, bounded output). A manifest (`builtin-scripts.ts`) adds the description, whether the script needs root and its parameters. They are made and kept current **by name at start** (idempotent: a missing one is created, one whose text, version, description, root flag or parameters differ is updated, one that is current is left alone; a script of the instance that already uses a built-in name is never overwritten, it is reported). Their SHA-256 is stored. A test fails the build when a file lacks its header or the promises, contains anything that writes, changes, installs or reaches the network (a deny-list of commands read at command position, and no redirection except to `/dev/null`), or uses an environment variable it does not declare; on Linux a second test runs every file in a real shell and checks that it exits 0 (or 3 with a message when its tool is not installed), leaves nothing in the home and temporary directories and keeps its output small.

### Runs are immutable records
A run stores a **snapshot**: the exact text that ran, its SHA-256, the script's name and version, the parameter values, the level, the time limit, who started it (the name at the time) and which level the person confirmed. Editing or deleting a script later changes nothing in the history (`script_id` is set null on delete, the name stays). The audit log holds the **SHA-256 of the text**, never the text or the values.

### Danger level and the confirmation that stands in for approvals
Every script has a level: `read`, `change` or `destructive`. A run whose level is not `read` must carry `confirmedLevel` equal to that level (otherwise 409 `confirmation_required` with `details.level`), and the console asks in a red confirmation that lists the servers. An inline command has no level Swellwright can know, so the person declares one (`change` by default, which asks for the confirmation). This is **the only check until the approvals of the engine are built** (phase 4); it is a statement of intent, not a control against a person who may run commands anyway, and the confirmation is recorded with the run and in the audit record.

### Typed parameters, delivered as data
A parameter is a string (with an optional pattern and a maximum length up to 1000), an integer (with a range), one of a list, or a boolean, with a label, a description, a default and a required flag. The values are checked **on the server before the run is queued** against the definitions (unknown names, wrong types, ranges, patterns, NUL characters are 400 `validation_failed` naming the parameter) by the same function the console uses for its form. They reach the script **only as environment variables** `SW_PARAM_<NAME>` (a boolean as `1` or `0`) through the step layer's environment file, which quotes every value (`export NAME='...'`, a quote inside is closed, escaped and reopened) and is sourced by the step's wrapper; nothing is ever put into the text of the script or into a command line. Tests send hostile values (quotes, `$(...)`, backticks, newlines, `-n`, a value that looks like an option) through the API into a real shell and check that the script prints them back exactly and that no file appears. A string without a pattern accepts any text up to its length; a pattern (JavaScript syntax, matched against the whole value, 200 characters at most) is the author's tool for tighter rules and runs on short input only.

Script parameter patterns use a bounded subset of JavaScript syntax: literals, character classes and supported Unicode properties, groups, alternation and repetition. Lookaround, back references, word boundaries and inline flags are not supported. The same bounded Thompson automaton checks the entire value on the server and in the browser; the native regex engine does not compile user-written patterns. An unchanged legacy pattern and default can be retained for editing, but a new or changed pattern must meet the dialect and work limits, and saving a new default requires a successful match.

### Execution: a small runner on detached steps
Each target is started as a **detached step** (ADR 0035) whose id is derived from the target's id (`sw-<uuid>`), so starting it twice attaches instead of running twice. The script runs under `setsid` on the server, survives the SSH connection and a restart of the API, and its output goes to files that are read **by byte offset**. The runner (`CommandRunner`) runs in the API process and keeps **everything it needs in the database**:

- **Polling, not a held connection.** One poll is one short use of a pooled connection: read the status, read what is new from the stored offsets, store it. A dropped connection is just a poll that failed and the next one reconnects and continues from the stored offset, so nothing is lost and nothing repeated. The poll slows down (up to four times the base interval, `SW_COMMAND_POLL_MS`) while nothing new arrives.
- **Output is stored as chunks** (`command_output_chunks`, keyed by target, stream and start offset, so a chunk is stored once even if a restart overlaps) with the last 16 KiB of each stream kept on the target row for the run view; the bytes are kept as bytes and shown as text with invalid sequences and NUL as U+FFFD. Pages by byte offset never start or end inside a UTF-8 character. **The limit is `SW_COMMAND_OUTPUT_LIMIT_KIB` per stream and server (1024 by default)**; past it the target says `truncated` with the kept and total sizes, and the **step directory is left on the server** (the only complete copy; it is removed otherwise, after the output is stored). Nothing removes it automatically yet.
- **Concurrency**: at most `SW_COMMAND_CONCURRENCY` (5) servers of one run at a time, a hard cap of 50 servers per run, and `SW_COMMAND_RATE_LIMIT_PER_MINUTE` (10) runs per user a minute. Servers that run already are followed first.
- **Restart**: at start the runner takes up every run that is `pending` or `running`. After a restart the **vault is sealed**, so a poll answers 423: the target stays `running` and says `waiting: vault_sealed` until someone unseals the vault, and then goes on, with the script untouched meanwhile. A target that cannot be reached for `SW_COMMAND_LOST_AFTER_MINUTES` (30) is given up as `lost` (`unreachable`; the script may have finished or may still run). A target whose step directory is gone is `lost` (`step_lost`). A shutdown stops following and waits for the polls in flight; what runs on the servers keeps running.
- **Every server is its own target.** A failure of one is never a failure of another. The pinned host key is required and the address policy of ADR 0037 is applied before every connection (a server without a pinned key or an access entry is **skipped** when the run is made, with the reason); a host key that is not the pinned one ends that target before a credential is sent; the first contact tries the access entries by priority, **a wrong password is tried once per entry and never again** (the working entry is remembered on the target, so a poll never hammers a server and fail2ban stays out of it); a refused login, a revoked key, a deleted server and an unusable secret end the target with a code; a connection that cannot be made at the start is retried once and then fails the target (`ssh_connect_failed`), a running script's server is waited for.
- **Time limit** (`timeoutSeconds`, 300 by default, at most 3600) per server from the moment it started: past it the script gets TERM, then KILL (the step layer's `cancelStep`), and the target is `failed` with `timeout`.
- **Cancel** is atomic with respect to the targets that have not started (flag and state change in one transaction, one audit record, asking twice or at once is harmless and answers the same run, a run that has ended is 409); the runner stops the targets that run within a poll. The exit code 143 or 137 of a stopped script is read as `cancelled` only when a cancel was requested.
- **State transitions are one conditional update each** (`pending` to `running`, `running` to an end state, the run's close from `pending`/`running`), so two things that happen at once cannot both win, and the run's `command.run.finished` record is written in the same transaction as the close and only once. A run is `succeeded` (every server succeeded), `failed` (none did), `partial`, or `cancelled`.

### Audit
Six new actions, strict (in the same transaction as what they record) and without secrets: `script.created`, `script.updated` (which fields changed, the version, the new hash), `script.deleted`, `command.run.started` (mode, level, number of servers, how many skipped, sudo, confirmed, time limit, the SHA-256 of the text, the script's name and version), `command.run.finished` (state, counts, duration, who started it; it has no actor, the runner closes it) and `command.run.cancelled` (who, how many servers ran, how many were cancelled before they started). A refused request (no permission, no step-up, 409 confirmation) is recorded by the guards as for any route and makes no run.

### Configuration
`SW_COMMAND_CONCURRENCY` (5), `SW_COMMAND_OUTPUT_LIMIT_KIB` (1024), `SW_COMMAND_POLL_MS` (1000), `SW_COMMAND_LOST_AFTER_MINUTES` (30), `SW_COMMAND_RATE_LIMIT_PER_MINUTE` (10).

### Console
The servers table gains row selection (`selectedRecords`, a checkbox column, as the panel's Hosts table) when the person may run commands, and the panel's bar for selected rows (an `Affix` with the count, select all, clear, and the action **Run script**). The run dialog chooses a script (a select with description and level badge, built-in and own scripts grouped) or a command (an editor), fills the typed parameters from a form generated from the definitions, takes the time limit and, for a level other than `read`, asks for the red confirmation; then the session is elevated if needed (the existing step-up dialog). **Operations > Scripts** is the library as the panel's cards (a filter bar, the level and "runs as root" badges, a menu, a drawer that edits a script with a parameter builder and the code editor); **Operations > Runs** is the history as the panel's table in a card with metric cards, a drawer per run with the immutable text, the parameters and an accordion of the servers (state, exit status, errors, the live output of both streams refreshed every 1.5 s while the run goes, "show all" for what was cut from the view, the truncation notice, cancel). Everything is in English and Russian; built-in script names and descriptions are English (they come from the API).

### The code editor and the content security policy
The panel's code editor is Monaco through `@monaco-editor/react`; the console uses the same two packages at the panel's version (`monaco-editor` 0.56.0 and `@monaco-editor/react` 4.7.0, exact pins, more than three days old, integrity hashes checked against the registry, tarballs read; transitive `@monaco-editor/loader` 1.7.0 and `state-local` 1.0.7). **`@monaco-editor/react` fetches Monaco from a CDN by default; the console does not**: `monaco-setup.ts` bundles Monaco with Vite and calls `loader.config({ monaco })` (the loader's only network code, the script injection of `${paths.vs}/loader.js`, is never reached), registers the editor worker as a `?worker` file of this origin, the shell syntax only (no JSON or YAML service) and the panel's GitHub dark theme. The editor and Monaco are one lazily loaded chunk (about 3.8 MB, 1 MB compressed), so the main bundle does not grow and the chunk is fetched only when an editor is shown. **The content security policy needed no change**: `default-src 'self'` covers the worker (`worker-src` falls back to `script-src`), `font-src 'self'` the icon font and `style-src 'unsafe-inline'` Monaco's styles; the page was checked in a browser against the API's own policy and no violation was reported. `monaco-editor` 0.56.0 depends on `dompurify` 3.4.8 exactly, which has eight advisories; `pnpm-workspace.yaml` overrides it to the newest 3.4.18 (a patch release of the same minor; drop the override when a Monaco that depends on a fixed version is used). `pnpm audit` is clean; the packages are listed in `THIRD_PARTY_NOTICES.md`.

### Tests
Besides the unit tests of the contract (parameters, requests), of the built-in scripts and of the output paging: API integration tests against an in-process SSH server that **emulates the step commands from memory** (`step-host.ts`: the runner's offsets, reconnects, cancel, timeout, restart and the output limit are tested on any machine, with programs written in TypeScript) cover three servers with their own output, one failing to log in while the others succeed (and the wrong password tried once), a wrong pinned key (the server sees no authentication attempt at all), servers skipped, a cut connection (cuttable proxy) that resumes by offset, the vault sealed and opened again, a vanished step, a time limit, a launch that fails, a server that is deleted, cancel (running, not started, twice at once, while the launch is on its way, a run that has ended), the concurrency limit, the output cap, hostile parameters, the confirmation, the history after an edit and a delete, paging inside multi-byte characters, a restart of the API in the middle of a run (the application is created twice on the same database), the whole permission matrix (observer and auditor read, operator needs a fresh code, unauthenticated, tokens cannot hold the permission or call the routes), the audit records and that no secret or command text reaches an answer or the log. A second suite runs the same stack against a **real POSIX shell** (the SSH layer's real step scripts under `setsid`, a stand-in `sudo`): three servers, exit status, hostile values written back verbatim with no file created, sudo, a script that writes over time, a cut connection, cancel and time limit (process group), the output limit, a restart, and every built-in script; it is skipped where there is no `setsid` (CI runs it on Linux).

## Consequences
- Several servers can be examined and changed from the console and the API with the output of each in front of the person, after a code and (for a change) a confirmation; every run is recorded with the exact text, and the audit log has its hash.
- The people who may read servers may read the output of every run: the permission model treats the output like facts, and the console warns that it can hold secrets.
- Until phase 4 there are no approvals, no policies, no resumable plan, no scheduling, and no retention: runs and their output are kept without a time limit (a retention policy with the engine's journal), and a step directory left behind by a truncated output stays on its server.
- The runner lives in the API process: two API processes against one database would both follow the same targets (the offsets and conditional updates keep the data right, but it is not a supported setup). A restart needs the vault to be unsealed before the runs continue (automatic unseal is not built).
- The execution layer asks the server for one `sh -c` per poll (a few per second per running target): at fifty servers that is a modest load; a streaming channel would be lighter and is not built.
- Artifact pushes (ADR 0039) are `servers:write` at the time of this ADR; they may be tightened to `servers:exec` afterwards, since both put files on servers that something may later run.

## Not built here
Approvals, policies and the engine's durable plans (phase 4); schedules; broadcast to a group by tags and conditions; an interactive terminal (a separate client); recording of runs; retention and removal of old runs and of the step directories of truncated outputs; automatic unseal after a restart; a streaming channel for the output; editing a script as a file with a history of its versions; an import of scripts from files; a per-server override of parameters.
