# ADR 0037: Servers over SSH: reading and pinning host keys, trying an access entry, collecting facts

Status: accepted

## Context
The inventory (ADR 0034) stores servers, pinned host keys and access entries that name vault secrets, and says "nothing connects yet". The SSH layer (ADR 0035) can connect, with the host key checked before any credential leaves. This slice joins them: the API reads a server's host key and lets a person pin it, tries an access entry, and collects the facts of a server; the console shows all three. The design is `docs/en/design/05-security.md` (section 4: host key pinning, confirmation on first connection, alert on change; section 7: where Swellwright may connect) and `02-data-model.md` (`ServerFact`).

## Decision

### Five routes, one permission
`POST /servers/{id}/host-keys/scan`, `POST /servers/{id}/host-keys/accept`, `POST /servers/{id}/access/{accessId}/verify` and `POST /servers/{id}/facts/refresh` need `servers:write`; `GET /servers/{id}/facts` needs `servers:read`. The four POSTs make the API open a connection, and verify and refresh use stored credentials, so a role that may only read must never be able to cause one; the scan sends no credential but opens a connection all the same, and the same role covers it. No step-up: none of these reveals a secret (a value is read only into memory for the length of the connection and never returned or logged), and a person who may change an entry may try it. The routes accept API tokens (`auth: any`) like the rest of the inventory. Reading the facts connects to nothing.

### Scan, confirm, pin
A scan reads the key with `fetchHostKey`, so no username, password, key or signature is sent. It answers the algorithm, the fingerprint and how it relates to the pinned keys: `new` (nothing pinned), `pinned` (it is one of them) or `differs` (keys are pinned and this is none of them). `differs` is expected after the operating system of the server was reinstalled and is what a man in the middle looks like, so the response makes it unmistakable and the console says so in red. A scan stores nothing; it writes the audit note `server.host_key.scanned` (an outcome, and for a failure the error code). The scan and every connection prefer the key types that are pinned (ADR 0035, ADR 0040): a server that gained a key of another type is not a changed server, and `differs` means that the key of a pinned type is another key.

Accepting takes the fingerprint the person confirmed and asks the server **again**: only if the key it shows now is exactly the confirmed one is it pinned (source `scan`, the same record as a key pinned by hand); otherwise 409 `host_key_mismatch` with both fingerprints and nothing stored, so a person never pins what they did not look at. A key that is pinned already changes nothing (200, no record). When other keys are pinned, a different key needs `replace: true` in the body, which deletes the old keys in the same transaction (each one a `server.host_key.revoked` record with `reason: replaced`, then `server.host_key.pinned` with the number replaced); without it 409 `host_key_replace_required` lists what is pinned. The transaction runs under the inventory's advisory lock, so two people cannot pin and replace at once, and a revoked or replaced key closes every pooled connection: nothing keeps using the old trust.

### Which addresses may be contacted
Before every connection the API applies `validateTargetAddress` and `resolveTargetAddress` of the SSH layer (ADR 0035) to the address in the inventory; the connection then goes to the checked address and the pinned key proves who answers. Loopback (the machine Swellwright runs on), link-local and cloud metadata addresses are refused unless the installation allows the first (`SW_SSH_ALLOW_LOOPBACK`, default false; the other two are never allowed); private ranges and host names are allowed by default because fleets live there (`SW_SSH_ALLOW_PRIVATE`, `SW_SSH_ALLOW_HOSTNAMES`, default true). A refused address is 409 `address_not_allowed`; a host name that does not resolve is 502 `ssh_connect_failed` with `reason: dns`. Tests turn loopback on per application instance; nothing else needs it.

### One pool, short idle, and what a connection needs
One `SshPool` per process serves every operation (two connections per host, ten seconds idle, closed on shutdown and whenever a pinned key is revoked or replaced). A connection to a server needs a pinned key (otherwise 409 `host_key_not_pinned` before any socket is opened), an address the policy allows, and the secrets. Secrets come from `VaultService.readForServer(id, type)`: it checks the secret type (`ssh_password` or `ssh_key`, so an entry cannot be pointed at a secret of another kind), needs the vault open (423 `vault_sealed`, the answer every other consumer of the vault gives) and writes no `secret.revealed` record, because no person asked; the operation's own record says that the secret was used. Deadlines: connect and log in `SW_SSH_CONNECT_TIMEOUT_SECONDS` (15), one command `SW_SSH_COMMAND_TIMEOUT_SECONDS` (60; the quick probes never take longer than 20).

### Errors
The typed errors of the SSH layer become stable API codes with an HTTP status: `host_key_mismatch` (409, `details: { expected, actual }`), `ssh_auth_failed` (502), `ssh_key_invalid` (409: the stored key cannot be parsed; nothing was sent), `ssh_connect_failed` (502, `details.reason`), `ssh_timeout` (504, `details.phase`), `ssh_failed` (502) and `facts_unreadable` (502). A defect stays a 500. A host key that is not the pinned one is its own, prominent error everywhere, never a "result": the connection stopped before a credential was sent, and the person must see both fingerprints.

### Trying an access entry
`verify` logs in with one entry and runs read-only probes: `id -un`, `id -u` and a sudo check (`true` through the sudo wrapper of the layer: the stored sudo secret on standard input when there is one, otherwise `sudo -n`). The answer is `{ ok, verifiedAt, latencyMs, remoteUser, isRoot, sudo, error? }` with `sudo` one of `not_needed` (the login is root), `ok`, `password_required`, `failed` or `unavailable`. A login that does not work is a **result** (200, `ok: false`, the code and message): checking is what the person asked for, and "the password is wrong" is the answer. What stops the attempt before it starts (nothing pinned, the address policy, a sealed vault) and a host key mismatch are errors. The time and the outcome are kept on the entry (`last_verified_at`, `last_verify_ok`, one moment for the answer, the entry and the record) and are shown in the console. The record `server.access.verified` carries the outcome and the code, the remote user, root or not, sudo and the latency, never a value.

### Facts
`refresh` runs a fixed script (`apps/api/src/servers/facts/collect-facts.sh`) over SSH and parses its output strictly. **The script is read-only**: it writes nothing (every redirection goes to `/dev/null`; the package list is read with `apt-get -s` and both package caches switched off, so even root writes no cache), starts and changes nothing, installs nothing and asks nothing outside the machine; every external program has a deadline, every list a length. It is plain POSIX `sh` with `LC_ALL=C`, starts with a header that says what it promises, prints `@@swf begin NAME` ... `@@swf end NAME` sections around the raw output of the tools and says `!absent` (the tool is not installed) or `!error` (it failed, usually for lack of root), so "none found" and "could not look" are told apart. A test reads the script and fails the build if it contains a write, a network tool or an installing package command. The SHA-256 of the file (read with LF line endings) is stored with every result (`server_facts.script_sha256`) and shown, so the history says which script produced which facts. It is sent as `sh -c '<script>'` rather than on standard input so that no tool inside it can swallow the script.

Rights: the script runs as root when the login is root, through `sudo` when the login is not root and the sudo probe says `ok` (the stored password on standard input, as for every sudo call), and as the plain login otherwise; `collectedAs` (`root`, `sudo`, `user`) is derived from the uid the script itself reports. What needs root (the owners of listening sockets, `sshd -T`, ufw, docker without the docker group) is `null` for a plain login, not empty. Several access entries are tried by priority: one that is refused is skipped, any other failure ends the refresh.

The schema (`ServerFactsSchema`, `schemaVersion: 1`) has every field nullable (a minimal server lacks tools): the operating system (`ID`, `VERSION_ID`, `PRETTY_NAME`), kernel, architecture and host name, uptime and boot time, processors, load, memory and swap, the disks of `/` and of block devices, the clock (server time, skew against the API, time zone, NTP state), the state of systemd and the failed units, a pending reboot, listening TCP ports with their processes, the state of `ssh`, `docker`, `haproxy`, `nginx`, `fail2ban` and `ufw`, the versions of docker, haproxy, nginx and fail2ban, the containers with their image tag (a node's version is its tag), the ufw status line, the effective `sshd` port, password authentication and root login, the number of upgradable packages (apt, from the lists the server already has), and `warnings`. The parser never throws: unknown text is ignored, a malformed section makes its field null and adds a warning, a section cut off keeps what came before it, an output that is not the script's at all is 502 `facts_unreadable` and does not replace the facts that were there. A stored record that does not fit the schema (another version) is shown as unreadable with one warning, never as a 500. The `ServerView.facts` summary (operating system, kernel, time) is filled from it, so the table columns work. One refresh per server runs at a time: a second request joins the one that runs and gets its answer; the record is written once, for the person who started it.

### Audit
Three new actions: `server.host_key.scanned` (a note: it records something that changed nothing), `server.access.verified` and `server.facts.refreshed` (strict, in the same transaction as what they changed; outcome `success` or `failure`, with the code for a failure). `server.host_key.pinned` and `.revoked` stay for accepting and replacing, with `source` and `replaced`. There is no record for a refusal before anything was attempted (not pinned, address policy, sealed vault, rate limit): nothing happened to a server.

### Rate limit
A person may start `SW_SSH_RATE_LIMIT_PER_MINUTE` (20) scans, confirmations, checks and refreshes a minute, counted per user over all four (a window limiter in memory, like the other limits); over it the answer is 429 with `Retry-After` and no connection is made. A request that joins a running refresh counts too.

### A defect of the SSH layer found on the way
`SshConnection.close()` called `Client.destroy()` of ssh2 a second after `end()` as a backstop against a peer that never answers, but ssh2's `destroy()` does nothing once the socket is no longer writable, which is the state `end()` leaves it in; a pooled connection to a peer that had gone away kept its socket for ever and the process could not exit. `close()` now destroys the socket itself, with a test.

## Consequences
- A server can be added, its key read and confirmed in the console, its login tried and its facts read without a shell on the Swellwright host. The first-use flow is the one `05-security.md` describes: the fingerprint is shown, a person confirms it, and what answers later must match.
- `ServerView.facts` and `GET /servers/{id}/facts` change shape (`{ facts: typed, collectedAt, source, scriptSha256 }`); nothing wrote facts before, so no data is lost. OpenAPI 0.20.0.
- Facts of a server that is not root and has no sudo are thinner, and say so (`collectedAs: user`, nulls).
- Passwords of a login are tried exactly as often as the person asks: nothing retries on its own.

## Not built here
Collecting facts on a schedule, drift between facts and a baseline, commands, scripts and detached steps from the console, SFTP, the terminal, SSH certificates as a method, linking a server to a panel node, alerts about a changed host key found by a background check (a changed key is found when an operation runs).
