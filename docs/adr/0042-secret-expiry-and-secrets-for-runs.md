# ADR 0042: The expiry of a secret means something, and a vault secret can be handed to a run

Status: accepted

## Context
The first real run of phase 2 (ADR 0040) left two things for a decision, and the owner decided both.

- **The expiry of a secret was a label.** A vault secret has an optional `expiresAt`; nothing read it. A secret that expired in 2020 still logged in to a server.
- **A vault secret could not be handed to a run.** The `SECRET_KEY` of a node, or the password of a new administrator, had to be typed into a command or a parameter, and a run stores both in plain text (and the output of a run is readable by everyone who may read servers).

## Decision

### Part 1: an expired secret is refused by everything that would use it

**One place decides.** `VaultService` hands a value to a consumer through one door (`takeValue`), and the consumers (a server login, a plugin, the token of a panel, a command run) differ only in which kinds of secret they take and in the words of their failures. The order is fixed: a sealed vault answers 423 `vault_sealed` first (nothing is decided about a secret that cannot be read); then the secret must exist (404), be of a kind this consumer may have (409), and not be expired; only then is the value decrypted. **Expired is `expiresAt <= now`:** the moment of the expiry counts as expired, so a secret never works a moment past its time. `now` is the clock of the process (`AppOptions.clock`, token `CLOCK`; tests move it instead of waiting).

**A typed error.** A refused use is 409 `secret_expired`, with `details: { secretId, secretName, expiresAt }` and a message that says to renew the expiry or replace the secret. It never carries a value. Every operation answers it in its own envelope, the way it answers `vault_sealed`: the HTTP routes as the error envelope (every route that connects to a server names it), the plugin broker as `PluginBrokerError` with `code: 'secret_expired'` and a message that starts with `secret_expired:` (a plugin sees only the text), the runner as the `errorCode` of the target. The console says which secret has to be renewed.

**The consumers.**
- *Server access* (`SshService.withAccess`, therefore verify, facts, the artifact push, check and removal, and the runner) reads the login secret and the sudo secret through the door, **before any credential is sent and before a connection is opened**: the host sees no authentication attempt. When a server has several access entries and one of them names an expired secret, that entry is skipped like an entry the server did not accept, and the next one is tried; when all are expired the answer is 409 `secret_expired` (and nothing is recorded as a failure of the server: nothing was attempted). The check of one entry (`verify`) is an error, not a result: like a sealed vault or an address the policy refuses, it stops the attempt before it starts.
- *Plugins* (`readForPlugin`): the broker maps the error, the plugin host turns it into the call error `secret_expired`.
- *The panel token* (`readForPanel`, ADR 0041) goes through the same door, so a panel connection whose token secret expired is refused like everything else. (The expiry read out of the token itself, ADR 0041, is a separate fact about the panel's own token.)
- *Command runs* (Part 2) go through it too.

**A run that has started is not cut short.** The expiry is checked when a use begins, not in the middle of one. A script runs detached on the server (ADR 0035); the runner follows it by polling and each poll opens a connection with the access entry's secret. If that secret expired meanwhile, the poll still goes ahead (`allowExpired`, only for a target whose step has started, for the cancel of a run and for removing the record of a step that ended), so the script is followed to its end, its output is complete and its record is removed. What is refused is the *next* use: a new run, a target that has not started. The same holds for the scrubbing of the output of a run that was handed secrets (below). A target that has not started when its secret expired ends `failed` with `errorCode: secret_expired` and a message naming the secret; the other servers of the run go on.

**What a person still can do.** A person may reveal an expired secret (to read it and rotate it): the answer says `expired: true`, and it is recorded as every reveal. Renewing (`PATCH` with a later `expiresAt`, or `null`) and replacing the value work as before. Nothing is deleted automatically.

**What people see.** `SecretView` has `expired` and `expiresInDays` (whole days, rounded up; 0 or less once it has passed; null without an expiry), worked out by the server clock, and the access entries of a server (`SecretRef`) carry the same with `expiresAt`. The vault table shows a red "Expired" badge or an orange "Expires in N days" (from `SECRET_EXPIRY_WARN_DAYS`, 14), has a filter by state and a notice above the table; the server drawer shows the badges and a red warning on an entry that names an expired secret; the pickers of secrets (access entries, plugin settings, the run dialog) mark expired secrets.

**The audit record.** A refused use is noted: `secret.use_refused` (outcome `denied`, no actor, the secret as the object; details `reason: expired`, the secret's type, the consumer kind and its id). It is written **at most once per secret per ten minutes** (a map in the process, on the clock above), so a loop that retries a server for an hour cannot flood the chain. No value is ever part of it.

### Part 2: a vault secret handed to a run as a file

A run (inline command or script) may carry `secrets: [{ name, secretId }]`. The runner writes each value to a **file below the step directory** for the length of the run, sets `<NAME>_FILE` for the script and removes the files when the script ends. The value is never in a command line, in the environment of the SSH command, in `script.sh`, in the `env` file, in the stored run or in a log.

**Which secrets, and which names.** The kinds a run may be given are `generic`, `panel_token`, `provider_token`, `telegram`, `dns_oauth` and `ssh_password` (`RUN_SECRET_TYPES`): text a script reads. **Not `ssh_key` and not `ssh_ca`:** a private key is structured and far more powerful than anything a script needs, and the CA key signs for the whole fleet; there is no scenario here that needs them. A name matches `^[A-Z][A-Z0-9_]{0,63}$`, is unique within the run, may not start with `SW_` or `SWELLWRIGHT_` (those are Swellwright's variables), and a run has at most 8 secrets. Anything else is refused before anything is queued.

**A `secret` parameter.** A script may declare a parameter of the kind `secret` with the kinds of secret it accepts (`secretTypes`, a subset of the above). Its value in a run is the id of a vault secret. The server turns it into a secret of the run named after the parameter in capitals (`node_key` becomes `NODE_KEY`, so the script reads `$NODE_KEY_FILE`) and keeps it out of the stored `parameters` and out of the environment. The parameter has no default (a secret is chosen by a person), and its name must not start with `sw_` or `swellwright_`. A name used both by a parameter and by `secrets` is a 400.

**Delivery.** The launch of a detached step already sends the script, its input and its environment on the standard input of one command. The secrets are further frames of the same input (`SECRET NAME sha256` and the base64 of the value, checked against the hash on the server). The launch program writes each to `<step dir>/secrets/NAME` (the directory 0700, the file 0600; the owner is whoever owns the step directory, as for `script.sh` and `env`, so a step that runs as root through sudo reads them as root and the login can still remove them) and any failure takes the whole step directory with it. The wrapper exports `NAME_FILE="$SWELLWRIGHT_STEP_DIR/secrets/NAME"` (a line of the `env` file built from the validated name, so no caller text is part of it) and **removes `./secrets` the moment the script ends, before the exit marker is published**, so a step that is seen to have ended has none left. The ways a script can end without the wrapper getting that far are covered by three more places: `cancelStep` removes the directory after TERM and after KILL (and when the wrapper is already gone), `getStepStatus` removes it when it finds the step `exited` or `lost` (a wrapper that was killed alone, the case "killed wrapper"), and `removeStep` removes the whole step directory. `shred` is not used: the files are unlinked (they sit on the file system of the server, which is not Swellwright's to wipe; the point is the time they exist, which is the length of the run). Proved by scenarios that run against a real shell in CI and against a real sshd: modes 0600/0700, the value in exactly one file while the script runs and in no command line (`ps`), no copy left after exit, failure, the script killing itself, cancel (TERM and KILL), a killed wrapper, a forced removal, and with sudo.

**What the runner keeps.** Nothing of a value in the database: the run stores `{ name, secretId, secretName, secretVersion }` per secret (the table `command_run_secrets`; the secret id goes null if the secret is deleted after the run, the name stays). The values are read from the vault **when needed**: to deliver them when a target is started, and on every poll of a run that was handed secrets, to take them out of the output; they are decrypted for that poll and dropped with it, never cached between polls. **The runner never needs a value to find a step again** (a step that exists is attached, and the launch program returns before it reads any frame), but the scrubbing needs the vault to be open, which polling needs anyway (the access secret is read from it too). So after a restart of the API the vault is sealed and the target says `waiting: vault_sealed`; once it is unsealed the run goes on. A restart between "run created" and "delivered" therefore needs no special case: no value was held across it, the values are read from the vault when the target is started, and until then nothing is on any server. If the value is not what the run was queued with (see below), the target ends `failed` with `secret_unavailable` before anything is written.

**The version, and the guard.** The run records the version of each secret it was queued with. The value is delivered, and scrubbed from the output, only if the secret is still at that version; otherwise the target fails (`secret_unavailable`, with the reason). While a run that was handed a secret is `pending` or `running`, the secret **cannot be replaced or deleted** (409, "still going"); its expiry and details can still change. Making a run, replacing a value and deleting a secret take turns under one advisory lock (`7761242`), so a value cannot be replaced between the check and the commit of the run: the run is queued with the versions it checked, re-read inside its transaction. A secret deleted after the run has ended keeps its name in the history.

**Authorization.** A person who can run commands could print the secret, so handing it over is a reveal in effect. `secrets` (or a `secret` parameter that is filled in) needs **`servers:exec` and `vault:reveal`**, and a fresh step-up (the route's `stepUp`, which is a session-only route: an API token can never make a run, the existing tests prove it, and a token cannot hold `vault:reveal` either). A role without `vault:reveal` gets 403 and an `authz.denied` record naming the permission, and nothing is queued. The vault must be open (423 first) and the expiry rule of Part 1 applies at creation (409 `secret_expired`, nothing queued, nobody connected to), and again when each target starts. **Audit:** `secret.used_in_run`, one record per secret **in the same transaction as the run** (its secret as the object; details the run id, the name, the secret's name and version, how many servers and the first five server ids), and `command.run.started` carries the number of secrets. Never a value.

**Output safety.** The stored output and the live output of a run that was handed secrets are scrubbed of the literal value: wherever it occurs it is replaced by `[secret NAME]`. Details that are decisions:
- *What is looked for* is the value without its trailing line break (a secret file of one line ends with one, and a script that prints `$(cat file)` does not), so the line break after a printed value stays: `cat "$NAME_FILE"` shows `[secret NAME]` and then a new line. Several secrets are looked for at once; of two that start at the same place the longer wins. Any length is scrubbed; a secret of one or two characters will turn every such character of the output into a marker, which is the person's choice of secret.
- *A value can straddle two reads.* The runner reads the server's output file in pieces, and a poll may fall in the middle of a printed value. A tail of a read that could be the start of a value is therefore **not stored yet**: the read offset stays in front of it and it is read again with the next poll (at the end of the step nothing is held back; at the output limit the held bytes are dropped, never stored). Because a marker is not as long as the value it replaces, two offsets are kept per stream: how far the server's file has been read and how much is stored (`stdout_read`/`stdout_stored` and the same for stderr); the chunks and the paging by byte offset work on the stored one.
- *It is best effort, and says so.* A literal match on bytes. A script that transforms a value (base64, reversing it, splitting it across lines, hashing, printing it character by character) is not caught, and no program can promise that; two secrets of which one is the beginning of the other can leak the rest of the longer one at the end of a read. The notice in the console and in the API description says what it does and what it does not. The protection that does not depend on it is the authorization above.

**Console.** The run dialog has a Secrets section: rows of `NAME` and a secret picker (the secrets of the kinds above, names only, expired ones marked), an add button that is disabled with a tooltip for a role without `vault:reveal`, a notice that says what a run can do with a secret and that the output is scrubbed best-effort, and the existing step-up dialog when the run is started. A script with a `secret` parameter shows a picker for it (closed, with the reason, for a role that may not). The script editor offers the new parameter kind and the kinds of secret it takes. The run view lists the names and the secrets (and says when one was deleted since) and shows the markers in the output in the colour of a warning. Texts are in English and Russian.

**The installer.** The node installer (ADR 0036) reads its secret parameters from the environment or `--env-file`; reading `<NAME>_FILE` for them is the installer's own change (another work item), and this ADR gives it the variable and the file.

## Consequences
- A secret that has expired can no longer log in to a server, run a plugin, connect a panel or be handed to a run, and everybody who looks sees it; the audit log says that it was tried, without flooding.
- The node's `SECRET_KEY` and similar values can be used by a script without being typed into a command, stored in a run, or left on the server after it.
- The stored output of such a run differs in length from the server's file; the run view shows the stored bytes, and the "kept of total" notice at the output limit compares the stored with the server's size (the two can differ by the markers).
- A value cannot be replaced or a secret deleted while a run that was handed it is going. That is a rule a person can run into; the message says why.
- The check of the expiry sits in the vault, so a new consumer (a later plugin broker, SSH signing keys, the engine) gets it by calling the same door.

## Not built here
Handing a private key (`ssh_key`) or a CA to a run, a secret as an environment variable (deliberately never), streaming the secret over a pipe instead of a file (a script that wants it on standard input can read the file), a transformation-aware scrubber (encodings of the value), scrubbing of the output of an interactive terminal (the terminal is a separate client and records nothing yet), expiry reminders by mail or message, an automatic rotation of an expired secret, deleting expired secrets automatically, and the engine's approvals for a run that carries secrets (phase 4).
