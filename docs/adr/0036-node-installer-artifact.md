# ADR 0036: The node installer as a built-in artifact

Status: accepted

## Context
Design principle 10 (`docs/en/design/00-index.md`) and policy P-009 of the engine say that every change to a node goes through a versioned artifact, verified by its hash before it runs. Phase 2 lists "artifacts (node installer, `node-engine`)" and its acceptance includes "artifact hashes are verified". The installer is the main thing Swellwright ships to a server: a Remnawave node needs a firewall that does not leak its API port, Docker, a TLS front that answers like an ordinary web server, the node container and a set of checks, and administrators have been installing that by hand or with private scripts.

A working installer exists in private use. It is a production tool, written in Russian, with the layout of one infrastructure in its panel-host steps. The public project needs a clean derivative: English, generic, parameterised, tested, and treated as data by the rest of the system (a file with a version and a hash), not as code of the server. The design already says where the line runs: the engine (workflow, snapshots and rollback, panel calls, DNS, delivery over SSH) lives in Swellwright; the installer is what runs on the node.

## Decision
**Location and shape.** `artifacts/<name>/` in the repository root, one directory per artifact: `install.sh` (POSIX `sh`, tested under dash), `manifest.json`, a README and `test/`. This replaces the `packages/node-assets` of the architecture sketch: an artifact is a file that is shipped, not a workspace package. The `node-engine` of the design will be the second artifact. `artifacts/README.md` states the contract.

**An artifact is immutable, versioned and verified by its hash.** The version is `INSTALLER_VERSION` in the script (semantic versioning); a released version is never edited, a changed script is a new version. `manifest.json` carries the SHA-256 and the size of the file; Swellwright will check the hash before upload (against the bytes it holds) and after upload (on the node, with `sha256sum`) before it runs anything (the artifacts mechanism is a later slice; this one only produces the artifact and its manifest). The script does not check itself: a modified script would check whatever it likes.

**The manifest is generated, never written by hand.** The script carries `#@meta`, `#@step` and `#@param` lines (one JSON object each); `scripts/artifact-manifest.mjs build` turns them into `manifest.json` and into the step and parameter tables of the README, and `--check` (a CI step, `pnpm run artifacts:check`) fails when the manifest, the README tables, the file hash or the size differ from the script. A pattern or default written `@NAME` takes the text of the assignment `NAME=...` in the script, so the regular expressions that validate input and the patterns the manifest publishes are one text. The tool also checks that the steps are functions, that `full` runs exactly the steps marked for it, that the parameter list the script loads from files is the list of the manifest, and that the file has LF line endings and no carriage return (a `.gitattributes` rule keeps checkouts from changing the bytes).

**The interface is steps and parameters.** One function per step (`preflight`, `base`, `system`, `hostname`, `firewall`, `fail2ban`, `docker`, `apiacl`, `certsync`, `nginx`, `haproxy`, `node`, `verify`, `ssh`, `rename`), each idempotent. `full` runs twelve of them in a fixed order; `ssh` and `rename` are separate because they need a decision (an administrator and keys, a new name). Parameters come from the environment, an `--env-file` or the saved configuration, in that order of priority, and every value is validated before the first step runs; without a terminal (`--non-interactive`) a missing required parameter stops the run with its name. `preflight` and `verify` are read-only and exit 2 when a check fails (1 is an error that stopped the run). The journal `/var/log/swellwright-node-installer.log` (mode 600) has one `CHECK ok|warn|fail | label | detail` line per check, which is what a caller should parse; the screen is for people.

**Safety properties that the tests pin.** The node API port is open only to `PANEL_ALLOW_IP`, in UFW and in the `DOCKER-USER` chain (Docker publishes around UFW); HTTPS without or with a foreign SNI gets the default site's 404, not a dropped connection; the certificate receiver is a user whose only power is `rrsync` into the certificate directory (`command=`, `restrict`); the key file is mode 640; the node container has `SNI_VERIFICATION=true`. The installer never edits SSH without a way back in: root login is closed only when the `sudo` group has a member, password login only when a member has a key, a configuration `sshd -t` refuses is reverted, SSH is allowed in UFW before UFW is enabled and the port of the current session is kept open. No secret is ever an argument, appears on the screen or in the journal; the node secret lives in the compose file (mode 600), an administrator's password goes to `chpasswd` on its standard input. Nothing is evaluated: an env file and the saved configuration are parsed line by line, names must be known parameters, values are validated and only then written into configuration files.

**Differences from the private script, on purpose.**
1. English only, and no step that depends on one panel server's layout: no nginx-ui, no panel-side certificate-sync menu, no closing instructions about one fleet's profiles and hosts. The certificate distribution to nodes is a plugin concern (`docs/en/design/13-plugins-and-opensource.md`); only the node side stays. Control variables are `SW_*`, units and files `sw-*` (the private script's `rw-*`); a node set up by the private script is therefore not recognised, only overwritten step by step.
2. Every parameter is validated, whether it was typed or given (the private script validated only what was typed at a prompt; a value from the environment went into root-written files unchecked). A value with a line break never matches. The panel address list rejects `0.0.0.0`, loopback and multicast addresses; a fail2ban ignore range must have a prefix of 8 to 32.
3. An env file is read, not sourced (`. file` would run it), must be mode 600 and owned by the user running the installer; an unknown name stops the run. The saved configuration is read the same way. Priority: environment, then env file, then saved configuration, then defaults (the private script let the saved configuration override the environment).
4. Signing keys are accepted only if the file carries a pinned fingerprint (Docker's `9DC8...CD88`; the three nginx.org keys), after which https or http makes no difference. The private script only checked that the file was an OpenPGP key. The fingerprints were read from the live key files on 2026-11-21. If a vendor rotates every pinned key, the installer refuses and a new artifact version updates the list.
5. Docker comes from Docker's apt repository by default (`DOCKER_SOURCE=apt`); the `get.docker.com` script of the private script is `DOCKER_SOURCE=script`. An existing Docker without the compose plugin is a stop, not an overwrite.
6. Debian 12 is a target besides Ubuntu 22.04 and 24.04: the nginx.org and Docker repositories follow `ID` and the release name, HAProxy comes from the PPA of its maintainer on Ubuntu (`HAPROXY_SOURCE=auto`, version `HAPROXY_VERSION=3.2`) and from the distribution on Debian. Debian has not been exercised on a real host.
7. fail2ban ignores loopback, `PANEL_ALLOW_IP` and `FAIL2BAN_IGNORE_EXTRA`; the private script also ignored `10.0.0.0/8`, an assumption of one network. `python3-systemd` is installed with it because `backend = systemd` needs it.
8. The firewall step stops if UFW cannot be enabled (the private script went on), and keeps the SSH port of the running session open besides `SSH_PORT`.
9. The SSH step takes its decisions from parameters (`SSH_DISABLE_ROOT`, `SSH_DISABLE_PASSWORD`) instead of questions, sets a password only on an account that has none and requires `NEW_USER_PASSWORD` without a terminal, has no `SSH_FORCE_ROOT_OFF` bypass, and reverts the root drop-in when `sshd -t` fails.
10. The nginx reload watcher (`sw-certs-reload.path`) belongs to the nginx step, not the receiver step, so a certificate that arrives any other way is picked up too; `certsync` is optional in `full` (no key, no receiver).
11. Fewer packages: only what the steps use (no `nano`, `wget`, `cron`; `software-properties-common` only for the PPA, `sudo` only for the SSH step).
12. Backups `file.bak.TIMESTAMP` are restored by name, not by modification time (`cp -a` keeps the original's time). One run at a time (`flock`). The journal is never moved to `/tmp`. A new node and a redeploy are two actions, not a question inside `full`.
13. Without a terminal `NODE_IP` is guessed only when it cannot be wrong (one address, or an A record that names one of them).

**Tests.** `artifacts/node-installer/test/run-tests.sh` (POSIX sh, runs in Git Bash and on the CI runner, refuses to run as root) executes every step in a temporary root with stubbed commands (`apt-get`, `ufw`, `systemctl`, `docker`, `sshd`, `useradd`, `iptables`, `curl`, `gpg`, ...) that record their calls, and asserts the files written, the calls and their order, the modes asked for, and that no secret reaches the screen, the journal or an argument. A table of accepted and refused values per parameter runs through the shell validators and, separately, through the patterns of the manifest, and the two must agree. `sh -n` and `dash -n` run on the script; `shellcheck` runs in CI; a real HAProxy checks the file the haproxy step generates. The CI job `artifacts` runs all of that and the manifest check.

## Consequences
- Anyone can read, run and audit the installer by hand; Swellwright will run the same file through its SSH layer, and the manifest says what to run, with what, and what it changes (`readOnly`) before it runs.
- The tests prove the logic of the steps, not the behaviour of apt, systemd, UFW, Docker or iptables on a real server. The private script has run in production for the steps they share; the differences above (Docker from the repository, key pinning, the SSH checks, Debian) have not, and the first real run of this artifact will be on a disposable server, one step at a time. (That run was made on a reset Ubuntu 24.04 server and found three defects of the installer, fixed in version 1.0.1; ADR 0040.)
- A change to the script is a change to a file that servers will run: it is reviewed like code, the version is raised, the manifest is rebuilt in the same commit.
- Pinned values go stale on purpose: the node image tag (`DEFAULT_NODE_IMAGE_TAG`, 3.4.6), the HAProxy series, the key fingerprints. Updating them is a new artifact version.

## Not built here
The artifacts mechanism of the server (the `Artifact` record, upload over SFTP, hash checks before and after, promotion), the `node-engine` (snapshot, undo plan, safety timer for SSH and UFW), messages in other languages, a JSON result of `verify`, an uninstall step, the split of the self-steal scheme (`certsync`, `nginx`, `haproxy`, the loopback publish of the node) into the `node-selfsteal` plugin of the design with a plain node flavor beside it, DNS and panel steps (the engine's), and signatures of artifacts (the hash is the integrity check; a signature would add who published it).
