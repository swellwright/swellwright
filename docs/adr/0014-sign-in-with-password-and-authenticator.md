# ADR 0014: Sign-in with a password and an authenticator

Status: accepted

## Context
The Phase 1 acceptance criterion starts with "login with TOTP". Three questions needed an answer: how passwords and one-time codes are handled, where the TOTP secret lives while the vault is sealed on start (ADR 0006), and how a brand-new instance, reachable from the network before anyone owns it, avoids being claimed by the first visitor.

## Decision
- **Passwords:** Argon2id from `node:crypto` (Node 24.7 and later; no dependency), 64 MiB, 3 passes, 1 lane, a 16-byte salt and a 32-byte tag, stored as a PHC string. Old hashes keep verifying after the parameters are raised and are rehashed on the next sign-in. Input is NFKC-normalized. At most four hashes run at once, because every one needs 64 MiB and the sign-in is unauthenticated. An unknown user costs the same work as a wrong password. The policy (12 to 128 characters) applies when a password is chosen; a sign-in only checks the bounds.
- **TOTP:** our own implementation of RFC 6238 (SHA-1, 6 digits, 30 seconds), checked against the RFC test vectors, with one step of clock drift. Every time step is accepted once: the step is stored with a conditional update, so two requests with the same code cannot both succeed. The secret is 160 random bits.
- **The TOTP secret is sealed with an instance authentication key, not with the vault.** The data model classes it as "vault only", but the vault starts sealed and the owner has to sign in to unseal it, so the secret must be readable while it is sealed. It is encrypted with AES-256-GCM under `SW_AUTH_KEY` (32 random bytes in base64, supplied by the deployment, never stored in the database), with the user id as authenticated context. A copy of the database alone reveals no TOTP secret. The key is required in production; in development a random one is made per process, with a warning. The blob carries a version byte so a later key rotation can tell old from new.
- **Sessions:** a random 256-bit token in the cookie `sw_session` (`HttpOnly`, `SameSite=Strict`, path `/api/v1`, `Secure` in production); the table keeps only its SHA-256. A session has a stage. The password makes a `password_verified` session (10 minutes) that can only finish the sign-in. Finishing it deletes that session and issues a new `active` one, so nothing is carried over (no session fixation). An active session has an idle expiry (120 minutes, moved forward at most once a minute) and an absolute one (12 hours); both are configurable. A disabled user's sessions stop working at once.
- **Lockout:** failures of the password and of the second step share one counter per account. Five in a row lock the account for 15 minutes and end its sessions; a completed sign-in resets the counter. Wrong passwords and unknown users answer the same 401. A locked account answers 429 with `Retry-After`: this confirms to someone who locked it that the account exists, which is accepted. An in-memory limit per address (30 sign-ins in 5 minutes) slows guessing from one place.
- **Recovery codes:** ten codes of 60 bits, shown once when the authenticator is confirmed, kept as SHA-256 hashes, each usable once (claimed atomically).
- **First run:** `POST /setup/owner` works once. It needs a setup token that the server prints to its log at start (or `SW_SETUP_TOKEN`), is limited to 10 attempts in 15 minutes per address, and creates the owner under a PostgreSQL advisory lock, so two simultaneous requests produce one owner.
- **CSRF:** `SameSite=Strict` plus a check of `Origin` on state-changing methods (the list in `SW_ALLOWED_ORIGINS`, by default the host the request was sent to), with `Sec-Fetch-Site` as the fallback. A request that carries neither is not from a browser. A CSRF token is planned for a later slice.
- **Contract:** every route states its `auth` level (`none`, `pending`, `session`, `token`); global guards enforce it and refuse `token` until tokens exist. Request bodies are validated against the contract before a handler runs, and a response without a body (204) is part of the contract.
- **Audit:** sign-in events are recorded in the audit chain (ADR 0015): user ids and login names of known accounts only, never codes or passwords, and nothing an unknown caller typed.

## Consequences
- The owner can sign in while the vault is sealed, and the database copy is still useless without the key. The price is a second key to look after: it lives with the deployment's secrets, and a lost `SW_AUTH_KEY` means every user enrolls the authenticator again.
- Known gaps, to be closed in later slices: no password change or reset, no user management, so an owner who loses both password and authenticator has no supported way back in yet (a command-line reset is planned); no WebAuthn, OIDC or IP restrictions. (Step-up authentication came with ADR 0017.)
- Node 24.7 or later is required for `crypto.argon2`; the project already pins Node 26 (ADR 0009).

## Note of 2026-11-26: the lockout is split (ADR 0049)

Changed by ADR 0049. Wrong passwords delay new sign-ins without ending sessions. Wrong second factors at sign-in or enrollment can lock an account/source pair and end its pending sessions (`SW_LOCKOUT_ATTEMPTS`, `SW_LOCKOUT_MINUTES`). A separate account-wide ceiling limits pending factor failures across sources. An active session has its own step-up budget and keeps existing elevation. Every session carries the user's credential epoch, and sign-in is serialized per account in PostgreSQL. An IPv6 `/64` counts as one source and the hasher queue is bounded.
