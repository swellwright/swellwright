# ADR 0046: The API console (read), and a budget of its own for the computed configuration

Status: accepted

## Context
Phase 3 lists "API console (read)" (`docs/en/design/11-roadmap.md`, P21 in `03-scenarios.md`, section 7 of `04-remnawave-integration.md`): a place inside Swellwright to explore the panel's API without leaving the console. The connection and the read model are in place (ADR 0041, 0043), accepted on a real panel. What is new is that a person can now ask the panel *anything the API offers*, with the token the vault holds, which is a different kind of power from reading the objects the typed client knows. The design therefore starts from what the console must never do.

The frozen description of the panel's API (3.4.11, `packages/remnawave/spec/`, OpenAPI 3.0) has 218 operations: 94 GET and 124 that change something. Reading it for this slice showed three things the design had not counted on. Some GETs are not reads of the panel's objects: two create a WebAuthn challenge on the panel when asked for, one returns the secret key a node is installed with, one returns thirty fresh X25519 key pairs, and three return subscription bodies or connection keys, which are the links that work as credentials for a user. Twenty-eight GETs are about the people who use the panel (users, devices, subscriptions, requests, per-user usage, who is connected from where, torrent reports), and their answers carry names, mail addresses, messenger ids, device ids and addresses. And some endpoints are "admin JWT only": a token gets 403, the panel says so in the description.

The real-panel acceptance of ADR 0041 also found a small defect: the computed configuration of a profile counted as a forced refresh, so after a burst of `?refresh=true` reads it answered 429 for a minute.

## Decision

### The catalogue is built from the frozen description, at first use
`consoleCatalogue()` in `packages/remnawave/src/console/catalogue.ts` reads `spec/remnawave-api-3.4.11.json` (the image copies the folder next to `dist/`) and builds, once, a list of all 218 operations: the panel's own `operationId` (`NodesController_getNodes`), method, path, the group (the tag without "Controller": `Nodes`, `Subscriptions (protected)`), summary, parameters (path or query, typed: string with format `uuid`, `date`, `date-time`, `email` or an enumeration, number with its minimum and maximum, boolean, or structured), whether the body of a write is described, the content types of the answer, whether the description says "admin JWT only", whether it lists no security (a public endpoint), and the scopes it names (none today). The detail of one operation adds the schemas of its request body and its answer with every `$ref` followed (a recursive schema is cut where it repeats, and the walk has a budget of nodes). Nothing is asked of the panel to list: the catalogue works before a panel is connected. A different description replaces the file; a test holds the counts (218, 94 reads: 59 open, 28 about people, 7 blocked, 124 writes) so that a new release has to be judged by a person.

### Four availabilities, decided in a table and not guessed
`policy.ts` classifies every operation by its `operationId`, with the reason next to it, and tests fail when a listed id is not a GET of the description.
- **open**: reads the panel's own objects and aggregate statistics. Allowed with the permission `panel:console`.
- **user_data**: about the people who use the panel. Refused unless the installation sets `SW_PANEL_CONSOLE_USER_DATA=true` (403 `console_user_data_disabled`, the default), and then it needs `vault:reveal` as well as `panel:console`, and a freshly verified second factor (403 `step_up_required`); the call is recorded *before* the answer is delivered.
- **blocked**: never sent (403 `console_operation_blocked`, `details.reason` is `secret_material` or `side_effect`): the node secret key, the X25519 generator, connection keys, subscription bodies, the two passkey challenges.
- **write**: not a GET. Listed in the catalogue, greyed in the console with a lock and a note that writes arrive with the approvals of a later release (403 `console_operation_blocked`, `reason: write_operation`). Writing through the console is phase 7.

### A request names an operation, never a target
`POST /panel/api-console/requests` takes `{ operationId, pathParams, query }`. There is no URL, no header, no method. The server finds the operation in the catalogue (404 `console_operation_unknown` if it is not there), checks the policy above, then builds the path from the catalogue path and the values, which are checked against what the description says each parameter is: a UUID is a UUID, a date is a real date, a number is a plain decimal within the minimum and maximum, a value of an enumeration is in it, a string that goes into the path is letters, digits, dot, hyphen and underscore, not `.` or `..` and not containing `..` (no separator, no escape, no `@`, no `:`), a string in the query has no control character, and every value is at most 256 characters. A parameter the operation does not list is refused, a structured one (the table state of the panel's own pages: `filters`, `sorting`, `filterModes`) is not sent. Every problem is reported at once, field by field (`validation_failed`, `details.issues[].path` like `pathParams.uuid`), and never repeats the value. The query is written with `URLSearchParams`, the path with `encodeURIComponent`. Below this, `PanelHttp.urlFor` refuses any path that does not start with one slash or whose URL does not stay under the origin and prefix of the panel: `@host/x` appended to `https://panel` would be a different host, so the guard is in the transport layer and not only in the validation above it.

### The same machinery as every read, with one more door
The request goes through `PanelHttp`, the layer of ADR 0041: the address policy at connect time, TLS, the timeouts, four requests at a time, retries only for a GET that failed in a way that may pass (a reset, a refusal, 429 with the waits the client is willing to make, 5xx), redirects only inside the origin, the token in the one `Authorization` header. What is new is `getRaw`, which returns the final answer **whatever its status**: a 404 or a 400 of the panel with its body is what a person exploring an API wants to see, and it is a result (200 here, `status: 404` inside). Failures that say something about the connection stay errors with the codes of ADR 0041 (401 is `panel_unauthorized` and moves the state of the connection, 429 beyond the wait is `panel_rate_limited` with `Retry-After`, `panel_timeout`, `panel_unreachable`). A 5xx that keeps coming after the retries is returned as the answer it is. Two new codes: 502 `console_response_too_large` (the answer is over `SW_PANEL_MAX_RESPONSE_MIB`, and the client stops reading it) and 502 `console_response_unsupported` (a type that is not JSON, YAML, XML or text, bytes that are not UTF-8, or a NUL: binary and streams are refused, not shown).

### Masking: the answer never leaves unmasked
`ConsoleClient.send` turns the answer into something safe to show, in this order: the headers are cut to `content-type`, `content-length`, `retry-after` and `x-ratelimit-*` (values without control characters); the body is decoded, the **exact token** is replaced wherever it occurs (a panel that echoes the token back under a name nobody predicted is the one thing a deny-list cannot know, and this client holds the token); the body is parsed as JSON and passed through `maskSecrets`, or masked as text by its values; the masked JSON is written indented by two spaces; and only then is it cut to `SW_PANEL_CONSOLE_MAX_BODY_KIB` (default 1024) at a line and never inside a character, with `truncated` and the size of the panel's answer. Masking is of the whole parsed body, before the cut, so a secret after the cut cannot be found by asking for a bigger window.

Two profiles of the masker (`maskSecrets` got `extraSecretKeys`, and `people: 'off'`):
- **standard**, for every operation: the secrets every masked view hides, plus the access material of a user (`shortUuid`, `subscriptionUuid`, `subscriptionUrl`, `vlessUuid`, `trojanPassword`, `ssPassword`, `links`, `ssConfLinks`, `connectionKeys` and the three key lists) and the addresses of administrators in the settings (`allowedEmails`). `vmess://` and `ss://` links are masked as a whole (their payload is the configuration, id included), like a `scheme://user@host` link already was.
- **personal**, for the operations about people: also names, `email`, `telegramId`, `description`, `hwid` and the device fields, `userAgent`, every address (`ip`, `ips`, `requestIp`, ...), every `uuid` and tags, with the Xray rule for `users` and `clients` switched off (here `users` is the panel's list of users, and the numeric `id` is what a person addresses a user by, so it stays). The answer says `maskProfile: 'personal'`.
A mask is `[masked:1a2b3c4d]`, keyed as in ADR 0041, so equal values give equal masks and a list of users can be read for its shape. A hostile structure is the test: names with any case and separators, a secret at any depth in lists of lists, a document inside a string, links under a key nobody predicted, prototype names, a structure deeper than the limit (replaced as a whole), two thousand users. What the deny-list cannot know is the same as before and the console says so: masking is best effort.

### The permission, the limit and the audit
`panel:console` (new, implies `panel:read`, owner and operator; observer, terminal and auditor can browse the catalogue, which is `panel:read`, and cannot send). The route is a cookie session only: the console uses the stored token and, for people, a second factor, which an API token of Swellwright does not have. Step-up is checked in the handler, for the `user_data` class only, so that exploring the open operations does not ask for a code every few minutes (the route does not declare `stepUp`, and a test that lists the step-up routes is unchanged). A request counts against `SW_PANEL_CONSOLE_RATE_PER_MINUTE` (30) per user **after** it has passed every check, so requests that are refused before the panel is asked do not use the limit up.

Every call is `panel.console.request`: the actor, the operation id, the path **with its placeholders** (never the values), the **names** of the query parameters (never their values), the status, the time, how many values were masked, whether it was cut, the size, whether it was about people; never the body, never the token. A failure of the exchange is a record with `outcome: failure` and the error code. A refusal (blocked, write, people off, no `vault:reveal`) is `outcome: denied`, capped at twenty a user in ten minutes like `authz.denied`, because the chain is never pruned. The record of a read of the panel's own objects is a note: a read is not a change, and a record that cannot be written does not stop it. The record of a call about people is **strict**: it is written before the answer is returned, and a failure to write it fails the request, so what is about people is never delivered off the record. Tests mock the writer to prove both.

### The browser keeps its own history
The last 20 calls and named samples (at most 20, 256 KiB each) are in the localStorage of the browser and nowhere else; every access is guarded, and the page works without the storage. A call about people is kept without its values (a short UUID in the history would be the credential it is), and an answer about people cannot be saved as a sample. A sample can be saved only for the standard profile. Download writes the masked JSON the server returned. "Copy as curl" writes the same request with the token as `$PANEL_TOKEN` and the connected panel's address.

### The console
Panel > API console, in the panel's patterns (no counterpart exists in the panel, so it is built from the closest): the header card, a searchable list of the operations in a `SectionCard`, grouped by the panel's own tags in `NavLink`s (reads by default, all with a switch), a request card with a field for each parameter (typed, with the description of the panel under it and the server's complaints on the field), the notes of the panel's `Callout`, the response card with Monaco in the panel's theme (read only, JSON folding and search are Monaco's own) in a tab beside the schema, and a titled card with two `@kastov/mantine-react-table-open` tables for the history and the samples. `panel:read` opens the page; `panel:console` enables Send; what a role or the installation does not allow is shown with the reason. English and Russian.

### The computed configuration
The computed configuration of a profile was not kept and counted as a forced read, so a burst of `?refresh=true` used the budget it needed. **Decision: it stays uncached and has a budget of its own** (`SW_PANEL_COMPUTED_RATE_LIMIT_PER_MINUTE`, 30 a user a minute). It is derived from the profile, its squads and its nodes together, so nothing short of reading it says that a kept copy is still the one the panel would give, and a stale one is what a person comparing it with a node must not be shown; a cache keyed by the profile's hash would also have to know when squads change. The reads are cheap and rare. A burst of forced reads of other objects no longer blocks it, and asking for it over and over is still limited (429 `rate_limited`, `Retry-After`). Tests: after the refresh budget is spent it is read; its own reads do not use the refresh budget up; its own budget is limited, and per user.

## Consequences
- OpenAPI 0.27.0: three routes, new schemas, the permission `panel:console` in the catalogue and the role descriptions, five error codes, one audit action.
- Settings: `SW_PANEL_CONSOLE_USER_DATA` (false), `SW_PANEL_CONSOLE_RATE_PER_MINUTE` (30), `SW_PANEL_CONSOLE_MAX_BODY_KIB` (1024), `SW_PANEL_COMPUTED_RATE_LIMIT_PER_MINUTE` (30).
- The image copies `packages/remnawave/spec/` (1.6 MB).
- `maskSecrets` has two options; the typed views use neither and their output is unchanged, except that a `vmess://` or `ss://` payload in a string is now masked everywhere.
- No dependency was added.

## Not built here
Writes (phase 7: the plan, the approval, the hash check), the query parameters that are structured (the table state of the panel's pages), a console for an administrator session (the token the connection holds is an API token), several panels, a server-side history, saving answers about people, and API tokens of Swellwright calling the console (the route is a session only).

## Note of 2026-11-26: no redirect, templates and administrators' ids

- The console follows no redirect, not even one inside the origin: its policy (the operation that is allowed, the masking profile, the audit record) was decided for the path it asked for, and a redirect to another path would be answered under that decision. A redirect is `redirect_refused`.
- The console masks a shared structure as a whole if it exceeds the separate repeat-work budget or crosses masking contexts (ADR 0041). Headers are scrubbed before truncating values or normalizing the reported media type.
- The `encodedTemplateYaml` of a subscription template is decoded and masked like the typed read does it (and encoded again), so the console does not return the credentials of a template in base64; a clean YAML answer of at most 64 KiB is masked by its names, and its comments are dropped when it is rewritten; any other text answer (a parse error or warning, a repeated key, over 64 KiB or 300 anchors and aliases, an env file, a page) is shown as `[masked: unreadable document]`, since no rule can tell its names from its values; only a trivial text (one line without a `: ` or `=` separator: an error sentence, a number, `ok`) keeps the value rules. A large or malformed subscription template is shown fully masked in the same way, and so is every string value of an answer that holds a document which cannot be read (a string that holds a readable one is masked by its names). The exact panel token, and its base64 and URL forms, are taken out of the decoded answer, the names in it, the content type and the errors. `allowedIds` (the Telegram accounts allowed to sign in to the panel) is masked in every answer, like `allowedEmails`.
