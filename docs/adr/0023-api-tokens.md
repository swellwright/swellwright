# ADR 0023: API tokens

Status: accepted

## Context
The CLI, integrations and later the probes need to call the API without a browser: no cookie, no password, no authenticator. The design asks for tokens with scopes, an expiry and address restrictions, stored as hashes (`05-security.md`). The route registry has had a `token` authentication level since ADR 0012 that nothing implemented.

## Decision
- **A token is a bearer credential issued in the name of a user.** `Authorization: Bearer swt_<43 characters>` (256 random bits in base64url). Only its SHA-256 hash is stored, the token is in the answer of the creating call and nowhere else, and a list shows a short prefix (`swt_ab12`) so a person can recognise it. A dump of the database cannot be turned into a token.
- **It carries a subset of the permissions of its owner and never one that needs a fresh second factor.** A token has no second factor to give, so `users:write`, `vault:manage`, `vault:reveal`, `terminal:use` and the other `STEP_UP_PERMISSIONS` could never be used with it; the schema refuses them at creation instead of issuing a token that fails later. The server also refuses a permission the creator's role does not have (400).
- **What it may do is the intersection of what it carries and what the owner's role allows now**, computed on every request. Demote the owner and the token loses power at once; disable the owner and it stops; restore the role and the token works again. A token cannot be more powerful than its owner at any moment.
- **Routes opt in.** A new authentication level `any` means "a signed-in session or an API token". Routes that are for the browser (`session`: sessions, token management, password and step-up) never accept a token, and a route that needs a step-up cannot be `any` (a test would catch a mix, and the guard has nothing to elevate). Today the read routes accept tokens: whoami (`/auth/me`), users, roles, the audit log and its verification, the vault status and the list of secrets, sessions and tokens of everyone. A bearer header means a token and only a token: a bad one is refused (401) and never replaced by a cookie that happens to be there.
- **Limits.** An expiry is required: 1 to 365 days, 90 by default. At most 20 active tokens per user. The token may be restricted to addresses or CIDR ranges (IPv4 and IPv6; an IPv4 address that arrives as `::ffff:a.b.c.d` is read as IPv4); a request from elsewhere is refused. The address is the one the server trusts (`SW_TRUSTED_PROXIES`, ADR 0019), so behind a proxy the restriction is only as good as that setting.
- **Creating needs the permission `tokens:create` and a step-up**; the operator and the owner have it. **Listing and revoking your own tokens is open to any signed-in user** (your own credentials: you can always see them and kill them, like sessions in ADR 0022). `tokens:read` lists everyone's tokens (owner, auditor), `tokens:revoke` revokes anyone's with a step-up (owner). Revoking is idempotent and keeps the record; revoked and expired tokens stay listed for 30 days and are then removed the next time their owner creates one.
- **Wrong tokens are slowed down.** More than 30 wrong or malformed tokens from one address in ten minutes answer 429. A dead token (revoked, expired, wrong address) that keeps being used is recorded as `auth.token.denied` with the reason at most five times per window per token, because the audit chain is never pruned.
- **Recorded.** `token.created` (name, prefix, days, how many permissions, whether restricted), `token.revoked` (scope, user, name), `auth.token.denied` (reason, prefix). The value of a token is never in the chain. `lastUsedAt` and the address of the use are kept on the token, written at most once a minute. Audit records of actions done with a token name the owner as the actor; marking them with the token is for the first route that changes something with one.

## Consequences
- The CLI and integrations get a credential that is revocable, expires, can be narrowed to the machine it runs on, and cannot reach anything that needs a human at the keyboard.
- A token that is stolen is as powerful as its permissions until it is revoked or expires, from the allowed addresses only if it was restricted. The mitigation is the narrow grant, the expiry and the address list, not a second factor.
- `lastUsedIp` is the address of the last use at the time the record was written (once a minute), not of every use.
- Known limits: tokens are accepted on read routes only for now (the first mutating route that accepts one decides how its audit records name the token); no per-token rate limit beyond the address limit on wrong tokens; no scoping to a single resource (a permission is global, as for a session).

## Note of 2026-11-26: revocation with the credentials, and address families
- **A token ends with the credentials it was issued under.** A credential reset (from the console or the host command), a password change and disabling the account revoke every live token of the user in the same transaction as the change; the audit record of the change carries how many (`tokens_revoked`). Enabling the account again does not bring a revoked token back: the integration needs a new one. Demoting the owner still only narrows what a token may do, as decided above. This replaces "disable the owner and it stops; restore the role and the token works again" for disabling.
- **Issuing and revoking are serialized per account.** They take a PostgreSQL transaction lock of the account (`pg_advisory_xact_lock(7761240, hashtext(user id))`) that the reset, the password change and disabling take as well, and the creation reads the session, its elevation, the role and the count of live tokens again under it. A token cannot be issued to a session that one of those changes has already ended, and two simultaneous creations cannot both take the last of the 20 places.
- **An address list compares an address only with ranges of its own family.** `::/0` admits every IPv6 address and no IPv4 one; allowing both takes `0.0.0.0/0` and `::/0`. An IPv4 address mapped into IPv6 (`::ffff:a.b.c.d`, in any spelling) is IPv4, and a mapped range of `/96` or narrower is the IPv4 range it covers. A stored range that cannot be read matches nothing.
- **A proxy's own authentication is not a token.** On a route that takes a session or a token, only a `Bearer` header means a token (the scheme matched without regard to case); `Basic` from an `auth_basic` proxy in front of the console leaves the request to the session cookie.
- Tokens issued before this note are not revoked by it; whether to rotate them once is an operator decision (release notes).
