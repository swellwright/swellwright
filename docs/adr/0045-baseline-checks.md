# ADR 0045: Baseline checks: what a healthy server looks like, observed read-only over SSH

Status: accepted

## Context
The inventory (ADR 0034), the SSH layer and its detached steps (ADR 0035), servers over SSH and their facts (ADR 0037), commands (ADR 0038), the node installer with its `verify` action (ADR 0036) and the expiry of secrets (ADR 0042) are in place. Scenario N12 of the design ("Hardening baseline: check, drift, repair") and the "fleet audit in check-only mode" of the roadmap ask for the next step: connect to the servers of the inventory, collect a fixed set of observations, compare them with what a healthy server of that kind looks like, and say where a server has drifted. This slice is **check only**: it changes nothing on a server and nothing in the panel. Repair (an installer step per difference, with approval) is phase 4.

Two things the slice must not do. It must not make "what is healthy" a property of the code of one infrastructure: the owner's own baseline is instance data. And it must not give a way to run arbitrary text on a server under a name that sounds harmless: observations are a closed catalogue of fixed fragments, and what a person writes is only a comparison.

## Decision

### A baseline is data: a document of checks over a closed catalogue
A **baseline** is a named, versioned document (YAML or JSON, validated by one Zod schema, `packages/contracts/src/baselines.ts`):

```yaml
schema: 1
checks:
  - id: ssh.root-login
    title: Root cannot log in with a password
    category: ssh              # one of 14 fixed categories
    severity: medium           # high -> fail, medium and low -> warn
    observe: { kind: sshd.effective, field: permitrootlogin }
    expect: { in: [no, prohibit-password, forced-commands-only] }
    remediationHint: Set PermitRootLogin no.
```

`observe.kind` is one of **31 observation kinds** of a closed catalogue; `field` names one of the fields that kind reports (a field is a text, a number, a boolean or a list of texts); `expect` has exactly one of **twelve comparators**: `equals`, `notEquals`, `in` (for a list: every entry is allowed), `matches` (a regular expression, at most 200 characters, no back reference and no repeated repeating group), `atLeast`, `atMost`, `contains`, `notContains`, `absent`, `present`, `versionAtLeast` (numbers compared part by part, so `6.8.0-36-generic` is at least `6.8`), `ageLessThan` (seconds against `30m`, `12h`, `7d`). The document is checked as a whole before it is saved: unknown keys, repeated ids, an unknown kind or field, a parameter the kind does not take or that does not match its pattern, a comparator that does not fit the type of the field (`atMost` on a list), a pattern that could run away. Every problem comes back with its path and, when the text is YAML, its line and column (`POST /baselines/validate`; the console underlines them in the editor). Aliases and anchors are refused (a few of them expand to a very large document).

The catalogue (`OBSERVATION_KINDS`, served by `GET /baseline-catalogue`) covers: `os.release`, `kernel` (running, newest installed, reboot pending), `uptime`, `time.sync` (service, synchronised, offset from chrony, and the skew against the clock of this server, which is the one field made here and not on the server), `disk.usage` (space and inodes of a path), `memory`, `updates.pending` (counts from the lists already on the disk, never fetched, and their age), `updates.auto` (unattended-upgrades), `systemd.failed`, `service.state` (one unit), `port.listener` (one port: addresses and program), `ports.public` (every non-loopback listener), `ufw.status`, `iptables.chain` (by default `DOCKER-USER`), `fail2ban.status`, `sshd.effective` (14 settings of `sshd -T`), `ssh.keys` (the fingerprints of `authorized_keys`, never a key), `sudoers` (drop-ins and `NOPASSWD` subjects), `users.login` (accounts with a shell, user id 0, empty passwords by name), `sysctl.value`, `docker.engine`, `docker.container` (state, image tag and id, restart policy, health, the **names** of its environment variables and the value of four that are not secret), `nginx.config`, `haproxy.config`, `cert.file` (subject, issuer, days left, mode, owner), `file.stat`, `file.hash` (the SHA-256 of a file, never its content), `certsync.account` (a restricted `rrsync` key), `installer.journal` (what the installer's journal says about its last `verify`), `http.local` (a status code, loopback or the machine's own address) and `dns.self`. A kind with a **presence field** (`exists` or `installed`) treats a thing that is not there as a miss of the expectation (a `fail` or `warn` by severity), not as "could not be observed".

Parameters are the only free text, and they are not free: each has a pattern in the catalogue (a path is `/` followed by plain characters, no `..`; a port is 1 to 65535; a unit is a full unit name; a host name is a host name). The pattern is checked when the document is saved, again when the plan is built, and a third time by the shell script on the server, which treats the value as data in any case (see below).

### One read-only script, one SSH session, one detached step
`apps/api/src/baseline/observe.sh` (POSIX `sh`, tested under dash) is the only thing that runs on a server. It reads a **plan** on its standard input, one observation per line (`INDEX TAB KIND TAB NAME=VALUE ...`; checks that ask for the same kind with the same parameters share one observation), and prints a document in a fixed format. Its header promises, and a test enforces by text and by running it, what a read-only script promises: it writes no file, changes no setting, starts and stops nothing, installs nothing, reads the **names** of the environment variables of a container but never their values (except four that are not secret), the fingerprints of authorized keys but never a key, the hash of a file but never its content, sends nothing beyond the machine (a request goes to loopback or to the machine's own address; the machine's own name is resolved once), runs every external program under `timeout` and cuts every list and every line. `set -f` is on, so a value that holds a star stays a value; the one `eval` assigns a parameter from a variable and cannot run what the value holds.

The output is parsed **strictly** and cannot be forged by what it reports. Every line of an observation begins with `| ` (the script prefixes them through a filter), and a marker is a line that begins `@@swb `, so a value that looks like a marker, from a file name or a config, is a value. Values are one line (control characters are removed, 400 bytes at most). A missing marker, an observation announced twice or one that never ends is an error and not a guess; output that is not the script's (a banner, a shell error) is `observe_unreadable`. The parser reads the fields of an observation from the catalogue itself: a boolean is `yes`/`no`, a number must be a number, a list is the same field repeated and capped, and an optional list (`emptyPassword`) is `null` when the script could not look and `[]` when it looked and found none.

The runner (`CheckRunner`) takes a queued run, tries the access entries by priority (a wrong password is tried once per entry and never again; the first contact needs the pinned host key and applies the address policy, as ADR 0037 says), and on one connection starts the script as a **detached step** (ADR 0035, id `swb-<run id>`), follows it by polling and removes the step directory. It runs as root, through the stored sudo secret when the login is not root, or, when sudo does not work, as the login: then everything that needs root says `denied` and the run records `collectedAs: user`. The step directory and the script's output are the only things written to the server.

### Runs, results, drift
A **check run** (`CheckRun`) copies what it needs from the baseline (name, version, the hash of the document), so it stays readable after the baseline is edited or deleted. Its states are `queued`, `running`, `completed` (the server was observed, whatever the results) and `error` (it could not be observed, with the code of why: `host_key_mismatch`, `host_key_not_pinned`, `no_access_entry`, `ssh_auth_failed`, `ssh_connect_failed`, `ssh_timeout`, `secret_expired`, `vault_sealed`, `check_timeout`, `observe_lost`, `observe_unreadable`, `baseline_deleted`, `interrupted`, ...). A run that cannot observe the server has no results: nothing is invented.

A **result** (`CheckResult`) per check: `pass`, `warn`, `fail`, `error` (could not be observed: needs root, the tool failed, timed out; an unknown is never a pass) or `skipped`, the value that was observed (bounded: 50 list entries, 400 characters), what was expected, one sentence that says why it did not pass and the remediation hint. A missed expectation is a `fail` for a `high` check and a `warn` for the others.

The **drift** between two completed runs of one server (`GET /baseline-runs/{id}/diff?against=previous|<id>`, a pure function in `diff.ts`): checks that got worse or better (ranked pass, warn, error, fail; a skipped check counts as a pass), checks whose observed text, flag or list changed, and checks that exist in one baseline only; a number that moves while the check passes (the use of a disk) is not a change, one that moves while it fails is. Each completed run stores how many checks changed since the previous one and whether it got better or worse (failures first, then errors, then warnings), which is what the fleet table shows without reading two runs. "No differences" is a result (`identical: true`).

### One run per server, a cap on the fleet, retention
Creating runs is one transaction under a per-server advisory lock, so two requests that arrive together cannot both queue the same server (`already_running` is reported in `skipped` by the fleet form and 409 by the single form). Queued runs are taken `SW_CHECKS_PARALLELISM` (3) at a time across all requests. After a run ends the newest `SW_CHECKS_KEEP_RUNS` (30) runs of that server stay and the rest are deleted with their results. A run that was queued or going on when the process stopped is closed as `error` / `interrupted` at start.

### Assignment: by server or by tag
A baseline applies to servers named in its assignment and to servers that carry a tag named in it (`PUT /baselines/{id}/assignments`). A server has at most one baseline of its own and a tag belongs to at most one baseline, so what applies to a server is never ambiguous: a baseline named for the server wins, otherwise the baseline of a tag it carries (the first by baseline name when it carries several tags that have one), otherwise none. A server that was named for another baseline, or a tag, is **moved** to the baseline that names it now, which the audit record counts. (The design mentioned assignment "by flavor"; the inventory has no flavor, so tags are the way to say "all nodes".)

### Versions are immutable; built-ins are files of the build
Every saved text is a new version (`BaselineVersion`, with the text as written, comments included, and the parsed document with its SHA-256); an older version can be read and compared, never changed; a stale edit (`expectedVersion`) is 409. Two **built-in baselines** ship as YAML files of this build and are made and kept current by name at start (a changed file adds a version, a baseline of the instance with the same name is never touched): `linux-generic` (updates, time, resources, SSH, accounts, firewall, 28 checks) and `node-selfsteal` (those, and the facts the node installer's `verify` checks: services, the node container and its `SECRET_KEY` and `SNI_VERIFICATION`, the ports and the loopback-only default site, the `DOCKER-USER` rules for the node API port, what the node answers to a foreign SNI, the certificate and the certificate receiver, 64 checks). They cannot be edited or deleted; copy one to change it. Nothing about an installation is in them (the node baseline uses the installer's own defaults, container `remnanode`, port 62050, `/opt/certs`, and says so). `examples/baselines/` holds an example with placeholders for a fleet of your own.

### Permissions, audit, step-up
Reading (baselines, the catalogue, runs, results, diffs, the fleet view, validation) is `servers:read` and is open to API tokens. Starting a run is `servers:exec`, which is a step-up permission (ADR 0017, ADR 0038): the routes need a fresh authenticator code and are not open to tokens, because they connect to servers and run a script there. Editing, creating, deleting and assigning baselines is `servers:write` **and** a fresh code. The schedule needs no person. Audit actions, all strict (same transaction as what they record) and without a single observed value: `baseline.run` (who, how many servers, which baseline and version, the trigger), `baseline.run.finished` (no actor: the runner closes it; the counts, the state or the error code, the duration), `baseline.version.created` (name, version, number of checks, the hash; not written for the built-ins, which are the build's content and are made at start before anyone can sign in: they keep their `source`, their hash and a note, and a run copies the hash), `baseline.assigned` (how many servers and tags, how many were moved) and `baseline.deleted`. The results themselves are not in the audit chain: they are records of the check, and they hold no secret.

### The schedule
`SW_CHECKS_INTERVAL_HOURS` (0, off, by default). The job ticks every quarter of an hour at most; a server is due when its newest run (of any trigger) is older than the interval, and a server that was never checked becomes due at a point of its own within the first hour (a hash of its id), so a fleet is not checked in one burst. It does nothing while the vault is not open, leaves out a server that has no pinned host key, no access entry, or no access entry whose secrets have not expired, and does not start a round that is running. The clock is injectable (`AppOptions.checksClock`), and so is `queuedAt`, so the tests move time instead of waiting.

### The console
Fleet > Baseline (`/dashboard/fleet/baseline`): the panel's header card (refresh, Baselines, check every server), the strip of four metric cards (servers checked, failing, with warnings, last check and the servers that could not be reached), the panel's `@kastov/mantine-datatable` of the fleet (server, baseline and whether a tag assigned it, last check, result chips with counts, trend arrow, run now and open), a drawer per server (summary, drift since the previous check, results grouped by category in an accordion with the status chip, what was seen and what was expected, the hint, history of earlier checks; the error and what to do when the server could not be reached), a dialog to start checks (all, or chosen servers, optionally against one baseline), the baselines drawer (list, an editor in Monaco with the problems underlined and a validation line, versions, assignment by server and tag, copy, delete, and the catalogue as a reference) and a card in the server's own drawer. The Overview gets a "Baseline" metric in its own block. Texts are English and Russian.

### Tests
The catalogue (patterns, defaults, presence fields, hostile values), the comparators, the document (every rule above, YAML errors with lines), the plan, the parser against a real output of an Ubuntu 24.04 server and against hostile output (binary, invalid UTF-8, huge, forged markers, duplicates, missing delimiters, truncated), the observation script **in a real shell** against stand-in commands (as root and not as root, no secret in the output, hostile parameters create nothing, forged markers in values, unknown kinds), and the whole run against the stand-in SSH server of ADR 0038 (one session per run, the step directory removed, one run per server at a time, the cap on parallelism, retention, drift between runs, every error code, expired secret, sealed vault, the permission matrix, step-up on every route that needs it, the audit records, the schedule with an injected clock, built-ins seeded). A hygiene test fails the build for an address or domain in the shipped files that is not a documentation value.

## Consequences
- A fleet can be checked against a baseline from the console and the API without a line of code on the servers, and with no change on them. A check is one SSH session and about ten seconds on a real node (measured: 61 checks, 11 s).
- The owner's real baseline is a baseline of the instance (a copy of the node one with its values), never part of the repository.
- The catalogue is closed on purpose: a new observation is a new function in `observe.sh`, a new entry of the catalogue and a golden test, reviewed like code. Plugins cannot add observations in this slice.
- The script reads files as root (`/etc/shadow` for empty passwords, `/etc/sudoers`), but prints only what the catalogue says. A bug in the script could print more; the tests run it against secrets in files and in a container's environment and assert the output holds none.
- `nginx -t` and `haproxy -c` are the usual read-only checks of a configuration; they open the log files of the configuration and, like the installer's own `verify`, are the closest this slice comes to touching a server.

## Not built here
Repair (a fixing step per difference, a plan, approval), running the installer's `verify` itself (it appends to the installer's journal and takes its lock, so it is a script a person runs, not an observation; `installer.journal` reads what the last `verify` found instead), baselines contributed by plugins, an `extends` between baselines, assignment by a condition on the facts, alerts on a regression, a baseline per operating system, windows and a quota of concurrent checks (phase 4 with the schedules of the engine), and a check that follows a server through a reboot.
