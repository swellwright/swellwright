# ADR 0041: The connection to a Remnawave panel and the read model of its objects

Status: accepted

## Context
Phase 3 is "panel integration" (`docs/en/design/11-roadmap.md`): Swellwright connects to a Remnawave panel and reads all of it, and on that the snapshots and diff, the convention linter, the impact calculator, the API console and the dashboard are built. This slice is their foundation: a typed client that can only read, the connection with its credential in the vault, normalised views of the panel's objects with every secret masked, and the console pages that show them. The design is `docs/en/design/04-remnawave-integration.md` (compatibility, tokens, the "panel as source of truth" model), `02-data-model.md` (`PanelConnection`), `05-security.md` (panel tokens) and `03-scenarios.md` (P01). The panel's frontend is the model for the pages (ADR 0032, 0033).

What the frozen API description of the panel (3.4.11, kept in the repository) shows, and the design had assumed otherwise in two places: the lists this slice reads are not paged (only the billing history and the user list are), and `GET /api/tokens` (the list of API tokens) is forbidden to an API token ("admin JWT only"), as are creating and deleting them. The API tokens of the panel are signed tokens (JWT) with an expiry claim.

## Decision

### A client that cannot write
`packages/remnawave` exposes `PanelReader`, an interface of reads (`nodes()`, `hosts()`, `configProfiles()`, `configProfile(uuid)`, ...), and `PanelClient`, its only implementation. There is no way to build a request that is not a GET: every endpoint is declared with the literal method `'GET'` (`PANEL_ENDPOINTS`), the one function that sends a request takes an endpoint, and the transport only has `get`. Three tests say so independently: the prototype of the client holds only the allowed method names and none that starts like a write; the type of `PanelReader` has no `post`, `delete`, `create...` (a `@ts-expect-error` for each), and the sources of the package contain no other HTTP verb; and a panel that records what it is asked sees only GET whatever the client is made to do. Writes arrive in later phases through a separate type that has to be asked for by name and goes through approval (`04-remnawave-integration.md` section 1).

### The transport: `node:https`, not `fetch`
The brief said "use `fetch`". `fetch` cannot take a certificate authority of its own, check the address a name resolved to at the moment of connecting, or set a connect timeout without a second HTTP library (`undici` as a dependency, whose `Agent` the built-in `fetch` accepts only by luck of versions). The transport (`transport.ts`) is therefore a small layer over `node:https` and `node:http` with a `lookup` of its own: it resolves the name, runs the address guard on **every** answer, and hands only checked answers to the socket, so a name cannot be pointed at an internal service after the check (DNS rebinding); an address literal in the URL is checked before connecting. The transport is injectable, and the tests run the real one against an in-process panel and, for TLS, against `https` servers with certificates made by the `openssl` command (skipped, with a message, where it is missing).

Limits, all with defaults and all configurable (`SW_PANEL_*`): 15 s per request and 5 s to connect, a response cap of 16 MiB (a declared length over it is refused before reading, a stream is cut when it passes it, a compressed one is decoded under the same cap), four requests in flight, three tries for a GET, backoff of 250 ms doubling to 4 s with jitter, `Retry-After` obeyed up to 10 s and reported at once beyond that (`PanelRateLimitedError` with the seconds), no retry for 401, 403, 404, other 4xx, a TLS failure, a refused address or a timeout (a slow panel is not made faster by asking again), a retry for a reset, a refused connection, 429 and 5xx. Redirects are followed inside the origin only (three at most); one that leaves it is `PanelUnavailableError` with `reason: redirect_refused`, and the `Authorization` header never goes anywhere but the origin of the panel. The client sends `accept-encoding: identity` and its own short user agent, nothing that identifies the installation.

TLS is verified (TLS 1.2 and up, the name checked against the certificate) unless told otherwise, and "told otherwise" is two things: a certificate authority of **one** connection (`trustedCa`, public PEM, stored with the connection and added to the system roots), and `SW_PANEL_ALLOW_INSECURE_TLS`, an installation-wide switch that is off by default and never set by the wizard. Plain `http:` is refused unless `SW_PANEL_ALLOW_HTTP` is on **and** the host is a loopback or private address (or `localhost`); a name is judged at connect time by what it resolves to, so `http://panel.example.com` is never accepted.

### The address policy is the SSH one
The panel's address goes through the same `validateTargetAddress` as an SSH target (ADR 0037): loopback refused unless `SW_PANEL_ALLOW_LOOPBACK`, private ranges and host names allowed by default (`SW_PANEL_ALLOW_PRIVATE`, `SW_PANEL_ALLOW_HOSTNAMES`), link-local and cloud metadata addresses never. The API applies it to the URL when it is typed (400 for a shape that is wrong, 409 `address_not_allowed` for a host the policy refuses) and hands the same function to the client as its address guard, so the check runs again at connect time on what a name resolves to. `packages/remnawave` itself does not depend on the SSH package: the API owns the policy and passes a function.

### Contracts: our own tolerant schemas, the panel's package as a cross-check
`@remnawave/backend-contract` 3.4.11 is the panel's own Zod description of its API (AGPL-3.0-only, compatible, ADR 0011; the tarball was read before first use, ADR 0009: pure schemas and route constants, no install scripts, no network, filesystem or process code). It is **not** used at run time. It pins `zod` 4.4.3 exactly (a second copy beside ours), and its schemas are exact for every field of every object, so a patch release that adds an enumeration value, a country or a field would make a whole list unreadable, which is wrong for an inventory tool that should degrade, not stop. The schemas of the client (`schemas.ts`) describe only the parts the adapters read, drop the fields they do not know (never kept in memory), keep an enumeration as a string, and make optional what the adapters can do without. A failure is `PanelContractError` naming the endpoint (`nodes.list`) and the path of the first bad field (`response[3].port`); the message repeats the Zod message (types, not values) and never a value from the body.

The package is a **devDependency** and a test partner: the fixtures of the fake panel are validated against its schemas (so the fake cannot drift from the panel), and the paths of the client are compared with its route constants. The frozen OpenAPI description of 3.4.11 (`packages/remnawave/spec/`, 162 paths, a generated public file with no instance data; one example address in a description is allow-listed for the hygiene check) is the reference for three more tests: every path and method the client uses exists in it, the schemas of the client accept samples generated from it with every field and with only the required fields and nulls (so a schema that demands more than the description promises fails the build), and the path parameters match. The future `oasdiff` job compares this file with a new release.

### Versions and capabilities
`probePanel` asks `GET /api/system/metadata` first (it is also the proof that the token works), judges the version against the window, and for a supported version reads each kind of object once. The window is the 3.4 line (`3.4.x`: every patch release): the description is the one of 3.4.11 and a patch release keeps it. The design says "current and previous minor", and the previous one (3.3) was not tested against anything, so it is not claimed; when 3.5 arrives it is added after the descriptions are compared, and 3.4 stays while it is the previous one. A newer or older minor is `unsupported` with a reason (newer than... older than...), not a crash, and nothing more is read from it. The result has, per resource, `ok`, `denied` (403: no scope) or `failed` (with the code); a 401 in the middle (the token was revoked a moment ago) makes the whole probe fail; what was read is kept so that the first pages need no second request.

### Views, hashes and masking
The adapters turn DTOs into the views of `@swellwright/contracts` (`PanelNodeView`, `PanelHostView`, `PanelConfigProfileSummary`/`View`, squads, templates, settings, snippets, node plugins, infra, API tokens). A view is what Swellwright knows about an object; a change of the panel moves one adapter. Node views carry the state worked out from the three flags, versions, the profile and its active inbounds, tags, provider, traffic and consumption fields; host views carry every field of the panel's host drawer; the opaque parts (mux, sockopt, XHTTP extra, final mask, the mappers, a profile's configuration, a template, a snippet, a plugin's configuration) are JSON after masking.

**Masking** is one function (`maskSecrets`) and the only way an opaque value gets into a view. It is a deny-list, because an Xray configuration is free-form and an allow-list would hide most of what an administrator reads: a key whose normalised name (case, `-`, `_` ignored) says it is a secret or contains `password`, `secret`, `privateKey`, `passphrase`, `apiKey`, `accessToken`...; the ids, logins and passwords of the items of `clients`, `users`, `accounts`, `peers` and `proxies`; a VLESS `decryption` that is not `none`; an `auth` that is not a plain mode word; the value of a `{name, value}` pair whose name is a sensitive header (`Authorization`, `Cookie`, `X-Api-Key`, ...); a `key` without a `value` beside it; and, wherever a string is, PEM private keys (every flavour, also unterminated), credentials in URLs (`scheme://user:pass@`, and the secret parameters `sid`, `password`, `token`, `key`, `psk`, ...), JWTs, bearer tokens, and a JSON document inside a string (read, masked, written back). Anything beyond 64 levels is replaced as a whole: it fails closed. A list under a secret name keeps its shape (how many short ids there are is visible), prototype keys are not special, and the input is not changed. What a deny-list cannot know is a secret under a name nobody predicted and without a shape that gives it away: the tests feed it hostile structures, the console says masking is best effort, and the route that carries a configuration needs `panel:read` only.

A mask is `[masked]`, or `[masked:1a2b3c4d]` when a key is given: the first four bytes of an HMAC-SHA256 of the value under a key derived from `SW_AUTH_KEY` (HKDF, purpose `swellwright:panel-mask:v1`). The same value gives the same fingerprint, so a REALITY key that is rotated shows as a change of the object and of its hash, and nothing about the value can be learned from it without the key (a short id of eight characters is brute-forced from an unkeyed hash in no time). The key is the authentication key, so a rotation of that key changes every fingerprint and every hash once; in development, where the key is made at start, hashes change on restart.

Every object has `hash`, the SHA-256 of the canonical JSON (sorted keys, no whitespace, `-0` written `0`) of its masked **configuration**: runtime state is left out (a node's online state, versions, counters, host facts, `updatedAt`), so a hash changes when somebody edits the object and not when a node restarts, and a profile's hash covers the masked configuration whether or not the list carries it. A snapshot (the next slice) stores what it needs to restore from, which is the unmasked object, encrypted: it will read it through a separate method that no route exposes; the hash is what compares snapshots cheaply and without a key.

### The connection
`PanelConnection` (one row for now, nothing prevents several): `baseUrl`, `tokenSecretId` (a vault secret of kind `panel_token`, **restrict** on delete, like server access), `state` (`connected`, `degraded`, `unreachable`, `unauthorized`, `unsupported`; `unconfigured` is the absence of a row), `panelVersion`, `capabilities` (JSON, per resource), `trustedCa`, `tokenExpiresAt`, `lastCheckedAt`, `lastErrorCode` and `lastErrorMessage`, `createdById` (no foreign key, like the audit chain). The state is worked out from a probe: `unauthorized` when the panel refuses the token (or the token has no scope even for the version), `unsupported` when the version is outside the window or the panel answers in an unknown shape, `unreachable` when it does not answer, `degraded` when it works but the token cannot read some resource or one failed, `connected` otherwise. The list of API tokens is not counted: no API token can read it, which is not a defect of the connection. At the time of looking, a token about to expire also makes a connected panel `degraded` (nothing is written for that).

Vault changes: `readForPanel(id)` (kind `panel_token`; not a reveal; 423 while sealed), `requireOpen()`, `createWithin(...)` (create a secret and let the caller do more in the same transaction), and deleting a secret that a connection uses is 409 that names the connection and its address (the foreign key is the last word).

### Routes and codes
`GET /panel/connection` (`panel:read`, never the token), `PUT /panel/connection` (`{ baseUrl, tokenSecretId, trustedCa? }`, `panel:write`), `PUT /panel/connection/with-token` (the wizard path, below), `POST /panel/connection/test`, `DELETE /panel/connection` (all `panel:write`), `GET /panel/overview` and one read route per kind (`nodes`, `hosts`, `config-profiles` and `/{uuid}`, `/{uuid}/computed-config`, `internal-squads`, `external-squads`, `subscription-templates`, `subscription-settings`, `snippets`, `node-plugins`, `infra`, `api-tokens`; all `panel:read`, `auth: any`, so a Swellwright API token with that permission reads too). Writing routes are `session` only. Connecting stores a credential reference and makes the API call out, hence `panel:write`, with no step-up except for the wizard path.

Connecting asks the panel **first**; nothing is stored when it refuses. Testing is a result: a panel that does not answer is `200` with `ok: false` and the state, and the state is saved. Failures of a read map to codes of their own: `panel_not_connected` 409, `panel_unsupported_version` 409 (a connection found to run another version answers every read with it), `panel_unauthorized` 502, `panel_forbidden` 502, `panel_unreachable` 502, `panel_contract_changed` 502 (details: endpoint and field), `panel_timeout` 504, `panel_rate_limited` 429 with `Retry-After`, `address_not_allowed` 409, `vault_sealed` 423, and 404 `not_found` for a profile the panel does not have (a 404 on a list means "this is not the panel's API" and is `panel_contract_changed`). A read that fails because the panel is down or refuses the token also moves the state (`unreachable`, `unauthorized`), and the next read that works moves it back; each change is a note in the audit chain.

### The wizard (P01), the token path
The panel's API tokens cannot be created with a token, so the wizard supports **pasting** an existing read or full token: `PUT /panel/connection/with-token` takes the address, the token and the name of the new secret; the panel is asked with the token first, and only if it answers is the token sealed into the vault (kind `panel_token`) and the connection saved, **in one transaction** (a taken name leaves the old connection and creates nothing). It needs `panel:write`, `vault:manage` (checked in the handler, since a route declares one permission; an operator, who has `panel:write` but not `vault:manage`, gets 403 and is told to ask an owner for the secret) and a fresh authenticator code, as every route that writes a secret.

Creating the token from a one-time administrator login (`POST /api/auth/login`, `GET /api/tokens/scopes`, `POST /api/tokens`) is **not built**. The endpoints are in the description and the profile mapping of the design (`readonly`, `core`, `probe`, `full`) is clear, but the login can be a password, a passkey or an OIDC flow depending on the panel's settings, the call creates a credential on the owner's production panel, and a flow that cannot be tried against anything but that panel is not something to ship untested. It is the next step of the wizard, with the JWT in memory for one call only, `panel:write` and a step-up, the scopes of the chosen profile, an expiry in days that is required, and an answer that says exactly what was done.

### Token expiry
The list of API tokens is unreadable with an API token, so the days left come from the token itself: it is a signed token with an `exp` claim, read **without checking the signature** (this is a date to show, the panel decides whether the token works), stored as `tokenExpiresAt` when the connection is made, shown with `daysLeft` and an `expiryWarning` from 14 days before, in the connection card and the overview, and as the warning `token_expiring` (the state looks `degraded`). A token with no readable expiry shows none; nothing is guessed. `GET /panel/api-tokens` exists and reads the list when the panel allows it (an administrator session would; a token gets 502 `panel_forbidden`, and the capability says `denied`).

### The memory of this server, joining, refresh
Per kind, for the current connection, for `SW_PANEL_CACHE_TTL_SECONDS` (15; 0 keeps nothing): what the adapters returned, masked. `?refresh=true` asks the panel again and counts against `SW_PANEL_REFRESH_RATE_LIMIT_PER_MINUTE` per user (429 with `Retry-After`); requests that arrive together for a kind share one request to the panel, with or without a memory; the computed configuration is not kept and counts as a forced read (changed by ADR 0046: it is still not kept, but it has a budget of its own, `SW_PANEL_COMPUTED_RATE_LIMIT_PER_MINUTE`, so a burst of forced reads of other objects does not block it). A connect, a test and a disconnect empty or reseed the memory. **The token is never in it**: a client is made for one piece of work with the token read from the vault for that work, and closed after it; a test looks for the token in the cache object. Connecting and testing share their own limit (`SW_PANEL_TEST_RATE_LIMIT_PER_MINUTE`).

### The background check
`PanelMonitorService` runs the same probe on a timer (`SW_PANEL_CHECK_INTERVAL_MINUTES`, 5; 0 off) while a panel is connected and the vault is open. It updates the state and the capabilities and writes **only when the state changed** (`panel.state.changed`, a note without an actor, `from`, `to`, the error code); a sealed vault or a vanished token skips the round silently. A round that is still running is not started again, the timer is unreferenced, and shutdown waits for the round.

### Audit
`panel.connected` (strict, same transaction; outcome `success`, or `failure` as a note for a refusal; address, version, state, secret id, whether it replaced one, whether it has its own authority), `panel.disconnected`, `panel.tested` (outcome, state, code, latency) and `panel.state.changed`. Reading is not audited per call: that is noise, and what was read can be read again. No record holds a token, an object from the panel or a masked value; tests scan every response, every record and the log for the fake panel's secrets and the tokens.

### The console
The Panel section of the navigation is enabled for what this slice delivers: **Connection** (the wizard and the status card), **Profiles**, **Hosts**, **Squads** (internal and external), **Templates**, **Snippets** and **Node plugins**, with **Nodes** under Fleet; subscription settings, infra billing and the API console stay disabled (`planned`). Each page is the read-only counterpart of the panel's own page for the same objects, built from the ported components and the panel's source (ADR 0032, 0033): inputs disabled, no footers, the Hosts and Nodes datatables with the panel's columns and filters, the profile and template viewers in the bundled Monaco (read only, the masked JSON as it is: the console never tries to unmask). The Overview page gets a block of metric cards (version, nodes up, problem nodes, health, hosts, profiles, users as counts, token expiry), or a card that links to the wizard when nothing is connected. Every panel page shows the panel's empty state with a button to the wizard while nothing is connected, and the failed-load card with the text of the error code (and a link to test the connection) when a read fails. The wizard hides nothing a role cannot do but disables it with the reason: `panel:write` for connecting, testing and disconnecting, `vault:manage` and a code for pasting a token.

## Consequences
- A panel can be connected from the console, with its token in the vault, and every object this release knows can be read without a secret leaving. A change of the panel's API inside the 3.4 line degrades one resource, with the endpoint and the field named, instead of the whole view.
- OpenAPI 0.24.0; `packages/remnawave` gets its first code and a fake panel (`pnpm --filter @swellwright/remnawave run fake-panel`) that the console can be tried against; the image carries the package.
- The user counts come from `GET /api/system/stats` (totals and status counts); no user is read.
- The unmasked objects exist only inside one request. The snapshots of the next slice need a privileged raw read, which does not exist yet.

## Not built here
Creating a token from an administrator login (above), several panels (the model allows them; the routes say "the connection"), writes of every kind, snapshots and diff, the convention linter, the impact calculator, the API console, users beyond counts, node integrations, shared lists and subscription page configs, a check against the `oasdiff` report, panel cookies or secret paths in front of the panel, and `extraHeaders` for a panel behind a proxy that wants them.
