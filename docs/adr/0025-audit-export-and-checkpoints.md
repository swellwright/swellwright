# ADR 0025: Exporting the audit log and checkpoints

Status: accepted

## Context
ADR 0015 made the audit chain append-only and hash-linked, and said so honestly: someone who can write to the database can rewrite every hash, and a cut-off tail is only visible against a head noted outside the database. It left "checkpoints and export" for later. The design (`05-security.md`, section 8) asks for export and integrity verification. Without them the chain protects against careless edits and not against the attacker the design worries about most: the one who has the database.

## Decision
- **Export in a form that can be checked elsewhere.** `GET /audit/export?from=&limit=` returns pages (up to 5000 events, 1000 by default) oldest first, each event with every field its hash covers and with its hash. A file is a header line `{"format":"swellwright-audit-export","version":1}` followed by one event per line; the console assembles it from the pages and the CLI can do the same. Needs `audit:export` (owner and auditor) and a fresh second factor: a copy of the whole log is a lot to hand over. Every page is recorded (`audit.exported`: where it started and how many events), never its content.
- **Offline verification.** `verifyExportText` recomputes every hash, link and number of a file with the same code the server uses, and reports the first problem and its place; `node dist/admin.js audit-verify <file>` runs it without a database (and without a server: copy the file to a machine you trust). A file that starts later than event 1 is checked from its first event on. A changed field, a removed, swapped or inserted event and a changed link are found.
- **Checkpoints are the answer to "a database writer can rewrite everything".** `POST /audit/checkpoints` (permission `audit:verify`, so a token can do it from a cron job) returns `swa1.<seq>.<hash>.<time>.<signature>`: the head of the chain, when it was noted, and an HMAC over both made with a key derived (HKDF) from `SW_AUTH_KEY`. That key is not in the database. The administrator stores the text **somewhere else**. A rewritten history, even one rewritten consistently with every hash recomputed, no longer has the event the checkpoint names with the hash it names, and the attacker cannot produce a new checkpoint for the new history without the key. A cut-off tail leaves a valid chain but not the event the checkpoint names.
- **Checking a checkpoint** (`POST /audit/checkpoints/verify`, or `audit-verify <file> --checkpoint <text>`): the signature (`not_ours` when it is wrong: another instance, or made up; the server then repeats nothing the text says), the event at that number (`event_missing`: the log is shorter than the checkpoint says), its hash (`hash_differs`: history was rewritten), and the chain from the start up to it (`chain_broken`); then `ok` with how many events came after. A failed check is an answer, not an error, and is recorded either way (`audit.checkpoint.verified`, with the result). The file form also checks that the file reaches the checkpoint and agrees with it; without `SW_AUTH_KEY` it says that the signature was not checked.
- **From the host, too.** `node dist/admin.js audit-checkpoint` notes the head with the instance key (it refuses when `SW_AUTH_KEY` is not set: a checkpoint nobody can check later is worse than none) and prints it, for a cron job that mails or stores it elsewhere. The creation is recorded without an actor.

## Consequences
- The honest limit of ADR 0015 becomes a practice instead of a caveat: note a checkpoint regularly (daily is cheap) and keep the text off the server; the log is then tamper-evident against an attacker who has the database but not the process environment.
- An attacker who has both the database and `SW_AUTH_KEY` can forge checkpoints made after they took the key; checkpoints noted before that still catch the rewrite of anything older. Rotating `SW_AUTH_KEY` invalidates all earlier checkpoints (they become `not_ours`), so keep the old key's text if they matter.
- The export is paged JSON and the file is assembled by the client: no streaming endpoint is needed, and a huge log is a loop of pages. The server does not keep exports.
- Not part of this step: signed exports (an export file proves its own consistency, and its head can be compared with a checkpoint, but the file itself is not signed), an external timestamp, scheduled checkpoints inside the server (a cron job calls the command or the API with a token), retention (the log is never pruned).

## Note of 2026-11-26: an export ends where it began
- **A multi-page export is bounded by its first head.** Every page writes an `audit.exported` event, so a walk that only follows `nextFrom` chases a head that keeps moving (at `limit=1` it never ends). The first page answers `head`; every following page sends `from=nextFrom&through=<head.seq of the first page>` and is cut at that event, so the file ends exactly there. `through` must name an event of the log (400 otherwise). A client that leaves it out still reads up to the current head, as before. The console sends it.
- **The checkpoint event of a file is found by parsing.** The offline check looks the event of a checkpoint up by reading each line as JSON, so a file whose members are in another order, or with other whitespace, is checked like the original.
