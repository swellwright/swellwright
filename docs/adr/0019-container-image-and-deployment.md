# ADR 0019: The container image and the first deployment

Status: accepted

## Context
Until now Swellwright ran from a checkout with `pnpm`. The first thing an operator needs is a deployment that can be started from nothing, that is safe by default and that can be rebuilt from the repository alone. The design (`09-ops-docker.md`) sketched a compose file with a worker and a registry image; neither exists yet. This slice makes the real thing for what exists today: the API, the console, PostgreSQL and Valkey.

## Decision
- **One image, one `Dockerfile` at the root.** It holds the API, the built console and the migration tool, and nothing that is only needed to build. The migrations and the administration commands (`node apps/api/dist/admin.js`) run from the same image with another command, so the server, the schema and the commands can never be of different versions. A second, leaner image for the server alone was tried and dropped: `@prisma/client` declares the Prisma CLI as an optional peer, and pnpm links it (about 190 MB with its dependencies) into every production install of the workspace anyway. `prisma` is therefore a declared dependency of `@swellwright/db` now, which is true to how it is used: the image runs `migrate deploy`.
- **Stages.** `base` (the pinned Node image plus OpenSSL for the Prisma engine), `tooling` (pnpm), `manifests` (only the `package.json` files, so the install layer is reused when only code changes), `build` (install with the development tools, build everything, drop the compiled tests), `server-deps` (a production-only install for `@swellwright/api` and what it needs, plus the migration tool with its engine) and `runtime`. A plain `docker build .` makes `runtime`.
- **Everything downloaded is pinned.** The base image by digest; pnpm by the hash of its registry tarball (checked in the `Dockerfile`, because Node no longer ships Corepack); packages by the lockfile with `--frozen-lockfile --ignore-scripts`; the Prisma schema engine by the checksum of ADR 0013. The engine is fetched and checked **while the image is built** (`prisma.mjs --verify-engine`), so a running container downloads nothing. The images of the compose file are pinned by digest too, and Dependabot proposes new digests and new action commits, only for releases that are a week old (`.github/dependabot.yml`). npm packages are left out of Dependabot on purpose: the lockfile is updated deliberately, after the three-day wait of ADR 0009.
- **The API serves the console** from the directory in `SW_WEB_DIR` (set to `/app/web` in the image), so there is one upstream for the reverse proxy and no second container. The console has real URLs (client-side routing, for example `/dashboard/security/users`), so a deep link or a reload must open the page: a GET or HEAD of a path that is not under `/api`, has no dot in its last segment (a missing file stays a 404), is not under `/assets/` and comes from a client that accepts HTML is answered with `index.html` and the same headers as `/`; unknown `/api/...` paths, other methods and `Accept: application/json` keep the 404. The server **refuses to start** if the directory has no `index.html`: a typo must not give an instance that answers 404 to everything.
  - Files carry what the console needs and nothing more: a content security policy (`default-src 'self'`; scripts only from this origin; inline styles allowed because React sets `style` attributes; no plugins, no framing, no `<base>`, forms only to this origin), `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, a restrictive `Permissions-Policy`, `Cross-Origin-Opener-Policy: same-origin`. The page itself is never cached; files under `/assets/` (named by hash) are cached for a year and marked immutable; other files for an hour. Dotfiles are not served. API answers keep their own headers (JSON, `no-store`) and none of these.
- **Who the client is behind a proxy.** `SW_TRUSTED_PROXIES` tells Express which peers may set `X-Forwarded-For`. Unset or `false` ignores the header in the standalone API. Production Compose requires an explicit value (ADR 0049): use the exact proxy peer address seen by the API or an exclusive proxy CIDR, and have the proxy overwrite the header. Use `false` only for direct access. Do not trust all private ranges or a shared network, since plugin sidecars can reach the same API port.
- **The compose file** (`deploy/compose/docker-compose.yml`, secrets in a `.env` next to it, `.env.example` explains each) has `postgres`, `valkey`, a one-shot `migrate` and the server. The server starts only after `migrate` has finished successfully, and `/ready` still refuses while a migration is missing (ADR 0013). The server container has a read-only root file system and a memory `/tmp`, no capabilities, `no-new-privileges`, an init process and the non-root `node` user; the image has a health check that asks the process itself. The database and the cache sit on an `internal` network that nothing outside can reach; only the server is also on the network that can reach the outside (the nodes and panels later) and is published, on `127.0.0.1:3100` by default. Required secrets are checked by Compose (`${VAR:?}`), so a missing one stops at once with a message.
- **CI starts the real stack.** The job `image` writes throwaway secrets, builds the image through the compose file, starts it and runs `scripts/smoke-test.sh`: ready (database, cache, migrations), the console with its headers, hashed assets cached for good, the API unchanged, first-run setup (wrong token refused, owner created, second setup refused). It then checks that the container is not root, that its file system is read-only, that the health check and `admin.js users` work. A change that breaks the image fails the pull request, not the first deployment.

A build behind a network that cannot reach `binaries.prisma.sh` passes `--build-arg PRISMA_ENGINES_MIRROR=<url>` (default: Prisma's own host). The variable reaches the engine download in both places it happens, the migration stage and `pnpm run build` (Turborepo only passes what it is told to, hence `globalPassThroughEnv`). The pinned checksum applies to whatever was downloaded, so a mirror is a source, not a trust anchor.

## Consequences
- An operator needs Docker and nothing else: `cp .env.example .env`, three secrets, `docker compose up -d --build`, a reverse proxy with TLS in front.
- The image is larger than a server-only one by the Prisma CLI (about 190 MB) and the engine (about 20 MB). In exchange there is one artifact to version, sign and pull.
- Known limits, deliberate for this slice:
  - Built for `linux/amd64` only. The engine checksum is pinned for `debian-openssl-3.0.x` (and `windows` for developers); an arm64 image needs its pin (`linux-arm64-openssl-3.0.x`) added to `engine-checksums.json`, and the build fails until then.
  - Built from a checkout. Published images, signatures, an SBOM and version tags belong to the release workflow (ADR 0010).
  - No worker container: there is no job runner yet. When it arrives it is the same image with another command.
  - The health check asks whether the process answers (`/health`); readiness (database, cache, migrations) is `/ready`, which the smoke test and an external monitor use.
  - Debian slim, not a distroless base: the Prisma engine needs glibc and OpenSSL, and a shell is useful when an operator has to look inside.
  - Valkey has no password: it is reachable only from the internal network, as the database is.
