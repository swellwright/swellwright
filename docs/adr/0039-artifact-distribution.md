# ADR 0039: Artifacts: the catalogue, and distribution over SFTP with the hash checked before and after

Status: accepted

## Context
Design principle 10 and policy P-009 say that every change to a node goes through a versioned artifact, verified by its hash before it runs. ADR 0036 made the node installer such an artifact (a file, a generated `manifest.json` with its SHA-256) and left "the artifacts mechanism of the server" for later; ADR 0035 gave the SSH layer SFTP with hashing. The roadmap's phase 2 acceptance says "artifact hashes are verified". This slice builds the mechanism: a catalogue of the built-in artifacts that the API serves, putting one on a server with the hash checked on both ends, checking later what is on a server, and the console for all of it. Running an artifact (commands, scripts, detached steps) is another slice and builds on this one.

## Decision

### The catalogue: files in the image, checked when the server starts and every time one is used
The built-in artifacts are the `artifacts/<directory>/` of the repository, which the container image carries (the `Dockerfile` copies them, without their test suites, to `/app/artifacts`) and `SW_ARTIFACTS_DIR` can point elsewhere. At start the API reads every directory that has a `manifest.json`, parses the manifest with a **strict** Zod schema shared with the console (`ArtifactManifestSchema` in `packages/contracts`: `manifestVersion`, `name`, `version`, `description`, `file`, `interpreter`, `sha256`, `size`, `minOs`, `steps`, `params`; an unknown key, a hash that is not 64 lower-case hex characters, a file name with a separator or `..`, a step that names a parameter the manifest does not declare, a pattern that is not a regular expression: malformed) and checks the file: it is a plain file (not a link) that stays inside its directory, has the size the manifest says (and not more than `SW_ARTIFACT_MAX_BYTES`, 64 MiB) and hashes to the SHA-256 the manifest says. Whatever is wrong makes **that** artifact `broken` with the reason in words; it is logged, noted in the audit chain (`artifact.broken`, outcome `failure`, no actor: nobody asked) and listed in the console in red, and it is neither downloaded nor pushed. Nothing in this can stop the API from starting: an unreadable catalogue is an empty one. Two directories that declare the same name and version make both of them broken (neither is trusted); two versions of one name are two versions. A directory with no manifest is not an artifact. The schema accepts what `scripts/artifact-manifest.mjs` writes today (a test reads the real manifest of the node installer), so the generator did not change.

The check is repeated **every time a file is used** (download or push): a file spoiled after the start is found then, marked broken, noted once (with the person who ran into it as the actor) and refused; a file put right on disk is accepted again. The immutability of a released version is therefore a property that is checked, not assumed. One version per artifact is in the image for now; the API already has the shape for several: `GET /artifacts` lists artifacts with `versions[]` (newest first) and `latestVersion` (the highest that is intact), `GET /artifacts/{name}` and `GET /artifacts/{name}/versions/{version}` give one, `GET /artifacts/{name}/content` and `.../versions/{version}/content` download.

A download streams the file from disk (no buffering) with `Content-Disposition: attachment; filename="<file>"`, `Content-Length` and `X-Content-SHA256` (the hash the manifest declares, so that the receiver can check what it got); the file is hashed once more before the first byte is sent. The contract registry learned a `binary` response (OpenAPI `application/octet-stream`, the two headers described, not checked against a JSON schema; the response check in development only asserts that a file was returned).

### Distribution: SFTP, with the hash checked before and after, and an atomic place
`POST /servers/{id}/artifacts {name, version?, destination?}` (`servers:write`): the file is **read and hashed now** (a file that is not what its manifest says is never sent, and the answer is 409 `artifact_broken` before any connection), the SSH layer connects through the same door as every other operation (pinned host key required and checked before any credential, address policy, access entries by priority until one logs in, secrets read for the length of the call), and then:

1. The server says who the login is and where its home is (`id -u`, `$HOME`; the home is validated, the paths are made only from a validated name, version and file name).
2. If the file is there already and hashes right (`sha256sum`), nothing is uploaded: 200 `unchanged`.
3. Otherwise the bytes that were hashed are uploaded with `SftpClient.put` to a temporary name next to the destination (`expectedSha256`: the library hashes what it sends), the server hashes the temporary file (`sha256sum`, falling back to reading it back over SFTP when the server has no such program), and only if that equals the manifest it is renamed over the destination. A mismatch deletes the temporary file and is 502 `artifact_hash_mismatch` (`details`: `expected`, `actual`, `stage: upload`).
4. The mode is set exactly (`chmod`, because a umask can only narrow what SFTP asked for): scripts (`interpreter` `sh`, `bash`, `python3`) 0755, a file that is only shipped (`none`) 0644; never writable by others.
5. The server hashes the file **in its place** once more. If that differs the file is removed (`stage: final`).
6. The record is written and `artifact.pushed` appended in one transaction.

A failure leaves nothing at the place of the file. A connection that dies mid-upload cannot delete its own temporary file; the **next** push to that directory removes such leftovers (`*.swellwright-*.part`) before it uploads, which the tests pin.

**Where.** `destination: user` (the default): `<home of the login>/.swellwright/artifacts/<name>/<version>/<file>`, directories 0700, private to that user (the same `~/.swellwright` the detached steps of ADR 0035 use). `destination: system`: `/var/lib/swellwright/artifacts/<name>/<version>/<file>`, owned by root, directories 0755, readable by everybody, written **as root through the sudo path of the SSH layer** (the stored sudo password on standard input only, `sudo -n` when none is needed; a login that is not root and cannot use sudo: 409 `sudo_unavailable`, with nothing written). The login cannot write there, so the file is uploaded and hashed in `~/.swellwright/incoming/`, installed next to its final place with `install -m <mode> -o root -g root` under a temporary name and renamed over it (atomic), hashed in place, and the staged copy is deleted. Root as the login needs no sudo. `~` is never expanded by SFTP; the home is asked of the server, so any login works. Everything about a system copy is asked **as root** (one command through the sudo path: missing, not a file, or its `sha256sum`), because the login may not be able to look at the directory at all: the step layer creates `/var/lib/swellwright` as 0700 when it runs as root, and the first push of a login that is not root failed with `stat failed: Permission denied` before a byte was sent (ADR 0040). The install command names the whole chain (`/var/lib/swellwright`, `.../artifacts`, the version directory) so that each is root-owned and 0755. The check of a copy falls back to the login's own SFTP when sudo does not work, as before.

**One place per version.** `ServerArtifact` has one row per (server, artifact name, version), because a version is immutable and so either on the server or not; the row carries the destination. Pushing a version to the other destination while it is at one is 409 `artifact_destination_conflict` (remove it first), which keeps remove and check unambiguous. The same hash already there is `unchanged` and does not touch the row except for the check time; a changed or missing file is replaced and the row updated.

**One operation per server at a time** (push, check and remove share the lock; the second gets 409 `artifact_busy`), and **a per-user rate limit** (`SW_ARTIFACT_RATE_LIMIT_PER_MINUTE`, 10) over all three, counted before anything else, so the API cannot be used to hammer a server or to upload in a loop.

### Checking and removing what is on a server
`POST /servers/{id}/artifacts/{name}/verify[?version=]` hashes each copy of that artifact on the server and compares it with the catalogue: `ok`, `differs` (the file is there and hashes to something else, and the answer carries both hashes) or `missing`. A copy of a version the catalogue lost or has broken is compared with what was pushed, and says so (`catalogue: broken|missing`). The time, the state and the observed hash are kept on the row and shown. A copy that is not intact is a **result** (200, `ok: false`), not an error: checking is what was asked. Nothing is repaired; pushing again does that. `DELETE /servers/{id}/artifacts/{name}/{version}` removes the file and the directories this push made if they are empty (a file of the person in them stays), and forgets the copy; a copy that is gone is not an error. `GET /servers/{id}/artifacts` lists what was pushed and never connects.

**The recorded path is not trusted blindly.** Before a copy is hashed or deleted its recorded path must have exactly the shape a push makes (`<artifact directory of its destination>/<name>/<version>/<file>` with plain segments): a record that was edited to point at `/home/user/precious` is refused (409) before one command runs. The commands are a closed set of fixed shapes with quoted arguments.

### Permissions, audit, configuration
Reading (the catalogue, the download, the list of copies) needs `servers:read`; checking a copy needs `servers:write`, like every operation that makes the API open a connection (ADR 0037). **Push and remove need `servers:exec` and a fresh second factor** (ADR 0038): what is pushed is meant to be run on the server, so putting it there is as consequential as running a command. They were `servers:write` when the slice was built, before `servers:exec` existed, and were tightened once both were merged (OpenAPI 0.23.0); like every step-up route they accept a cookie session only, so an API token cannot push. Audit actions, all strict and in the same transaction as the change except the notes: `artifact.pushed` (outcome, `result` `pushed` or `unchanged`, destination, remote path), `artifact.verified` (one per copy: state, expected and observed hash prefixes, catalogue state), `artifact.removed` and `artifact.broken` (a note). Details hold the artifact, the version, the server name, hash prefixes and error codes; never a secret. A refusal before anything was attempted (not pinned, address policy, sealed vault, rate limit, busy, broken before connecting) is not a record about a server. Configuration: `SW_ARTIFACTS_DIR`, `SW_ARTIFACT_MAX_BYTES` (a push holds the file in memory, so the limit is also the most memory a push takes) and `SW_ARTIFACT_RATE_LIMIT_PER_MINUTE`. New error codes: `artifact_broken`, `artifact_busy`, `artifact_destination_conflict`, `artifact_hash_mismatch`, `sudo_unavailable`.

### Why SFTP, and what a later engine builds on
SFTP is part of every OpenSSH server (no agent on the node), is already in the SSH layer with streaming, hashing and an atomic rename, and keeps the file's bytes out of any command line. The hash is the integrity check and the only one in this slice: signatures (who published an artifact) are not built. The node engine (snapshots, undo plans, the safety timer) and the scenarios will find an artifact where this slice puts it, know its hash from the catalogue, and run it as a detached step with the parameters its manifest declares; the files on a server are the ones this mechanism recorded, so a later "is this node's installer the one from the catalogue" is `verify`.

### The console
Operations, Artifacts: cards of the panel's `EntityCard` kind (name, version, state chip, size, short hash with copy, interpreter tag), a detail dialog (description, interpreter, file, size, the whole SHA-256 with copy, the steps with their read-only, root and `full` markers, the parameters by group, a red reason for a broken one, the download). The server drawer has an Artifacts card (what was pushed with its last check, `Push` with a dialog for artifact, version and destination, `Verify` and `Remove` per copy), gated by `servers:write` for the actions.

## Consequences
- The installer ships to a server as a file whose hash was checked on both ends, which is what policy P-009 wants, without the server running anything of Swellwright's.
- A repository file edited after release shows up as `broken` in the console and the logs instead of being sent; the image carries the artifacts, so an operator can check them from outside with `node apps/api/dist/admin.js artifacts` (the CI `image` job does).
- A push holds the file in memory (bounded by `SW_ARTIFACT_MAX_BYTES`); streaming from disk twice was rejected because the bytes that are hashed must be the bytes that are sent.
- OpenAPI 0.21.0; `ServerArtifact` and its migration.

## Not built here
Running an artifact, scheduled or automatic checks of copies, pushing the same artifact to several servers in one request, signatures of artifacts, several versions in the image (the shape is there), promotion of a version, the `node-engine` artifact, downloading to a person with the hash verified in the browser, and a step-up or `servers:exec` for artifacts that are meant to run.
