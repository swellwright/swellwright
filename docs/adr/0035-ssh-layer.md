# ADR 0035: The SSH layer: ssh2 in pure JavaScript, pinned host keys, sudo over stdin, detached steps

Status: accepted

## Context
ADR 0007 decided that Swellwright is agentless over SSH, uses `ssh2`, pins host keys, passes `sudo` passwords through standard input and runs long node-side work as detached processes that are followed by polling. Phase 2 builds that layer as `packages/ssh` (`@swellwright/ssh`), a pure library: no database, no HTTP, no UI. This record says how, what was checked before the dependency was trusted, and what the layer does not do.

## Decision

### The library: `ssh2` 1.17.0, pure JavaScript only
The Remnawave panel already depends on `ssh2`, it has a client and a server half (the server half is what makes the tests possible), and it needs no binary on the worker. Alternatives were rejected: running the `ssh` program (a program must be on the worker, secrets would travel through files, agents or `SSH_ASKPASS`, there is no pooling and every channel costs a process), native bindings to libssh2 (a compiler and a native add-on in the image), and wrappers around `ssh2` (`node-ssh`: one more layer to read, no gain).

`ssh2` is pinned exactly (1.17.0, published 2025-08-20) with `@types/ssh2` 1.15.6 as a development dependency. Before first use the tarballs of `ssh2` and of its four runtime dependencies (`asn1` 0.2.6, `bcrypt-pbkdf` 1.0.2, `safer-buffer` 2.1.2, `tweetnacl` 0.14.5) were downloaded, their integrity checked against the registry and their contents read. Findings:

- `ssh2` declares an `install` script (`install.js`) that runs `node-gyp` to build an optional native crypto binding, and two optional dependencies (`cpu-features`, `nan`) that build native code too. The repository never runs lifecycle scripts (ADR 0009), and the two optional packages are excluded with `ignoredOptionalDependencies` in `pnpm-workspace.yaml`, so they are not even downloaded. `ssh2` loads both inside `try`/`catch` and falls back to Node's `crypto` and to a WebAssembly build of Poly1305 that is embedded as base64 in `lib/protocol/crypto/poly1305.js`: the library runs, and is tested, in this pure mode. The `src` of the native binding (`binding.cc`) is in the tarball and is never compiled.
- No network code other than the TCP socket to the server the caller names and, for Windows only, the Pageant agent helper (`child_process.spawn`, reached only when an `agent` option is set, which this package never sets). No `eval`; one `new Function('return 2n ** 32n')()` with a constant string in `node-fs-compat.js`. The library code does not read `process.env` (only `install.js` reads one CI variable). The Emscripten glue of the Poly1305 module contains `fetch` and `fs.readFile` branches for loading a `.wasm` file, which are not taken because the binary is a `data:` URI.
- `asn1`, `bcrypt-pbkdf`, `safer-buffer` and `tweetnacl` have no lifecycle scripts, no network, no `eval`, no `child_process`. Licences: MIT (`ssh2`, `asn1`, `safer-buffer`), BSD-3-Clause (`bcrypt-pbkdf`, with Niels Provos' Blowfish portions), Unlicense (`tweetnacl`); all compatible with AGPL-3.0-only and listed in `THIRD_PARTY_NOTICES.md`. `pnpm audit` is clean.
- `@types/ssh2` depends on `@types/node` 18, which therefore appears in the lockfile as a type-only transitive dependency.
- Risk accepted: `ssh2` has one maintainer and releases rarely (1.17.0 is from August 2025, the one before it from September 2024). Mitigation: the exact pin, a test suite that exercises the library through the real protocol (the in-process server and a real sshd), and a thin wrapper, so that replacing the library touches one package. A defect met on the way: the key generator of `ssh2` produces a malformed ed25519 key about once in 300 calls (a public key that starts with a zero byte loses it). The production code never generates keys; the test helper generates again until the key parses.

### Host key policy
`SshTarget.hostKey` is required. `pinned` lists OpenSSH style fingerprints (`SHA256:` plus unpadded base64); the key must match one of them, compared in constant time, or the connection fails with `HostKeyMismatchError` (carrying the expected and the actual fingerprints). The check runs in the `hostVerifier` of `ssh2`, during key exchange: the client has not yet asked for the `ssh-userauth` service, so no username, password, key or signature has been sent, not even the `none` probe. The tests assert this on the server side (the in-process server records every authentication request, and the list is empty after a mismatch, also for key authentication). `discover` accepts any key and reports it; it exists for the first-use flow. The preferred way to learn a fingerprint is `fetchHostKey(host, port)`: it performs the handshake up to the host key, refuses it in the verifier and disconnects, so credentials are not involved at all. The caller shows the fingerprint to a human, then pins it. `discover` on a connection that carries real credentials is only acceptable after such a confirmation. **Key types (added after the first real run, ADR 0040).** A server has a host key of every type and shows the one the client prefers; a client that pinned an RSA key and found the server showing a new ed25519 key took the server for another machine. A pinned policy can therefore say which types its keys have (`keyTypes`, as `fetchHostKey` names them): the connection then offers those algorithms first (`hostKeyAlgorithmsPreferring`: the RSA names of the signature algorithms for `ssh-rsa`, then every other algorithm) and the server shows the pinned key while it still has it. It never excludes a type, and the fingerprint check is unchanged: a key that is not pinned is still refused before any credential is sent.

### Secrets
Passwords, passphrases and sudo passwords are never in an error message (text from `ssh2` or from a remote shell is passed through `redact` with the operation's secrets), a log line, `toString`, `JSON.stringify` or `util.inspect` of a connection, the pool key (a keyed hash with a random per-process key), a command line or an environment variable. The tests print every error of every failure path and look for the secrets in message, cause and stack. Private keys are parsed before connecting, so a missing or wrong passphrase is reported as `ssh_key_invalid` without touching the network.

### sudo through standard input
`exec(command, { sudo: { password } })` sends `sh -c '<wrapper>' name '<command>'` with the password as the first line of standard input. The wrapper reads that line itself, so it can never reach the command, and then decides: already root, run directly; `sudo -n -- sh -c :` succeeds (NOPASSWD, or a cached ticket), run with `sudo -n` and drop the password; otherwise `sudo -S -p ''` fed by a pipe that carries the password line followed by the rest of the input. A plain `sudo -S` would hand the password line to the command whenever sudo does not ask (root, NOPASSWD), which is how a password ends up in a file written by `cat > file`; the tests cover each of the cases against a stand-in sudo and the real sudo of the test server, and look at the process list of the server while a sudo command runs. Limits: the password is in the memory of the wrapper shell for the length of the call; with a wrong password sudo reads further lines of the input as retries (they go to sudo and nowhere else); `Defaults requiretty` is not supported (no pseudo-terminal is allocated).

### Detached steps
A step is a directory `<baseDir>/<id>/` on the server, created and started by one command whose standard input carries everything: the script, its input and environment as base64 frames with their SHA-256, and the wrapper. Nothing secret is in a command line and nothing depends on SFTP. The directory holds `script.sh`, `script.sha256`, `stdin`, `env` (a sourced file of `export` lines), `run.sh` (the wrapper), `out`, `err`, `pid`, `started` and `exit`. The wrapper runs under `setsid`, so it leads its own session and process group (cancel is `kill -- -PID`), ignores `SIGHUP`, records its pid and start time, runs `sh script.sh` with the redirections, and records the exit code. `exit` (code, then finish time) is created by hard-linking a complete temporary file, so the first writer wins and a reader never sees half of it; the wrapper writes it, and `cancelStep` writes 143 or 137 only when the wrapper could not. State is derived on the server: `exited` (marker present), `running` (no marker, and the pid is alive with a command line naming this step's `run.sh`, so a recycled pid does not count), `lost` (no marker, process gone: a reboot, a hard kill), `unknown` (directory present, wrapper not yet started). `readStepOutput` reads by byte offset and says `eof` only when the marker was seen before the size was taken, so a reader that lost its connection continues exactly where it stopped; `waitForStep` reads the status first and then drains the output, so everything written before the step was seen finished is delivered. `startDetachedStep` is idempotent through `mkdir` (atomic): the same id with the same script attaches, another script is a conflict, a half-created directory is reported.

The default `baseDir` is per user: `/var/lib/swellwright/steps` for root, `~/.swellwright/steps` for anybody else, also when `sudo` is used. `~` is expanded by the remote shell from `$HOME`, and the sudo of Debian and Ubuntu gives the command root's `HOME`: `cancelStep` and `removeStep` with `sudo` therefore ask the login for its home first and pass the absolute path (found on a real server: a cancel did nothing, the run was marked cancelled while the script ran to its end, and the step directories of sudo runs were never removed; the stand-in sudo of the tests keeps the caller's `HOME`, which hid it, so it can now reset it as the real one does). This refines ADR 0007, which named `/var/lib/swellwright/runlogs/<run>/`: with the directory in the user's home a non-root user can poll status and output without privileges, while the root-owned job only writes into it (its output files are pre-created by the user, its markers are world-readable inside a 0700 directory). Ids are `[a-z0-9-]{1,64}`; directories are absolute or `~/...`; every value that reaches the shell goes through `shellQuote` or a validator, and the tests feed hostile ids, directory names, environment values and scripts to a real shell.

The server needs `sh` (dash is enough), `setsid`, `base64`, `sha256sum`, `tail`, `head`, `wc`, `tr`, `date`, and `sudo` for the sudo variant: nothing is installed. Known limits: Linux servers only (BSD and macOS lack some of these tools and `/proc`); with `hidepid` mounted on `/proc` a root job cannot be seen by another user and is reported `lost`; `systemd-logind` with `KillUserProcesses=yes` ends the processes of a non-root user's last session (root is exempt by default), and the layer does not leave the session scope; step directories are kept until `removeStep`; scripts and input are limited to 2 MiB each.

### Which addresses may be contacted
`validateTargetAddress`, `assertTargetAddress` and `resolveTargetAddress` implement the address part of the outbound policy (`05-security.md`, section 7) for server entries. They are pure functions of the text (the last one also resolves names): loopback, link-local and cloud metadata addresses are refused unless the policy allows them, unspecified, multicast and reserved addresses and ambiguous numeric forms (`127.1`, `2130706433`, `0x7f.1`, which the system resolver reads as loopback) never pass, IPv6 forms that embed an IPv4 address are judged by it, and private ranges are allowed by default because fleets live there. The connection itself does not apply the policy, so that tests can use loopback; the API calls the helper first and connects to the checked address (`resolveTargetAddress` refuses a name if any of its answers is forbidden), and the pinned host key proves who answers.

### Deadlines
Everything that can wait has a deadline: connect, key exchange and authentication together (`connectTimeoutMs`, with a backstop timer), each command (`timeoutMs`, default 120 s, then a `TERM` signal request and `SshTimeoutError`), SFTP requests and transfers (idle timeout), keepalive (a silent link is declared dead after interval times count), the pool (`acquireTimeoutMs`), and the step controls. Output is capped per stream (`maxOutputBytes`, default 4 MiB) and flagged `truncated`; streaming callbacks still see everything.

### Not in this layer
The outbound allowlist of `05-security.md` (section 7) beyond the address check above: the API decides which hosts may be contacted and applies it before it asks this layer to connect; port and agent forwarding, keyboard-interactive and other second factors, SSH certificates (planned with the access policies, ADR 0004), a pseudo-terminal and the web terminal (phase 9), jump hosts, and anything that is not a plain SSH exec or SFTP session. The default algorithms of `ssh2` are used (modern first); a caller may narrow them with exact lists (`algorithms`), and `strictVendor` stays at its default.

### Tests
The package ships an in-process SSH server built on the server half of `ssh2` (`@swellwright/ssh/test-support`): it records every authentication request, presents any host key, stalls, freezes, drops connections, runs commands in a real POSIX shell, serves SFTP from a directory, and comes with a stand-in `sudo` and a TCP forwarder that can be cut. The failure paths (wrong keys, wrong passwords, timeouts, drops) are tested only there. A second set of tests (`*.integration.test.ts`) runs the same step scenarios and more against a real sshd when `SW_TEST_SSH_*` is set; CI runs them against a small Ubuntu 24.04 image with key logins only, a throwaway key and a throwaway sudo password made in the job. They never send a wrong credential.

## Consequences
The rest of the system gets one typed, secret-safe way to run things on a node, and the engine can re-attach to a step after a worker restart with nothing but the step id and the byte offsets. The wrapper scripts are code that runs on every managed server, so they are plain POSIX sh, small, and covered by tests on a real shell and a real sshd. The price is a dependency with a slow release rhythm, and the limits listed above.
