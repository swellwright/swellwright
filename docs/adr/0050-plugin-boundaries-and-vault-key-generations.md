# ADR 0050: Hardening the plugin boundaries and the vault key in memory

Status: accepted

## Context
A review of the plugin system and the vault (2026-11) found that several boundaries promised by ADR 0027 to 0031 and ADR 0024 did not hold at their edges:

- **The digest did not cover what the process could read.** The digest skipped a top-level `.git` before checking whether it was a link. The plugin process may read its whole directory, and the Node permission model follows a link inside an allowed path: measured on Node 26.13.1 (Windows, a junction), a plugin read a file outside its directory through `./.git/…` while the direct path was refused. The same holds for a link nested inside a real `.git`, and a module could be loaded from `.git`, which is not hashed.
- **Reading plugin files.** The driver file was read in full, following links, before its size was checked; an oversized settings schema was silently dropped, leaving a plugin that looked usable without its settings.
- **The process protocol.** Messages from the plugin process were cast to a type, not checked: a malformed message threw inside the parent's event handler and ended the API. Requests to the core were answered at any time (during module initialisation, after a call had ended) and without limit. The last line the process printed was kept as `runtime.lastError`, which `GET /plugins` shows to everyone with `plugins:read`; a plugin that printed a secret it was given before crashing published it.
- **Lifecycle.** Disabling a plugin while its process was starting left the process running; approving a plugin again reused a process started under the earlier approval, with its permissions.
- **Deadlines.** A declarative operation that timed out kept running: a later step could still be sent. Transport timeouts were inactivity timeouts, so an answer that kept trickling in was never ended. `each` loops were expanded eagerly without a budget, and in a request body `each` was checked as a plain key but run as a loop.
- **Addresses.** The public-address filter parsed IPv6 by its first group and missed equivalent spellings and translation prefixes (NAT64, 6to4, Teredo, IPv4-compatible).
- **The sidecar gateway** looked at every plugin's files before checking the token, and every sidecar shared one network with the others and with the core.
- **The vault.** A second API process that still held the previous key could write a secret under it after another process rotated the key; the value could not be decrypted afterwards. A rotation whose commit succeeded but whose answer was lost left the process with the old key and lost the new recovery key. Changing the passphrase compared the texts without the normalisation the key derivation applies.

## Decision
- **Links and `.git`.** The digest covers every regular file readable in the plugin directory, including repository metadata. A link anywhere in the tree makes the plugin invalid. The walk stops at 4,000 entries, 2,000 files, 32 MiB, or a depth greater than 12 directories. The manifest must still name files in the working tree rather than in `.git`. The cache checks the change time and file identity as well as size and modification time.
- **Reading files.** Discovery, digesting and bounded reads use the same filesystem path guard. It checks relative names before resolving them and enforces the normalized root boundary at the filesystem call. It rejects parent segments, absolute paths, drive or stream syntax, backslashes and NUL. The bounded reader also checks the file type, link count, canonical path and size before reading, then verifies its identity after opening and after reading. The file's recorded size bounds the read, plus one byte to detect growth. A refused schema is a discovery problem.
- **The process protocol.** The core validates messages at run time. An invalid message, or `ready`/`failed` after startup, ends the process, not the core. A request to the core names the call it belongs to and is served only while that call is under way; at most 8 run at once and at most 256 per call count toward the broker budget (`PLUGIN_LIMITS.concurrentCoreRequests`, `coreRequestsPerCall`). When a call ends, its network requests are aborted, and results of outstanding broker requests are not delivered. The host reserves each of the 8 call slots before reading settings. The core discards standard output and standard error. `lastError` contains a core-owned diagnostic, never a plugin's exception text, even at startup.
- **Lifecycle.** Each running process is bound to the approval it was started under (time, digest, permissions). Stopping a plugin aborts a start under way and discards a process that becomes ready afterwards; a process whose approval differs from the current one is replaced on the next call (on every API instance, since each call reads the approval). Enabling a plugin ends the process of the earlier approval at once on the instance that handled it.
- **Deadlines and budgets.** A declarative operation gets an abort signal that the deadline fires: no further step is sent, no further secret read, and a request under way is closed. An effect already sent may have happened. Network and sidecar exchanges have an absolute deadline in addition to the inactivity timeout. Building a result or a request body is bounded to 20 000 parts and 1 MiB of text, charged before a loop is built and sequentially, not with every branch at once. `each` is a loop only in a result, where the check allows it; in a body it is an ordinary key, as it is checked. Lookups of parameters and settings use own properties only.
- **Addresses.** IPv6 is classified in binary. Only global unicast (`2000::/3`) is public, without `2001::/23` (Teredo, benchmarking and other protocol assignments), `2001:db8::/32`, `2002::/16` (6to4) and `3ff0::/12`. An address that carries an IPv4 address (mapped, compatible, NAT64 `64:ff9b::/96`) is judged by that address, so NAT64 to a public address keeps working. The former IPv4 6to4 relay block is refused too.
- **The gateway.** A missing or malformed token is rejected without an approval lookup.
  Up to 12 initial lookups run at once; requests for the same plugin share the in-flight lookup,
  with at most 128 additional waiters across the API process. Four separate slots are reserved for
  fresh approval reads after a token matches either that initial lookup or the last verified
  revision in the bounded file cache. A cached revision only selects a lane, even after its file
  verification expires: no operation is served without a fresh enabled approval matching the
  token. A local stop clears the hint and detaches the initial lookup; an in-flight read cannot
  carry authorization across the stop. Unmatched guesses cannot consume the reserved slots,
  and the guessing counter does not block a valid token from the same source. A correct token
  whose plugin fails file verification does not consume the guessing budget. Guessing counters
  track at most 1,024 sources and one shared overflow counter; sources are IPv6 `/64` or one IPv4
  address. A full table is swept at most once per five seconds. The token covers plugin ID, digest
  and approval time; reapproval invalidates it. Each sidecar can make 120 authenticated requests
  per minute per API instance. File verification checks only that plugin and is reused for at most
  one second.
- **Gateway audit.** The first denial per prefix and plugin is recorded, up to 128 pairs in ten minutes. The summary has an exact total and an approximate top five from a bounded candidate table. On saturation the table ages older counts so a new persistent source can enter even after noise; the summary also counts overflow misses. Each successful gateway secret delivery requires an audit record before returning the value (at most 120 deliveries per minute, per plugin and API instance); internal audit failures are not disclosed to the sidecar. Process plugins and declarative drivers use best-effort secret audit notes deduplicated per plugin and secret for ten minutes.
- **Filesystem errors.** Unverified files block new calls without changing approval. A transient check retries once; three consecutive strikes stop the local process and record one `plugin.unverifiable` event for the episode. Failed checks in the same process count at most once per second per approval, whether from listing or attempting to run the plugin. A multiply linked file has a separate diagnosis and triggers the stop and audit immediately; install an independent copy rather than retrying the same files. On Linux, keep `fs.protected_hardlinks=1` and the plugin tree owned by a trusted account and not writable by untrusted users. Otherwise a user able to create a hard link to a plugin file can make it unavailable; the kernel setting does not protect against accounts already allowed to create the link. Once verification succeeds the failure episode ends. Discovery does not let an unverifiable candidate hide a usable one in another root. An existing approval is tied to its digest and trust tier; failure in that tier does not authorize a fallback in another tier. Confirmed changes still revoke approval. Keep `.git` covered by the digest; install exported trees without it.
- **Existing secret bindings.** Adding or changing a binding, exporting a token with approved secret access, and approving a plugin with a value saved in a secret field of its current schema require `vault:reveal`. A new binding records the field and secret ID, not the value. Upgrading does not erase or reauthorize saved bindings; before rollout or a schema change, an owner should inspect each configured secret field, remove stale IDs, and deliberately rebind or reapprove the reviewed settings. A field changed from ordinary to secret is checked against the schema being approved; its old stored text must not be assumed authorized.
- **The sidecar network.** The compose fragment gives each sidecar a network of its own (`<SW_PLUGIN_NETWORK>-<id>`, `internal`), which only the core joins. Sidecars cannot reach one another; each still reaches the core's listener, which is the gateway and the API behind authentication.
- **Expired secrets.** For a process call the core records the vault refusal against the call ID and can report `secret_expired` on failure. With sidecars this works when exactly one call is in flight: the gateway protocol has no call ID and does not guess when calls overlap. A plugin that merely says the words gets `failed`.
- **The key in memory has a version.** The process keeps the version of the key it holds. A status read wipes an observed key that no longer matches the stored version; it does not wipe a newer key installed while the read was in progress. Secret use and reveal also verify the key version. Encrypted writes verify it under the shared vault lock, which the KEK rotation takes exclusively. Reopen a sealed replica to load the current key.
- **A rotation whose answer was lost.** The success response uses the status captured before commit, so there is no additional read that could prevent returning the new recovery key. If the commit reports an error, the core checks the stored version and recovery wrap. A match means this rotation committed and the new recovery key can be returned; if the old version remains, the original error stands. If the database is unavailable or a different rotation superseded the attempt, the process seals itself and answers 503. If the API process actually stops or the client loses the reply, the recovery key cannot be fetched again: unlock with the current passphrase and issue a new recovery key.
- **Passphrase change** compares the NFKC forms, as the key derivation does.

## Not done, and why
- **Memory outside the V8 heap.** `--max-old-space-size` does not limit `Buffer` and `ArrayBuffer`; a plugin process can allocate outside the heap within its deadline. Node has no flag for that, and an RSS watchdog would differ per platform. The container limit of the API is the backstop; `local` code stays the administrator's responsibility (ADR 0028).
- **The digest binds files, not behaviour.** Approved code can still turn data into code (an `import()` of a `data:` URL works under the permission model, measured on Node 26.13.1), and the files can change between the check and the start of the process (the next call notices). Approval remains a decision to trust the author of `local` code, as ADR 0028 says.
- **Immutable staging and IPC framing.** The host does not copy verified plugins into a private immutable directory. Mount code read-only and publish updates outside its running directory; gateway file changes can be observed up to one second later. The decoded IPC budget limits application validation and forwarding, but Node deserializes the frame before dispatch and provides no hook to enforce a raw frame bound. Enforcing that bound requires a replacement transport.
- **A second instance and disable.** There is no cross-instance stop signal. An in-flight call on another API instance may finish within its deadline, but new calls must check the stored approval. An unused process exits on its idle timer.
- **Docker enforcement of the per-sidecar network** is not tested here: it follows from `internal` networks in Compose and has to be confirmed on a real deployment.
- **Distributed audit and limits.** Gateway counters and the verification cache are per process. A crash can lose a partial denial-summary window; first-denial entries already committed remain. Shared quotas or durable denial aggregation would need shared state and a policy for database overload.
- **Gateway capacity and audit volume.** A sidecar without a verified cache entry still shares the initial lane with unknown tokens and can receive 429 under load. The reserved lane protects verified tokens from unmatched guesses, not from other matched tokens or a saturated database. A compromised, approved sidecar can generate about 172,800 secret-delivery audit rows per day per API instance at 120 deliveries per minute. This is accepted to preserve an audit record for every successful delivery; there is no separate daily cap or aggregation of successful deliveries.

## Consequences
- A plugin installed as a Git working copy may exceed the same limits as any other plugin. Prefer an exported tree without repository metadata. Existing approvals of working copies can become invalid when the digest starts including `.git`; review and approve again. Plugins without `.git` retain the same digest if their contents did not change.
- A plugin method that keeps its `context` and uses it after the call returned gets an error; a plugin that asks the core more than 256 times in one call must be split.
- Old Compose fragments must be regenerated and reapplied after upgrading or reapproving a sidecar: old tokens no longer authenticate, and each regenerated fragment joins a separate internal network.
- A deployment with more than one API process no longer loses secrets written after a key rotation elsewhere; a stale process is sealed and must be opened again.
