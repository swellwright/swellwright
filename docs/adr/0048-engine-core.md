# ADR 0048: The engine core: runs, steps, durable execution and the worker

Status: accepted

Proposed on 2026-11-24 and accepted on 2026-11-25, with one change to the proposal: the loop runs inside the API process in this slice, because the vault key lives there (see "Where the code lives" and "Decisions of the owner").

## Context
ADR 0005 chose to build the engine on PostgreSQL and a queue, with no external workflow engine, and `docs/en/design/08-engine.md` describes the lifecycle of a run, the step contract, durability, rollback, approvals, strategies and policies. Phase 4 builds it. What exists today:

- **Servers can already be driven durably.** A detached step on a server survives a dropped connection, is followed again by byte offset, and is owned by exactly one launch (ADR 0035). A step is addressed by an id, so "start it again" with the same id attaches to the step that exists instead of running it twice.
- **A runner exists, in the API process.** Commands (ADR 0038) and baseline checks (ADR 0045) run in the API: one process, a compare-and-set on the row's state, a restart picks the rows up again. That is right for a single read-only job and is not an engine: it has no lease (two processes would both take a row), no journal of what was changed, no undo, no approval and no resource lock.
- **The inputs of a plan exist.** The panel client reads (ADR 0041), snapshots and diffs exist (ADR 0043), the impact calculator says what a change restarts (ADR 0044), a vault secret can be handed to a run and is scrubbed from its output (ADR 0042).
- **`apps/worker`, `packages/engine` and `packages/policy` are empty skeletons.** There is no queue library in the repository: Valkey is used only by the readiness check.

The acceptance of the phase (`docs/en/roadmap.md`): "rollback restores the pre-run snapshot; killed worker resumes". Everything below is chosen so that this can be tested, on a real PostgreSQL and with faults injected, not argued.

This ADR decides the core only: the data model, the state machine, the lease and lock, the checkpoint protocol, what a step is, how a run is stopped and undone, the events, and how it is tested. Approvals and the enforcement of policies, the panel write client, the workflows (verify, adopt, deploy, redeploy, rollback) and the run screens each get an ADR of their own, because each has decisions that are the owner's.

## Decision

### PostgreSQL is the only truth; there is no queue library in this slice
ADR 0005 said a run is a PostgreSQL record **plus** a queue job on Valkey, with locks taken by advisory locks **and** Redlock. This ADR narrows that. A run is a PostgreSQL record, and the worker finds work by asking PostgreSQL for it (`SELECT … FOR UPDATE SKIP LOCKED` over runs that are `queued`, or `running` with an expired lease). Reasons:

- **Two truths disagree.** A job that is lost while the row says `queued`, or a job that fires for a run that was cancelled, are bugs the design would have to defend against forever. With one store a run that needs a worker is a row that says so.
- **A lock that gates changes to servers must be checked in the transaction that records the change.** A lock held in Valkey cannot be, and Redlock's safety under pauses and clock jumps is exactly what is disputed. A lock row in PostgreSQL with a **fencing token** (below) can be checked by the very `UPDATE` that writes a checkpoint.
- **No new dependency** to review for a slice whose load is a few runs at a time. Valkey stays what it is (readiness, and later rate limits and wake-ups). If the load ever outgrows polling (an interval of a second or two, plus `LISTEN/NOTIFY` as a hint), a queue library can be put in front of the same tables without changing a step.

### The tables
- `Run`: id (UUIDv7), `workflowKey`, `params` (JSON, **no secrets**: a secret is a reference to the vault), `planHash` (SHA-256 of the canonical plan; the approvals of a later ADR are bound to it), `state`, `risk`, who asked and when, `cancelRequestedAt`, `pauseRequestedAt`, and the lease: `workerId`, `leaseExpiresAt`, `fence` (an integer that only grows).
- `RunStep`: run, `index`, `key` (`node.install.nginx`), `state` (`pending`, `running`, `succeeded`, `failed`, `skipped`, `undone`, `undo_failed`), `attempt`, `remoteId` (the id on the server, below), `output` (JSON, **no secrets**), the error code and message, times.
- `UndoRecord`: run step, `seq`, `kind`, `data` (JSON, **no secrets**), `state`. Written in the same transaction as the step's success.
- `RunEvent`: run, a per-run `seq` that only grows, `kind`, `data`, time. Append-only.
- `ResourceLock`: resource (`node:<name>`, `server:<id>`, `dns-zone:<zone>`, `panel`), the run that holds it, the fence it was taken with, `expiresAt`.

`CommandRun` and `CheckRun` stay as they are. They are not migrated into the engine in this phase: they work, they are read-only, and moving them would be a change with nothing to show for it.

### The state machine is one pure function
`packages/engine` holds `transition(state, event) → state | error` as a table, with every state of design §1 (`planned`, `awaiting_approval`, `queued`, `running`, `paused`, `awaiting_input`, `succeeded`, `failed`, `cancelled`, `rollback_requested`, `rolling_back`, `rolled_back`, `rollback_partial`). An impossible transition is an error that names both states, never a silent no-op. The table is tested exhaustively (every state against every event), and the database layer applies a transition only as a compare-and-set on the state it read.

### A lease and a fence, and a worker that can be killed at any point
A worker takes a run by one statement: it sets `workerId`, `leaseExpiresAt = now() + ttl` and `fence = fence + 1` where the run is claimable, and gets the new `fence` back. It renews the lease on a timer (ttl three times the interval). Every write the worker makes about the run (a state change, a checkpoint, an event, a lock) carries the fence and fails when the row has another one. So a worker that stalled (a long GC pause, a lost network) and wakes up after another worker took the run **cannot write anything**: its next write fails, it stops, and it does not touch the run again.

What the fence cannot do is stop a stalled worker's step that is already running on a server. That is bounded by two things: the step runs on the server as a detached step with an id derived from the run and the step (`remoteId = <runId>-<index>`), so the second worker that starts the same step **attaches** to it (ADR 0035), and the lock on the resource is taken with the same fence, so the second worker's lock supersedes the first's.

### A checkpoint is one transaction
For a step the worker does, in order:
1. **Intent** (one transaction, fence-checked): the step goes `pending → running`, `attempt` grows, an event is appended.
2. **Effect**: `apply` runs.
3. **Checkpoint** (one transaction, fence-checked): the output, the undo records and `running → succeeded` are written together, then the event.

A crash between 1 and 3 leaves a step that says `running` with an expired lease. The next worker decides what to do from the step's declaration:
- **`idempotent: true` (the default)**: run `apply` again. For a step on a server that is a re-attach by `remoteId`.
- **`reconcile(ctx)` declared**: ask the step first. It looks at the world and answers `done` (with the output), `not_done` or `partial`. This is for a step whose effect is on the panel or in DNS, where "again" is not free.
- **`idempotent: false`**: the run goes to `awaiting_input` with the three choices a person has (retry, mark it done, roll back). It is never retried by itself (design §4).

### The step contract
The contract of design §2 stands (`key`, `title`, `estimateSeconds`, `locks`, `plan`, `apply`, `verify`, `undo`), with these additions that the core needs: `idempotent` and `reconcile` (above); every call gets a `StepContext` with the run id, the step index, the attempt, the fence, an `AbortSignal` (cancellation reaches the step), a clock, and **ports** for what it may touch (SSH, panel read, vault references) so that a test supplies fakes; the output and the undo data have a Zod schema each, and a step whose output holds a value that was handed to the run as a secret fails (the same scrubber as ADR 0042 checks it before the write). A step never reads the database.

### Locks
A step names the resources it changes (`locks(ctx)`), and the engine takes all of a run's locks for a stage in one statement, in a fixed order, so two runs cannot wait for each other. A lock row is held with the run's fence and a short expiry that the lease renewal extends. A run that cannot get a lock waits in `queued` with the reason on the run (`waiting: lock server:42 held by <run>`), it does not fail.

### Stopping, pausing, resuming and undoing
`cancelRequestedAt` and `pauseRequestedAt` are rows the worker reads at every renewal and between steps; for a running step the worker aborts the `AbortSignal` and, when the step runs on a server, asks it to stop (`cancelStep`). Cancelling before an irreversible step is `cancelled`; after one the engine offers an undo instead, as design §4 says. Resuming continues from the first step that is not `succeeded`; no secret is typed again, because steps hold references.

Undo runs the undo records in **reverse**, each as an idempotent, journaled step of its own, against the **current** state of the world (design §5). A run is `rolled_back` only when the check the workflow declares (for panel objects, the snapshot diff of ADR 0043 against the one taken before the first change) finds no difference; otherwise it is `rollback_partial` with the list. An undo that fails is `undo_failed`, and the rollback can be resumed.

### Events
Everything the run does is a `RunEvent` with a per-run `seq`. `GET /runs/{id}/events?after=<seq>` answers a page and the same route streams the following ones as server-sent events, so a client that reconnects asks for `after=<last seq>` and misses nothing. People's actions on a run (start, approve, cancel, resume, undo) also go to the audit chain (ADR 0015); the events of the engine itself do not, they are the run's own timeline.

### Where the code lives, and who holds the vault key
`packages/engine` is the core with no I/O: the state machine, the step and workflow types, the scheduling loop over a `RunStore` **port** and the ports of a step (SSH, panel read, secrets). In this ADR a *worker* is an instance of the scheduling loop; nothing in the design ties it to a process of its own.

**In this slice the loop runs inside the API process.** The key that opens the vault lives only in the memory of the API process (ADR 0006 and 0018: sealed on start, unsealed by a person), so a process of its own, such as `apps/worker`, could not read an SSH key, a panel token or a secret handed to a run. Letting it do so is a decision about the threat model of the vault (a second unseal, or a channel that carries decrypted values between processes) that this ADR does not take. So the API hosts the loop, as it hosts the runners of commands and checks today: a module of `apps/api` provides the `RunStore` over Prisma (`packages/db`), the SSH, panel and vault adapters, the configuration and the shutdown. The HTTP handlers create and read runs through the same tables and the pure parts of the engine; the loop, started with the application, executes them.

A step reaches a secret only through the secrets port, which the API implements with the one door of the vault (ADR 0042: a sealed vault answers first, then the expiry rule). A sealed vault does not fail a run, it makes it wait (`waiting: vault_sealed`, the way the commands runner waits, ADR 0038), and after a restart of the API the runs that were going on resume once the vault is unsealed. No decrypted value is part of a run's row, checkpoint, event or output.

`apps/worker` stays a skeleton. The lease, the fence, the locks and the `RunStore` are written so that several loops can work on the same tables, in one process (the tests do that) or in several, so moving the loop into `apps/worker` later needs one more decision only: how that process gets secrets. The Prisma schema, the contracts of the run routes and the permissions come with the first code that uses them, not in this ADR.

### How it is tested
The golden and the fault tests of design §13 are part of the core, not a later addition:
- **Pure parts**: the transition table exhaustively; the planning of a run; the order of the undo.
- **Golden scenarios** over fakes and a fake clock: a fixed input gives fixed events, a fixed order of steps and fixed undo records.
- **Fault injection on a real PostgreSQL** (the CI service; PGlite cannot show behaviour under concurrent transactions, which is the point): a worker that is killed at each named point (before the intent, after `apply` and before the checkpoint, after the checkpoint, in the middle of an undo, while holding a lock) and restarted, ending with the same journal and each effect done once; two workers where the first one's lease has expired while it is still alive (the fence must stop it); a lock contested by two runs; a lost `LISTEN/NOTIFY` (polling alone must be enough).
- **The lab** (`P-016`, objects tagged `sw-lab`): the acceptance of the phase, with a real panel and real nodes.

## Consequences
- The run is always what PostgreSQL says. A run cannot be lost with a queue, and a restart of everything is a restart of workers that find the same rows.
- The cost is polling and the load it puts on one table; `FOR UPDATE SKIP LOCKED` and an index on the claimable states keep it small, and the interval is a setting.
- A lock and a checkpoint share a transaction, so the fence is a real guarantee; it does not make a stalled worker's step on a server disappear, and the idempotency of steps is therefore a **requirement on every step author**, tested by the fault suite for every step the engine ships.
- ADR 0005 is narrowed, not reversed: no external engine, durable checkpoints, resume, approvals bound to the plan. Valkey and BullMQ are out of this slice.
- The API process hosts three loops: the runners of commands and checks (ADR 0038, 0045), which stay as they are, and the engine. The documentation says which is which. A run that needs a secret while the vault is sealed waits, and so does every run after a restart of the API, until a person unseals the vault.
- The engine can move into its own process later without changing a step or a table, once the question of secrets for that process is decided.

## Not built here
Approvals and the enforcement of policies P-001 to P-016; the panel write client (its own ADR, it is the first code that changes the panel); the workflows and their step catalogue; rollout strategies (canary, waves) and health gates; schedules and windows; the run screens; metrics; moving `CommandRun` and `CheckRun` into the engine; the `worker` process and the way it would get secrets.

## Decisions of the owner
Taken on 2026-11-25: the owner approved this text, with the change in item 3, before it was merged.
1. **ADR 0005 is narrowed**, as proposed: PostgreSQL only, no Valkey or BullMQ in this slice. Valkey stays what it is today (the readiness check). The alternative, BullMQ as the wake-up with PostgreSQL as the truth, would add a dependency to review and a second place that can disagree.
2. **An interrupted step that is not idempotent waits for a person**, as proposed. Retrying by itself is not offered.
3. **No `worker` service in the compose file in this slice.** The proposal was one more container from the same image. It is replaced by running the loop in the API process (see "Where the code lives"), because the vault key is in no other process. The compose file does not change; a `worker` service comes with the decision on how a separate process gets secrets.
4. **Policies P-001 to P-016 get an ADR of their own**, with a proposal for each (which are on by default, which only warn), before any code that enforces approvals.

## The first slice: what the pure core decided
The pure core (`packages/engine`, no database) had to settle some points that the text above leaves open. They are in the tables and covered by tests; a later slice that disagrees changes the table and the test together.
- **A paused run goes back through `queued`.** Pausing lets go of the lease, so resuming puts the run in the queue and a worker claims it again; the design diagram had `paused → running`. The same applies to a run that waits for a lock or for the vault (`running → queued`, event `wait`).
- **`claim` is the only event that starts or continues the work of a worker**: `queued → running`, `rollback_requested → rolling_back`, and `running → running` or `rolling_back → rolling_back` when another worker takes over after the lease expired. The database applies it as the statement that also bumps the fence.
- **A `succeeded` run has no way back.** Undoing a run that finished is not a transition of the same run; whether it is a new run that undoes the old one is for the ADR of the workflows. `rolled_back` is final too; `rollback_partial` goes back to `rollback_requested`, because a rollback can be resumed.
- **`awaiting_input` leaves by `retry`, `mark_done`, `request_rollback` or `cancel`**: the three choices of a person from "A checkpoint is one transaction" and the way out.
- **Recovery of an interrupted step**: a person who chose to retry wins; otherwise a step that declares `reconcile` is asked first, even when it is idempotent; the answer `done` records the success without running `apply`, `not_done` runs it again (safe even for a step that is not idempotent, because nothing was done) and `partial` runs it again only when it is idempotent. A step with no `reconcile` is run again only when it is idempotent.
- **Locks are taken in one order** (`panel`, `dns-zone:`, `server:`, `node:`, then by id), all or nothing: a run that has to wait holds none, so it cannot keep another run from working.
- **The approval hash** covers the workflow key, the parameters, and for every step its place, key, locks and planned changes; it does not cover a step's title or estimate, which only describe it. The text that is hashed is strict canonical JSON (a value JSON cannot say is an error, not a `null`), and a golden test pins the hash so that a change of format is a deliberate one: it voids the approvals that exist.
- **Left open**: how a rollback executes an undo record (the contract has `undo`, which declares the records at the checkpoint; the executing side comes with the loop), and the event names of the run's timeline.

## The second slice: the loop on a store
`packages/engine` now has the port the loop and the people use (`RunStore`), the store in memory that is its reference (`MemoryRunStore`), the loop (`Worker`) and a suite of tests that every store runs (`@swellwright/engine/testing`, `runStoreContract`). The store over PostgreSQL comes next and has to pass the same suite. What the loop and the port settled:
- **Every rule that makes the engine safe is a rule of the port**, so that no store can forget one: a write of a worker carries its `Claim` (run, worker, fence) and is refused with `FenceLostError` when the row has another fence, another worker, or a state in which nobody holds the run (a worker that was restarted with the same id is not the stalled one); a person's event is a compare-and-set on the state the person saw and is refused while a worker holds the run (a cancel or a pause of a held run is a flag that the worker reads when it renews the lease); the time is given, never read.
- **The locks of a run are those of its plan, taken together at the claim and held until the run lets go.** The loop takes them in one operation (all or none, in the fixed order); a run that cannot waits as `queued` with the reason on it and a `retryAfter`, so it is not claimed again at once and the runs behind it are not starved. A write that changes a step (the intent and the checkpoint) also checks that every lock of the run is still the run's, with its fence, and fails with `LockLostError` otherwise: a worker that stalled after another run took its expired lock cannot record anything, even though its own fence is still valid.
- **A step that cannot go on yet** (the vault is sealed) throws `StepDeferredError` before any effect; the step goes back to `pending` (new step event `defer`) and the run waits. A step that fails throws `StepFailure` with a code, or is given the code of the phase it failed in (`step_error`, `output_invalid`, `verify_failed`, `undo_failed`); a failed step ends the run as `failed`, and a retry puts the failed steps back to `pending`.
- **A step's input is part of the plan**: the plan stores what each step is given, the step parses it with its own schema before use, and it is part of the approval hash.
- **The timeline has names**: `run.created`, `run.<event>` for every event of the table (`run.claim`, `run.succeed`, ...), `run.cancel_requested`, `run.pause_requested`, `step.<event>` and `locks.acquired`.
- **Tests**: golden (a fixed input gives fixed events), a worker killed at each of six points (after the claim, after the locks, before the intent, after the intent, after `apply`, after the checkpoint) for each step, taken over by another worker with each effect once, a stalled worker whose run was taken (it writes nothing and says it lost the run; the step on the server did run twice, which is why steps must be repeatable), contested locks, cancel and pause, a step that cannot be repeated (waits, goes on after a person says it was done or chooses to retry), `reconcile`, and the loop in the background. The fault tests on a real PostgreSQL are the next slice.
- **Not built yet**: the Prisma tables and the store over them; the execution of an undo (the contract has `undo`, which declares the records at the checkpoint; the step that carries them out comes with the first workflow); the wiring into the API process (ports for SSH, the panel and the vault); backoff for retries of network errors; the check that a step's output holds no secret.

## The third slice: the store over PostgreSQL
The tables of "The data" exist as the migration `20261125000000_create_runs` (`runs`, `run_steps`, `undo_records`, `run_events`, `resource_locks`, with the enums `run_state`, `run_risk`, `run_step_state` and `undo_record_state`) and `PrismaRunStore` in `apps/api/src/engine` implements the port over them. It passes `runStoreContract`, and `runWorkerScenarios` (the loop's scenarios, moved out of the engine's tests into the same `@swellwright/engine/testing`) runs on it as on the store in memory. What it settled:
- **A run is serialised by an advisory lock named after it, not by `SELECT … FOR UPDATE`.** Every operation starts by taking an advisory lock of the run (`pg_advisory_xact_lock(<namespace>, hashtext(<id>))`, see "The review of the fourth slice" for the two integers) and then reads the row, so everything written about one run happens one operation at a time, the event numbers have no gaps and the fence is checked on the row as it is after the lock. `claimNext` takes the oldest runs that can be taken (the window is twenty) and the first whose lock it gets at once (`pg_try_advisory_xact_lock`), then applies the rule of `isClaimable` again to the row it now holds, because the run may have changed between the look and the lock. It does what `FOR UPDATE SKIP LOCKED` does (several loops poll one table without waiting for each other) and needs no SQL that names a table, so it works whatever the schema of the connection is. A collision of the 32-bit hash only makes two runs wait for or skip each other for one operation. The ADR's text above named `FOR UPDATE SKIP LOCKED`; this is the way it was done.
- **The locks of a run are taken under advisory locks per resource, in the fixed order of the keys,** after the lock of the run: an operation holds the lock of one run and then those of its resources in order, so two operations cannot wait for each other. The rows are then read and `planAcquisition` decides, as in memory.
- **The database keeps some of the rules itself** (`CHECK` constraints): the fence is not negative, a run has a worker and a lease together or neither, a step's place and attempts and an undo record's place are not negative, an event number is from 1.
- **Times are given, never defaulted:** `created_at` and the others have no `now()`, because the clock is a port of the engine.
- **What only a real server can show** is in the API's tests and skipped where the server runs one connection (`SW_TEST_DATABASE_POOL=1`): many loops claiming the same queue claim each run once, two runs that ask for one lock at the same moment get it one at a time, and people who answer one run at once get one winner and an event log in order. The rest runs on any PostgreSQL.
- **Not built yet:** the wiring of the loop into the API process, undo execution and the lab acceptance.


## The fourth slice: the loop in the API process
The loop now starts and stops with the application (`EngineRunner` in `apps/api/src/engine`), a run can be made from a workflow, and a sealed vault makes a run wait. The design was drawn by Codex (read only) and checked against the code; what it settled:
- **One worker per slot, started with the application and stopped before anything it uses.** `SW_ENGINE_CONCURRENCY` (1 to 4, default 1) loops, each doing one run at a time, with ids made of a random name of the start and the slot, so a process that is restarted is never mistaken for the one that stalled. They start in `onApplicationBootstrap` and stop in `beforeApplicationShutdown`, which Nest calls for every provider before any `onApplicationShutdown`, so the database, the vault and the SSH connections are still there while a step gives up. `SW_ENGINE_ENABLED=false` starts no loop in this process; runs can still be made and stay queued. Without a database there is no loop and no run can be made (503): nothing is put in its place, because a run in memory would be lost at the first restart. Two processes on one database work, as the store already promises; the locks of the engine do not coordinate with those of `CommandRunner` and `CheckRunner`, so this is not yet evidence for a whole API in two copies.
- **Stopping is not finishing the run.** `Worker.stop()` used to wait for the whole run and never reached the step. Now it claims nothing more, aborts the signal of the step in hand with a `ShutdownError` (a person's cancel aborts with another error, so a step that runs something on a server can stop that work for a cancel and leave it running for a shutdown), and stops renewing the lease. A step that gives up leaves the run as a crash would: the step `running`, the lease running out, recovery deciding. A step that finishes anyway gets its checkpoint, and then the run is handed back at the boundary of the step (`queued`, waiting `worker_stopped`, locks released, claimable at once). With `timeoutMs` (`SW_ENGINE_STOP_TIMEOUT_MS`, 8 s) a step that has not given up is left behind and the worker is halted: its store refuses every new call, so the step cannot start a write after the database is closed, and `stop` waits for the calls already on their way for `STOP_DRAIN_MS` (5 s) at most (a transaction cannot be called back through the port; closing the pool waits for one that takes longer); the lease decides, as after a crash. A stop that comes while the run is being read, or while the start of a step is being written, starts no step: the run goes back to the queue. The new scenarios run on both stores.
- **The vault is a port, and a sealed one is a wait.** `EnginePorts` (`packages/engine/src/ports.ts`) has `vault: VaultGate`; `requireOpen()` throws `StepDeferredError('vault_sealed')` when the vault of this process is sealed (or has not been made), and only for that answer: any other error of the vault fails the step. A step calls it before its first effect, because a deferred step is started again from the beginning. A wait that comes later (the reconcile of an interrupted step, `verify` or `undo` after `apply`) does not send the step back to `pending`: the effect may be there, so the step stays `running` and the run waits, and whoever takes it next reconciles or asks a person; an effect that the reconcile finds is verified (`verify`) before it is recorded, and `null` is an output like any other. Such a wait starts no step, so the attempt does not count it: the fence of the run (one for every claim) does, and the wait grows the same way. A run that waits is picked up again by any process whose vault is open. There is no signal on unseal in this slice, only the `retryAfter` of the run: each deferral makes the next wait twice as long, from `SW_ENGINE_WAIT_BACKOFF_MS` (15 s) up to eight times that, so a vault that stays sealed all night is looked at some thirty times an hour and not every few seconds (and a run does not write thousands of events); the cost is that after an unseal a run can wait up to two minutes. Every start of a step counts as an attempt, the deferred ones too. An explicit wake-up on unseal needs a store operation of its own and comes when the waiting is a problem.
- **A run is made from a workflow, never from a plan.** A `Workflow` has a key, a risk, a schema of the parameters and `steps(ctx, params)`, which lists the steps after the workflow's conditions were decided (a workflow lists `StepCall`s, a step key and its parameters; the registry plans every step from its own definition, the one the loop runs, after the input went through the step's own schema, so the locks follow the value the step will act on; an input that schema refuses is an `InvalidStepInputError`). `planRun` checks the parameters, refuses a plan that names a step no registry holds (a run that no worker could finish is never made), builds and hashes the plan. `EngineRunsService.create(key, params, requestedBy)` writes the run as `planned` and queues it, in two transactions: a process that dies between them leaves a `planned` run that no worker takes and a person can cancel. No route calls it, because who may start which workflow and the approvals in front of it are the next ADRs; the catalogue of the build is empty, and the tests bring workflows of their own. Run ids are UUIDv7 (`uuidv7`, made by the caller).
- **The log of the loop tells about trouble once.** What the loop could not handle (the database is down) is logged as its name and a message cut to 300 characters, never the stack, because the error of a driver can carry a statement; the same message is said once a minute. The run is not failed: its lease runs out and another worker takes it over. The events of a run stay in `run_events` only; the audit chain gets the actions of people when there are routes for them.
- **Excluded on purpose, with the reason.** The ports for a server (SSH) and for the panel (reads) come with their adapters. Delivery of the value of a vault secret into a step is not built: the vault's guard against replacing or deleting a secret that a run needs covers command runs only, so it needs durable bindings of secrets to engine runs, an extension of that guard, and the check that the output of a step holds no secret (a schema is not a secret scan). The adapters that open an SSH key or a panel token do it inside the adapter, through the same door, and never hand the value to a step.
- **Tests.** In `packages/engine`: the scenarios of a stop (a step that gives up, one that finishes anyway, one that ignores the signal until the timeout, a stop that comes while the run is read or the step is begun, a write already on its way, a worker that was stopped and starts again), a wait of the reconcile or of `verify` that leaves the step `running`, the growth of the wait after a deferral, the workflows and the plan of a run, `uuidv7`. In `apps/api`, on PostgreSQL: a run from its creation to its end through the loop that the application started, the refusals of `create` that leave no row, a loop switched off, a sealed vault and an unsealed one (the step does nothing while sealed, the run waits with `vault_sealed`, holds no lock, and goes on), the application closing in the middle of a step and the next one taking the run over, two applications on one database doing every run and every step once (CI, it needs several connections), no database, an empty catalogue, and the log. The configuration is tested for its defaults and bounds.
- **Not built yet:** the ports for SSH and the panel, undo execution, delivery of secret values to steps with the check of the output, and the lab acceptance.

## The review of the fourth slice
Before the slice was published the engine and its wiring were read in full by three reviewers (Claude, Codex and Copilot, each on its own). What they found and what it settled:
- **The image carries the engine, and a test holds it to that.** `packages/engine/dist` is copied into the image (the server starts the loop with the application, so without it the container does not start). `apps/api/src/deployment.test.ts` compares the `COPY` lines of the Dockerfile with the workspace packages the API depends on, directly and through the others, and holds `stop_grace_period` of the server in Compose above the default stop timeout plus the drain plus ten seconds, so a new package that is not in the image, or a grace period that is too short, fails a test and not the first start.
- **Stopping is bounded: `timeoutMs` plus `STOP_DRAIN_MS` (5 s).** The wait for the step in hand is `timeoutMs`; the wait for the writes already on their way is the shorter of `timeoutMs` and 5 s, not as long again. Compose gives the server 30 s (`stop_grace_period`), and the comment there says to raise it with the timeout. A halted worker also starts no `verify` or `undo`: the ports of an application that is closing are not touched by a step that was left behind.
- **A rollback is not claimed.** `needsWorker` still says that a run in `rollback_requested` or `rolling_back` wants a worker, but `isClaimable` (the rule of both stores) leaves it alone: the loop goes only forward and would run the workflow's steps that the person wanted undone. It is claimable again when the executor of undo exists.
- **A worker whose lock went to another run learns it at its next renewal.** `renewLease`, `failStep`, `deferStep` and `finishRun` with a failed step check the locks of the plan as `beginStep` and the checkpoint do, and fail with `LockLostError`; the heartbeat aborts the step's signal with it, and the worker gives the run up. Nothing about the step is written by it; whoever takes the run finds the step `running`.
- **The last look before the effect.** After the intent of a step is written the worker renews its lease once more, a write that only the worker that holds the run and all its locks gets through, and reads the flags of the people with it. A worker that stalled after its intent while another worker took the run over and did the step finds out here and does not repeat it. It is not a proof (the worker can stall after the renewal too), so a step that cannot be repeated must also use `ctx.fence` where its target can refuse an old one. A cancel or a pause that came while the intent was written, or that the heartbeat saw during a reconcile, stops the run before the effect: the step goes back to `pending` (`deferStep`, nothing was done) and the run is cancelled or paused. A stop between the intent and `apply` does the same.
- **The output of a step is checked once.** `StepRegistry` gives the worker a `CheckedOutput`: the value the schema produced, and `verify` and `undo` already bound to that value, so what is stored, what is verified and what the undo records are made from are the same, for a schema that changes what it parses, after `apply` and after `reconcile`.
- **The stores keep the same rules, and the loop never repeats a step for a value only the database refuses.** `limits.ts` holds the sizes of the columns and what a `jsonb` or a `text` cannot hold. Canonical JSON refuses a NUL and a lone surrogate in a text or a key (so a plan, an input, an output and an undo record are checked by the code that hashes or stores them). The stores refuse, with `InvalidDataError`, a code or an undo kind that is too long or holds a NUL, and clean and cut a message and a reason (they are diagnostics). The worker checks the output and the undo records before the checkpoint, so such a step fails with `output_invalid` or `undo_invalid` and the run ends, instead of a checkpoint that the database refuses and a step that is repeated every lease for ever; a `StepFailure` whose code does not fit its column fails as `step_error`. What the stores accept is the same in memory and on PostgreSQL (the contract tests hold both). An error of the store that is none of these (the database is down) still leaves the step to its lease.
- **The failure of a step and the end of the run are one write.** `finishRun` takes `failedStep`: the step is written as failed in the transaction that ends the run, so a worker that dies between them cannot leave a run `running` with a `failed` step (the recovery would end it as `engine_state`, not as the failure it was). A run that ended, or stopped for a person, has no request of the people left (`cancelRequestedAt`, `pauseRequestedAt`): a cancel that came too late for a step that failed no longer turns a later retry into a cancel. A pause keeps a cancel, and a wait keeps both, for whoever takes the run; a run claimed with a flag set cancels or pauses before it takes its locks. A worker that asks for a person (`await_input`) or pauses while a cancel is pending does not park the run, because nothing claims a run that waits for a person or is paused and the cancel that was accepted would never be read: the store carries the cancel out in the same transaction (the timeline says `run.cancel`, with what it replaced in its data) and the outcome of the worker is `cancelled`. The same goes for a person's pause of a run that has a cancel kept for it by a wait: a cancel that was accepted comes before a pause.
- **A run that waits for the vault is left to a process whose vault is open.** `VaultGate.isOpen()` says whether `requireOpen` would pass; the runner gives the loop `skipWaiting`, the reasons it cannot serve (`vault_sealed` while this process is sealed), and `claimNext` leaves such runs alone. A sealed process no longer takes the run only to put it back with a later time, which kept an open process from ever reaching it. A run with a cancel or a pause pending is never left (a cancel needs no vault, and a request that was accepted must not wait for one).
- **The advisory locks of the engine have key spaces of their own.** The lock of a run is `pg_advisory_xact_lock(0x53570001, hashtext(<id>))` and that of a resource `(0x53570002, hashtext('resource-lock:<key>'))`; the one-bigint form that audit, setup, plugins and baselines use is another key space, which the two-integer form never meets. The locks of a run's resources are taken in the order of the numbers (each once), not of the names: two names can hash to the same number, and transactions that take `[A, B]` and `[B, C]` by name could then take the same two numbers in opposite orders.
- **A plan and a run cannot disagree about the resources.** A workflow no longer builds step plans: it lists `StepCall`s and `planRun` plans each through the registry that the loop runs, so a step defined twice cannot be planned by one and run by the other. The input is JSON-normalised first and the step's schema parses that, which is what the run will parse, so a schema that tells "not set" from "absent" gives the plan and the step the same value. Still open: persisting a version of the definition with the run, so that a run planned by an older build is interpreted by the definition it was planned with; it comes with the first workflow that changes.
- **A run that waits for a lock waits longer each time**, from the backoff up to eight times it (the fence of the run counts the waits), and the idle loop's sleep leaves no listener on the signal (it left one at every poll, some 86,400 a day).
- **Known limits that remain, and are not hidden.** The locks of a run are released when it waits for a person or for the recovery of a step whose effect is not known, so another run can change the same resource meanwhile (whether to keep them is a decision for the policies ADR). `run_events` has no retention yet. The clock for leases is the claiming process's, so two copies of the API need clocks within a few seconds. `EngineRunner` stops concurrently with the other shutdown hooks of the API (the shared SSH pool closes in its own hook), which matters when the ports for SSH exist.
