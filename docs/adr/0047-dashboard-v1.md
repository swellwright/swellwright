# ADR 0047: Dashboard v1: what needs attention, and the health of the fleet, from what the server already holds

Status: accepted

## Context
Phase 3 gave the console several places that each say something about the state of the system: the connection to the panel and its token (ADR 0041), the expiry of vault secrets (ADR 0042), the snapshots of the panel and what changed since (ADR 0043), the convention linter, the reconciliation of the panel with the inventory (ADR 0044), the baseline checks of servers over SSH (ADR 0045), the history of runs of commands (ADR 0038), the audit chain (ADR 0015) and the update check (ADR 0019). The Overview page showed some of them as separate blocks that each slice had added. Nobody could answer "what should I look at first?" without opening six pages. Phase 3 ends with a dashboard that answers it, built **only** from data Swellwright already holds: no new probe, no new SSH session, no new call to the panel when the page loads.

## Decision

### Two read routes, a projection and nothing else
- `GET /dashboard/attention`: a ranked list of items, each `{ id, fingerprint, severity, kind, source, title, detail, params, since, link }`, plus the counts by severity and the state of every source (`ok`, `not_permitted`, `failed`). Open to every signed-in user and every API token (`auth: any`, on the short list of routes that name no permission, `ROUTES_OPEN_TO_ANY_SESSION`, now eleven): **what is in it depends on what the caller may read**.
- `GET /dashboard/fleet`: one row per server of the inventory (`servers:read`), paged (`limit` up to 100, `offset`), filterable (`q`, `state`, `tag`, `health`, `flag`) and sortable (`health`, `name`, `lastCheck`, `order`).
- Both are cheap and **never call the panel or a server or GitHub**. They read database rows (`SELECT`s) and the memory of this process: the last convention run, the last reconciliation, the update check. A test records zero requests at the fake panel and zero connections and commands at the stand-in SSH hosts while it calls both routes many times as four roles.
- Nothing is stored and nothing is dismissed on the server. The feed is a pure projection; "hide for this browser" is the console's own business (`localStorage`, per user, together with the `fingerprint` of the item, so a hidden item comes back when the facts behind it change: another count, another name, not merely another day).
- A short in-memory cache (`SW_DASHBOARD_CACHE_SECONDS`, 5 by default, 0 for none) keyed by **which sources the caller may read** (the feed depends on nothing else about the caller), and a rate limit per user (`SW_DASHBOARD_RATE_LIMIT_PER_MINUTE`, 120; the console reads once a minute per route and tab). A source that throws is reported as `failed` and the rest is still returned: one broken table never blanks the page.

### The sources, and who may see them
A caller sees the items of a source only when their role (or their token, as far as the role allows) may read it. The table is `ATTENTION_SOURCE_PERMISSIONS` in the contract.

| Source | Permission | Items (kind, severity, link) |
| --- | --- | --- |
| vault | `vault:read` | `vault.secrets_expired` critical (a secret whose `expiresAt` is now or past: the boundary counts, ADR 0042), `vault.secrets_expiring` warning (whole days left, rounded up, at most `SW_DASHBOARD_EXPIRY_WARNING_DAYS`, 14), `vault.sealed` warning, `vault.uninitialized` info; link: Security > Vault |
| panel | `panel:read` | `panel.unauthorized` critical, `panel.token_expired` critical, `panel.unreachable` warning, `panel.unsupported` warning, `panel.degraded` warning, `panel.token_expiring` warning (whole days, **floor**, the way the Overview card says it: 14 days and 23 hours is "14 days"), `panel.not_connected` info; link: Panel > Connection |
| conventions | `panel:read` | `conventions.errors` warning, `conventions.warnings` info, `conventions.not_run` info (a panel is connected and nobody ran the checks since the start); link: Panel > Checks |
| reconciliation | `panel:read` | `reconciliation.drift` warning (drifting + missing + extra from the last run; `info` while the inventory has no servers and the only differences are nodes that have none: that is where everyone starts, and one difference of any other kind keeps the warning; amended 2026-11-24), `reconciliation.undecided` info; link: Panel > Checks |
| snapshots | `panel:read` | `snapshots.stale` warning (older than twice the interval of the background job counting the newest of "taken" and "compared", or `SW_DASHBOARD_SNAPSHOT_STALE_DAYS` days when the job is off), `snapshots.changed` info (`changesSince` > 0), `snapshots.none` info; link: Panel > Snapshots |
| baseline | `servers:read` | `baseline.host_key_mismatch` critical (a run ended `error` / `host_key_mismatch`: the key a server shows is not the pinned one), `baseline.failing` warning, `baseline.unreachable` warning (any other error of a run), `baseline.stale` warning (the newest finished run older than `SW_DASHBOARD_BASELINE_STALE_DAYS`, 7), `baseline.warnings` info, `baseline.never_checked` info; link: Fleet > Baseline |
| servers | `servers:read` | `servers.not_ready` warning (a server in use without a pinned host key or without an access entry; info when only drafts are incomplete; retired servers are left out), `servers.facts_stale` info (a server that can be reached whose facts are older than `SW_DASHBOARD_FACTS_STALE_DAYS`, 14, or were never collected); link: Fleet > Servers |
| runs | `servers:read` | `runs.failed` warning (runs of commands that ended `failed` or `partial` in the last `SW_DASHBOARD_RUNS_WINDOW_HOURS`, 24); link: Operations > Runs |
| audit | `audit:read` | `audit.chain_failed` critical (the newest `audit.chain.verified` record says `failure`, until a later one succeeds), `audit.verify_overdue` info (no verification for `SW_DASHBOARD_AUDIT_VERIFY_DAYS`, 30, counting from the first record when there was none: a chain younger than that is left alone); link: Security > Audit |
| plugins | `plugins:read` | `plugins.switched_off` warning (an approval that is off and whose newest `plugin.disabled` record says `changed`, `missing` or `unavailable`: the plugin was switched off by itself); link: Settings > Plugins |
| updates | none | `updates.available` info (the release the update check already holds is newer than this build); no link; this is public data about the project, like `GET /updates`, which is also open to every session |

Thresholds of 0 switch a check off. Ranking: critical, warning, info; inside a severity by the order of `ATTENTION_KINDS` (what stops things comes before what nags); inside a kind the oldest `since` first, an item without a date last. Each kind appears at most once and its `id` is the kind; the items carry numbers, flags and a few **names** (of secrets, servers, plugins: things the caller may read anyway, at most three, then `more`), never a secret value, an address, a token or a person. A test scans every answer of every role for the secrets, tokens and addresses of the test world.

### The health of the fleet
A row has the facts (time, OS, kernel, stale or not), the newest finished baseline check (`pass`, `warn`, `fail`, `unreachable`, `never`, `unassigned`, counts, trend, whether a check is running), whether a host key is pinned, the state of the access entries (how many, how many usable, how many expired, the newest try and its result), the node of the panel that the last reconciliation matched (name, state, and the time of the reconciliation: it is shown as of then, never refreshed) for a caller who may also read the panel, `flags` (14, each with a level) and a rolled-up `health`: `critical` (a failing check, a host key mismatch, or every access entry expired), `warning`, `ok`, or `unknown` (nothing was checked and no facts exist, and every draft and retired server). Drafts and retired servers are not expected to be set up, so their gaps are not flags. The reconciliation now keeps, in memory with the counts of its last result, which node answers for which server (the surest match when several do: address, then DNS, then host name); a run made without the right to read servers does not replace one that had the inventory. `GET /panel/checks/reconciliation/last` (`panel:read`) gives the counts the way `.../convention/last` does, for the Checks section of the Overview.

### The console
The Overview (`/dashboard/home`, the route table is unchanged) opens with the card of the attention feed (the panel's titled card, rows with a soft icon, a bold line, a dimmed line, the age with the exact time in a tooltip, a link button and "hide for this browser"; grouped by severity; six items and "show more"; an empty layout when nothing needs attention; a note when a source could not be read; skeletons while loading; the buttons drop under the text on a phone), then the sections in one order: **Remnawave panel** (the cards the page already had), **Fleet** (cards by health and the baseline card, over the table of the health of the fleet: the panel's `@kastov/mantine-react-table-open` in a titled card, filters under the head, paged by the server, status chips, links to the server drawer and to the baseline results through `?server=<id>` on those pages), **Checks** (the last conventions and reconciliation), **Snapshots**, **System** (the API and its dependencies). A section whose source the role may not read, or that is not set up (no panel), is not drawn; each reads its own endpoint, so a failure is shown in its place and the rest stays. The page asks again every minute while the tab is visible (React Query pauses in the background) and has a refresh button on the first card with the panel's loading state; that refresh reads this server's records again and never forces a read of the panel (the Panel section keeps its own button for that).

### Where the page still reads the panel
The Panel section's numbers come from `GET /panel/overview`, as before this slice. That read is served from the memory of the server (`SW_PANEL_CACHE_TTL_SECONDS`) and asks the panel again only when that memory is older; it is not new, and it is not what the two dashboard routes do.

## Consequences
- One place answers "what needs attention" for every role, and an operator who may only read servers sees servers, not the vault.
- The feed is only as fresh as the records: the memory of the last conventions run and reconciliation is lost at a restart (the dashboard says "not run yet" for the former and nothing for the latter), a snapshot job that is off makes the staleness a number of days, and the node of a server is shown as of the last reconciliation. This is stated in the API description and in the console.
- `ROUTES_OPEN_TO_ANY_SESSION` grows to eleven; the test that keeps it short now allows eleven and names the reason.
- Nothing about this slice changes the data model: no migration.

## Not built here
Alerts and notifications (the monitoring slice), dismissals shared between people, the daily availability picture, probes, per-section customisation, a WebSocket (the page polls), history of the feed.
