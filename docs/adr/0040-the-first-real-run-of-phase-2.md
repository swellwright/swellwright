# ADR 0040: The first real run of phase 2: what a reset Ubuntu server found

Status: accepted

## Context
Everything of phase 2 (the inventory, the SSH layer, the node installer artifact, servers over SSH, commands and the script library, artifacts and their distribution; ADR 0034 to 0039) had been tested against in-process servers, a real `sshd` in a container in CI and, read-only, three production nodes. The owner then reset a disposable foreign server (a fresh Ubuntu 24.04, one vCPU, 2 GB, root with a password) and allowed every scenario on it. They were run for real through a development stand (the API and the console, the vault in the stand's own database), one after the other: the inventory and the SSH wiring (scan, pin, access entries with the root password and a key as vault secrets, verify, facts, a regenerated host key and the replace flow), the commands (every built-in script, inline commands, sudo, the confirmation levels, parameters with hostile values, a long step and its cancel, a time limit, the API killed in the middle of a run, the connection dropped by killing the `sshd` session and by a firewall rule, the vault sealed during a run, two servers in one run), the artifacts (user and system destinations, tampering, deletion, a wrong pinned key), the node installer through Swellwright step by step (`preflight`, `base`, `system`, `hostname`, `firewall`, `fail2ban`, `docker`, `apiacl`, `certsync`, `nginx`, `haproxy`, `node`, `verify`, `ssh`, `rename`, and `full` on the finished node, each step twice with a hash of every file before and after), and the failure handling. The server was compared with its own tools (`ss`, `ufw status verbose`, `haproxy -c`, `nginx -t`, `docker ps`, `sshd -T`, `fail2ban-client`, `sha256sum`) and with `/var/log/auth.log`. The password of the server and the private keys never left the vault, the stand and the scratch directory: the API log, the audit export, every run view and every server view were searched for them afterwards, and none had them.

Most of it worked as designed. Six defects did not show up in any test, because every one of them needs a real server, and are fixed here; three behaviours are reported for a decision.

## Defects found and fixed

**1. A server that gained a host key of another type looked like another machine.** A real `sshd` has a key of every type and shows the type the client prefers (ed25519). The first scan of this server found only an RSA key and pinned it; after `ssh-keygen -t ed25519` and a restart every operation answered `host_key_mismatch` ("somebody may be answering in its place") and a scan said `differs`, although the pinned RSA key was unchanged. The connection and the scan now prefer the key types that are pinned (ADR 0035), so the server shows the pinned key while it still has it. A key that changed is still refused before any credential is sent (the in-process server now has several host keys, and the tests pin each case: RSA pinned beside ed25519, the pinned type gone, the pinned type changed).

**2. Cancelling a sudo run on a login that is not root did nothing.** `cancelStep` and `removeStep` look for the step below `$HOME`, and the sudo of Ubuntu gives the command root's `HOME`: the step was looked for in `/root`, "not found" was an answer, not an error, and so the run was marked `cancelled` while the script ran to its end, and the step directories of every sudo run stayed on the server for ever. Every node of the fleet has a login that is not root and uses sudo, so this was the common case, not a corner. The home of the login is asked first (ADR 0035). The stand-in sudo of the tests kept the caller's `HOME`, which is why the suites passed; it can reset it now, and the step scenarios (which also run against a real `sshd` when one is configured) have a case for it.

**3. Pushing an artifact to the system directory failed on a server that had run steps as root.** The step layer creates `/var/lib/swellwright` as 0700 when it runs as root. The push looked at the destination over SFTP as the login before it sent anything and failed with `stat failed: Permission denied`; the check of a copy failed the same way. Everything about a system copy is asked as root now, and the install command makes the whole chain root-owned and 0755, as the decision of ADR 0039 says (ADR 0039). The artifact test host has a switch for a root-only parent, and the in-process SFTP server can refuse paths, so the test fails on the old code with the very message of the real server.

**4. The installer waited fifteen minutes for a daemon, on every apt call.** `apt_wait` waited for any process called `unattended-upgr*`, and the watcher of that package (`unattended-upgrade-shutdown`) runs for as long as an Ubuntu machine is up and holds no lock; the first `apt-get update` waited 15 minutes and so would every call. After an upgrade the daemon of PackageKit stayed for five minutes, and the last install waited for it (5 min 02 s measured). Installer 1.0.1 asks the lock files (`fuser`) when it can, and without it tells a run of `unattended-upgrade` from the watcher by its command line. The test double of `pgrep` has a process table now, with the three cases (the watcher, a run, the daily job) and one with `fuser`.

**5. The installer glued its line to the last line of `/etc/hosts`.** The file of this provider's image has no final line break, and `hostname` appended `IP name short` to it: the line of the machine itself became `198.51.100.7 vm-name198.51.100.7 test1.example.com test1`, its host name was garbled (`hostname -f` printed it) and the node's own mapping was lost. The same append is used for the `authorized_keys` of the administrator and by `rename`. A helper adds the line break first (`append_line`); three tests.

**6. `rename` left four new backups on every run.** The step backed up and rewrote its three files and `/etc/hosts` whether or not the rename changed them, against the README ("never rewrites a file with the same content"); and its restore after a refused configuration took the newest backup, which with an unchanged file would be an older rename's. A file is now touched, and backed up, only when it changes, and a refused configuration restores only what this run changed.

## Verified, and worth saying
- The fingerprint of the scan equals `ssh-keygen -lf` of the server's key; every fact of the facts script (OS, kernel, hostname, uptime, boot time, memory, swap, disk, time and synchronisation, failed units, listening ports, services, ufw, `sshd -T`, upgrades) matched what the server says by its own commands, and the console showed the same after a refresh.
- A host key that is not the pinned one, on every operation (verify, facts, push, run): the server's log has only `[preauth]` disconnects, not one authentication line.
- The step layer survived everything done to it: the API process killed and restarted in the middle of a 60 s run (the output of the two servers was complete and contiguous, 60 lines each, after the vault was unsealed), the `sshd` sessions of the login killed, a firewall rule that dropped the API's address for 14 s (and for 40 s, long enough for the run to say `waiting: ssh_timeout` and to go on when the server answered again, with its output complete), a time limit (143 and `timeout`), a cancel.
- Hostile parameter values (quotes, `$(...)`, backticks, a newline, `-n`, `--help`, a backslash sequence, non-ASCII) came back verbatim from a real shell, through sudo as well, and no file appeared.
- The installer's steps are idempotent on a real server: the second run of each step changed no file and no service (only the container, which could not start without a panel, flapped); `full` on the finished node ran in 31 s and changed only what its parameters changed. The checks of `verify` agreed with the server (`ss`, `ufw`, `iptables`, `haproxy -c`, `nginx -t`, `docker ps`, `sshd -T`): HAProxy answers a foreign or missing SNI with the decoy's 404 and the node's SNI with a closed connection (no Xray yet), the node API port does not answer from an address that is not the panel's, and the key of `certsync` is `command="rrsync /opt/certs/",restrict ...` and refuses `id`, `ls`, a shell and a pty.
- `ssh` refuses to close password login while no member of the sudo group has a key, and after it ran root and password login are refused by the server (`BadAuthenticationType`, only `publickey` allowed) while the key of the administrator and its sudo go on working.

## Reported for a decision, not changed
- **The expiry of a secret is only a label.** A secret whose `expiresAt` is in the past still logs in to a server. Nothing documents what expiry means; enforcing it needs an error code and a decision about runs that are already going.
- **A vault secret cannot be handed to a run.** The node's `SECRET_KEY`, or the password of a new administrator, has to be typed into the command or a parameter, and a run stores both in plain text (the console and ADR 0038 say not to). The installer reads `--env-file`, so a stored-secret mechanism (a secret file written by the runner for the length of a run and removed) is the natural next step. *Follow-up: the installer half exists since 1.0.2, every secret parameter can be given as `NAME_FILE` (ADR 0036); the runner half (writing the file for the length of a run) is a later slice.*
- **Closing root login needs a member of the sudo group, not a member who can log in.** On this server an account of the hosting provider was in the group (no key, unknown password), so `ssh` closed root login although the administrator that Swellwright knew had just been taken out of the group; only the closing of password login checked for a key. It is what the README says, and the first line of the step warns; a stricter rule (at least one member with a key or a usable password) would also refuse this case. The way back worked: the administrator's key, then `su` with the root password. *Follow-up: fixed in installer 1.0.2, see below.*

## What this run could not show
Debian 12 (only Ubuntu 24.04 was available), the node container working (it needs a real panel; with a syntactically valid fake key it pulls and starts and says `SECRET_KEY contains invalid JSON`), the real certificate delivery, a second reset to run `full` on, and a refused (not filtered) port as the SSH layer sees it: the development machine reaches the server through a VPN tunnel that answers the connection itself, so a closed port and an unrouted address both read "connection lost before handshake" (the unit tests cover the refusal), and a filtered port reads `ssh_timeout` after 15 s as documented.

## Consequences
- The installer is version 1.0.1; the manifest and the README tables are regenerated. A released version is still never edited: 1.0.0 had not been given to a fleet.
- The in-process servers of the tests learned two things a real server does and they did not: several host keys, and a directory that only root can enter; the stand-in sudo can reset `HOME`.
- Phase 2 is now accepted against a real Ubuntu server for everything in this ADR; Debian and a real panel remain for the first production node.

## Follow-up: who counts as an administrator (installer 1.0.2)
The third item above is fixed. The `ssh` step no longer treats a member of the `sudo` group as an administrator: it closes root login, and password login, only when an account can really log in, one function for both closings (`ssh_admin_check`). An account counts when it exists and is an ordinary account (not `root`, not `certsync`, a user id of `UID_MIN` to `UID_MAX`), sshd lets it in with a key (`sshd -T -C user=NAME,host=localhost,addr=127.0.0.1`: public-key login on, `AuthenticationMethods` does not ask for more than a key, and `AllowUsers`, `DenyUsers`, `AllowGroups` and `DenyGroups` do not exclude it), it is not disabled (a real login shell, no passed expiry date or inactivity period, a locked password only when sshd uses PAM), sshd would read a valid key that gives a shell (the file named by `AuthorizedKeysFile`; with `StrictModes` the file, `~/.ssh` and the home belong to the account or root and are not writable by group or others, the account can read the file; at least one line passes `ssh-keygen -l` and has no `command=` and no `restrict` or `no-pty` that no later `pty` undoes) and it can become root (sudo installed, not refused by sudoers, a usable password or a `NOPASSWD` rule). The step shows who counts and, for every other candidate of the group, the first rule it fails, before it closes anything; a refusal is exit code 1 and lists them; `verify` has the same list as a check. Not recognised, on purpose: keys from `AuthorizedKeysCommand`, certificates, and accounts that are not in the `sudo` group; on such a server the step refuses and root login stays open, and there is no bypass.

**Verified on the same disposable server** (Ubuntu 24.04, OpenSSH 9.6), with the installer file checked against its hash on the server, and a second root session, a copy of `/etc/ssh` and a systemd timer that would restore it kept as the way back:
- The state that made 1.0.1 lose access (the group lists an account of the hosting provider that `passwd` does not know, and a leftover administrator without a key): `verify` says `none, the ssh step would not close root or password login` with both reasons, and the `ssh` step in the root phase refuses, with either closing and with the default parameters, exit code 1, `/etc/ssh` byte for byte as before.
- A throwaway administrator made by the user phase with `NEW_USER_PASSWORD_FILE` (a root-owned 0600 file without a final line break): the step reports it, the key login from the development machine works, and so does `sudo`. The hardening then closes root and password login in one run; both logins are refused by the server (`publickey` is the only method offered), the key login and `sudo` go on working, and the way back was that administrator (key, `sudo`), which restored `/etc/ssh` byte for byte and root login.
- Each rule against what the real sshd does: an expired account is refused by PAM with a valid key (the installer says so); a locked password still logs in by key (the installer refuses it only because `sudo` would then ask for a password it does not have); a forced `command=` runs instead of a shell; `restrict` still lets the key run commands (the installer does not count it, it gives no terminal); `nologin` accepts the key and ends the session; a home directory, `~/.ssh` or key file that is world-writable, or group-writable by a group with another member, is refused by sshd, as is a key file owned by somebody else, root-owned with mode 0600, or with mode 000; `AllowUsers`, `DenyGroups` and a `Match` block that turns public-key login off are all seen through `sshd -T -C user=...` (it prints one `allowusers` line per entry) and refused by the server too.
- One place where sshd is more lenient than the installer: with `StrictModes` on, OpenSSH 9.6 accepts a group-writable home directory, `~/.ssh` or key file when the group is the account's own private group with no other member. The installer refuses any group write; it cannot know which sshd build answers, and a wrong yes loses access (`chmod g-w` is the fix, and the README says so).
- The `_FILE` refusals (mode 644, both given, a symbolic link, a missing file) and that neither the password nor the value given the plain way reached the journal.
- The whole suite (200 tests under `dash`) and shellcheck ran on that server as an unprivileged user; the same suite fails 59 of the 71 new tests against 1.0.1 (the other 12 are the cases that must still pass).
The server was put back as it was (the throwaway account and its files, the keys, the timer, the runtime fail2ban exception for the test machine and the temporary package are gone; root and password login are open again).
