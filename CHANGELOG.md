## [Unreleased]

### Added
- Phase 4, first slice of the engine: the pure core in `packages/engine` (ADR 0048; no database, no loop, no I/O). The state of a run (13 states, 17 events) and of a step (7 states, 9 events) are tables behind one pure `transition` that throws an `InvalidTransitionError` naming the state, the event and what the state would take, never a silent no-op; the tables are checked when the module loads and tested against every state and event, for reachability and for a way to an end from every state, and the run diagram in `docs/en/architecture.md` is now that table edge by edge, read by a test that fails when they differ. Resource locks (`panel`, `dns-zone:`, `server:`, `node:`) in one fixed order and an all-or-nothing decision over the rows that are held, lease and fence arithmetic (a lease of three renewal intervals, a write accepted only with the fence on the row), the plan of a run with its approval hash (strict canonical JSON, SHA-256, a golden hash that pins the format; the title and the estimate of a step are not part of it), the order and the verdict of an undo (`rolled_back` only when every record is done and the workflow's check finds no difference), the recovery of a step that a crash left running (reconcile first, repeat only what is idempotent, otherwise wait for a person) and the step contract with `defineStep` and the id of a step on a server. `@types/node` is a dev dependency of the package (already in the lockfile at the same version); no new package.
- Phase 4, the engine core decided (ADR 0048, accepted; no code yet): runs, steps, undo records, events and locks live in PostgreSQL only (ADR 0005 is narrowed: no queue library in the first slice), a worker claims a run with a lease and a fence token, a checkpoint is one fence-checked transaction, and in this slice the loop runs in the API process because the vault key lives in no other process (a separate worker waits for a decision on how it gets secrets). The architecture, design and status documents (English and Russian) say the same.
- Shared contributor instructions and UI skill for Codex and Claude Code, current implementation status and development/validation guides in English and Russian, and a dependency-free `pnpm run doctor` preflight for toolchain and workspace links.
- Phase 3, dashboard v1 (ADR 0047): the Overview page is a dashboard built only from what the server already holds (no call to the panel, a server or GitHub). `GET /dashboard/attention` (open to every signed-in user and token) is a ranked list of what needs attention, from the sources the caller may read: the vault (sealed, secrets expired or expiring within `SW_DASHBOARD_EXPIRY_WARNING_DAYS`, 14), the panel connection and token, the last convention run and reconciliation, the snapshots (stale, changed, none), the baseline checks (failing, host key mismatch, unreachable, stale, never checked), servers without a pinned key or an access entry and old facts, failed runs of commands, the audit chain (failed or not verified for 30 days), plugins that switched themselves off and a newer release; 32 kinds, each with a severity, a stable id, a fingerprint that changes with its facts and a link to the console page that deals with it; a source that fails is reported and the others are still returned. `GET /dashboard/fleet` (`servers:read`) has one row per server with health, flags, facts, the newest baseline check, host key, access entries and the node the last reconciliation matched, paged and filtered. `GET /panel/checks/reconciliation/last` gives the counts of the last reconciliation from memory. A short cache and a rate limit per user (`SW_DASHBOARD_CACHE_SECONDS`, `SW_DASHBOARD_RATE_LIMIT_PER_MINUTE`) and thresholds (`SW_DASHBOARD_BASELINE_STALE_DAYS`, `_FACTS_STALE_DAYS`, `_SNAPSHOT_STALE_DAYS`, `_AUDIT_VERIFY_DAYS`, `_RUNS_WINDOW_HOURS`). The console opens with a "Needs attention" card (grouped by severity, six items then "show more", an empty layout, "hide for this browser" per user that comes back when the facts change), then the sections Panel, Fleet (cards and a table of the health of the fleet in the panel's table card, with links that open the server drawer and the baseline results), Checks, Snapshots and System, each read from its own endpoint and left out when its source is not permitted or not set up; the page reads again every minute while visible. OpenAPI 0.31.0; texts in English and Russian.
- Phase 3, baseline checks of servers over SSH, read-only (ADR 0045): a baseline is a versioned document of checks (YAML or JSON, one Zod schema, `docs/en/baselines.md`, an example in `examples/baselines`) over a closed catalogue of 31 read-only observations and 12 comparators; one POSIX `sh` script (`apps/api/src/baseline/observe.sh`) runs as one detached step in one SSH session per server and prints a strictly parsed document that a value cannot forge (every line of a value is behind `| `), and never prints a secret (names of container variables, fingerprints of keys, hashes of files). Runs and results are stored (`CheckRun`, `CheckResult`; the newest `SW_CHECKS_KEEP_RUNS` per server), with the drift between two runs and a trend, one run per server at a time under an advisory lock, `SW_CHECKS_PARALLELISM` at once, and a server that cannot be observed ends as `error` with the code (host key changed or not pinned, login refused, expired secret, sealed vault, timeout, output that is not the script's). Baselines are immutable versions assignable to servers or tags; two ship built in (`linux-generic`, 28 checks; `node-selfsteal`, 64 checks, the facts the node installer's `verify` checks). Fourteen routes (`GET /baseline-catalogue`, `/baselines`, `POST /baselines/validate`, `PUT /baselines/{id}/assignments`, `POST /servers/{id}/baseline-runs`, `POST /baseline-runs`, `GET /baseline-runs/{id}/diff`, `GET /baseline-fleet`, ...; OpenAPI 0.30.0): reading is `servers:read`, starting a run is `servers:exec` with a fresh code, editing is `servers:write` with a fresh code; audit actions `baseline.run`, `baseline.run.finished`, `baseline.version.created`, `baseline.assigned`, `baseline.deleted` hold no observed value. An optional schedule (`SW_CHECKS_INTERVAL_HOURS`, off by default; staggered; skipped while the vault is sealed or a secret has expired). Settings `SW_CHECKS_KEEP_RUNS`, `SW_CHECKS_PARALLELISM`, `SW_CHECKS_INTERVAL_HOURS`, `SW_CHECKS_TIMEOUT_SECONDS`, `SW_CHECKS_POLL_MS`, `SW_BASELINE_RATE_LIMIT_PER_MINUTE`. Console: Fleet > Baseline (the panel's header card, four metric cards, the fleet datatable, a drawer per server with the drift and the results by category, a dialog to start checks, the baselines drawer with a Monaco editor that underlines the problems, versions and assignment), a card in the server drawer and a metric on the Overview; English and Russian.
- Phase 3, the API console (read) (ADR 0046): Panel > API console lists the 218 operations of the frozen description of the panel's API (3.4.11, `packages/remnawave/spec/`, built into a catalogue at first use and shipped in the image) grouped by the panel's own tags, and sends the reads among them. A request is `{ operationId, pathParams, query }` (`POST /panel/api-console/requests`, permission `panel:console` for the owner and the operator, a session only), never a URL or a header: the values are checked against the types of the description (UUID, date, date-time, e-mail, enumerations, numbers with their bounds, path segments without separators, escapes, `..`, `@` or `:`), a parameter the operation does not list is refused, and the transport refuses any path that leaves the panel's origin and prefix. Only the 94 GET operations can be sent: 7 (the node secret key, key generation, connection keys, subscription bodies, two passkey challenges) are blocked, the 124 that change the panel are listed greyed and wait for phase 7, and the 28 about the people who use the panel are off unless `SW_PANEL_CONSOLE_USER_DATA=true` (then they need `vault:reveal` and a fresh second factor, and the call is recorded before the answer is delivered). The answer is the final answer of the panel whatever its status (new `PanelHttp.getRaw`), with only `content-type`, `content-length`, `retry-after` and `x-ratelimit-*` headers, the exact token and every secret masked (new `maskSecrets` options `extraSecretKeys` and `people`, the access material of users, a profile for answers about people that also hides names, mail, device ids, addresses and UUIDs, `vmess://` and `ss://` payloads), cut to `SW_PANEL_CONSOLE_MAX_BODY_KIB` and shown in read-only Monaco with a schema tab; the history of the last 20 calls and named samples are kept in the browser only. Rate limited per user (`SW_PANEL_CONSOLE_RATE_PER_MINUTE`), recorded as `panel.console.request` (operation, path with placeholders, names of the query parameters, status, time, masked count; never a value, the body or the token). New error codes `console_operation_unknown`, `console_operation_blocked`, `console_user_data_disabled`, `console_response_too_large`, `console_response_unsupported`; OpenAPI 0.27.0; no dependency added.
- The computed configuration of a config profile has a budget of its own (`SW_PANEL_COMPUTED_RATE_LIMIT_PER_MINUTE`, 30 a user a minute) instead of counting as a forced refresh: a burst of `?refresh=true` reads no longer makes it answer 429 for a minute (found on the real panel; ADR 0046, note on ADR 0041).
- Phase 3, the convention linter, reconciliation and the impact calculator (ADR 0044): `packages/conventions`, pure functions over what the panel reported (no I/O, no write client), with a pattern engine that cannot take exponential time (a Thompson automaton for a safe subset of regular expressions, whole-value matching, refused at save time), RFC 6902 JSON Patch and a canonical form for hashing. The conventions are data: a convention pack `swellwright.conventions/v1` (YAML or JSON, strict schema, rules by id with `enabled`, `severity`, `params`, `scope` and `note`, a pack scope, reconciliation settings, impact thresholds), stored as versions in `convention_packs` (the text as written, the validated document, the SHA-256, a comment, one active version, a conflict check on save), the built-in pack without any installation data, an example pack with placeholders in `examples/conventions/`, and the audit records `panel.convention_pack.saved` and `panel.convention_pack.reset` in the same transaction as the change. Thirty rules for hosts, nodes, profiles, squads, templates and the token of the connection (a rule whose resource the token cannot read is skipped and listed, a rule that throws is isolated and listed, at most 5000 findings), findings with a message key and parameters, JSON Pointers to the fields involved and fix hints that nothing applies. Reconciliation of hosts, nodes and the server inventory, check only, with eleven checks, statuses `ok`, `drift`, `missing`, `extra` and `unknown` (a name that did not answer is a row, not an error), DNS looked up under a timeout, a cap, a concurrency limit, a CNAME chain limit, a short memory and a rate limit, through an injectable resolver and the address policy of the SSH layer. The impact calculator, a dry run of a change to a profile, an internal squad, a host, a node or a template given as fields or as a JSON Patch: the restarts with the rule behind each, a versioned rule table with the basis (observed, documented, assumed) of every rule, hosts and subscriptions that change, dangling references, users online, findings introduced and fixed, a risk level with its reasons and the safer way (clone a shared profile). Routes `GET /panel/checks/rules`, `/convention`, `/convention/last`, `/reconciliation`, `GET`, `PUT` and `DELETE` `/convention-pack`, `/convention-pack/versions`, `POST /convention-pack/validate`, `GET /panel/impact/target` and `POST /panel/impact` (reading with `panel:read`, writing the pack with `panel:write` and a step-up), OpenAPI 0.25.0, `SW_CHECKS_DNS_TIMEOUT_SECONDS`, `SW_CHECKS_DNS_MAX_NAMES`, `SW_CHECKS_DNS_CONCURRENCY`, `SW_CHECKS_DNS_CACHE_SECONDS`, `SW_CHECKS_DNS_SERVERS` and `SW_CHECKS_RATE_LIMIT_PER_MINUTE`. The console gets Panel > Checks (Conventions, Reconciliation and Impact tabs in the panel's look, a pack editor with Monaco, validation as you type, history and load-from-file, export as YAML), a Preview impact button in the profile, squad, host and node drawers, a card on the Overview page, and English and Russian texts that a test keeps in step with the rule catalogue; the fake panel gets a `checks` scenario with things wrong in it. Documentation for rule authors in `docs/en/conventions.md` and `docs/ru/conventions.md`; the design documents 02, 03, 04, 06 and 07 say what is built.
- Phase 3, snapshots of the panel and the diff (ADR 0043): `POST /panel/snapshots` reads every kind of object the token may read (nodes, hosts, config profiles with their configuration, squads, subscription templates and settings, snippets, node plugins, infrastructure billing) and keeps the masked, normalised configuration of each with a hash per object, per kind and overall, gzipped in the new tables `panel_snapshots` and `panel_snapshot_contents` (migration `20261122080000_create_panel_snapshots`); no unmasked value is ever read into a snapshot, a kind the token cannot read is left out and said so, and a snapshot is refused with 413 `snapshot_too_large` above `SW_PANEL_SNAPSHOT_MAX_MIB` (32). `GET /panel/snapshots` (paged), `GET` and `DELETE /panel/snapshots/{id}` (delete needs a code), `GET /panel/snapshots/{id}/diff?against=live|<id>` and `GET /panel/snapshots/{id}/export` (a masked JSON file); a Swellwright token with `panel:read` reads, compares and exports. The diff engine (`packages/remnawave`, pure and covered by property tests) matches objects by uuid and arrays by their natural key, compares sets without regard to order, only counts lists of clients, shows a rotated secret as changed and masked and never as a value, leaves out runtime state and timestamps, caps its answer and says "no differences" as a result; two snapshots masked with different keys are compared with the fingerprints set aside and say so. The background job (`SW_PANEL_SNAPSHOT_INTERVAL_HOURS`, 24, 0 off) takes a snapshot when the panel changed and only notes "checked, no change" otherwise; retention keeps the newest `SW_PANEL_SNAPSHOT_KEEP` (50) and the newest of each of the last 14 days. Audit: `panel.snapshot.created` and `panel.snapshot.deleted`. Console: Panel > Snapshots (list, details, comparison with the panel now or another snapshot, download, delete) and a "last snapshot" card on the Overview. OpenAPI 0.26.0.
- The expiry of a secret means something, and a vault secret can be handed to a run (ADR 0042). A secret whose `expiresAt` has passed (the moment itself counts) is refused with 409 `secret_expired` by everything that would use it: a server login (verify, facts, artifact push and check, the runner), a plugin, the token of a panel and a run; the vault is the one place that decides, after the sealed-vault answer and before anything is decrypted or sent, and an access entry that names an expired secret is skipped for the next one. A run that has already started is not cut short. `SecretView` and the access entries show `expired` and `expiresInDays`, a reveal says `expired: true`, the vault table has the badge, a filter and a notice, the server drawer a warning, and a refused use is noted once per secret per ten minutes (`secret.use_refused`). A run may carry `secrets: [{ name, secretId }]` (or a `secret` parameter of a script): the runner writes each value to a 0600 file below the step directory, sets `<NAME>_FILE`, removes it when the script ends by any route (the wrapper, cancel, the status read of a lost step, removal), takes the value out of the stored output (`[secret NAME]`, also across two reads) and keeps only the name and the secret in the record; it needs `servers:exec`, `vault:reveal` and a fresh code, is recorded as `secret.used_in_run` in the transaction of the run, and a secret that a running run was handed cannot be replaced or deleted. The run dialog has a Secrets section, the script editor a secret parameter. OpenAPI 0.25.0.
- Installer 1.0.2: a secret parameter (`SECRET_KEY`, `NEW_USER_PASSWORD`) can be given as a file, `SECRET_KEY_FILE=/path`, `NEW_USER_PASSWORD_FILE=/path` (environment, env file) or `--secret-file NAME=PATH`: a regular file (a symbolic link is refused) owned by root or the invoking user, mode 600 or 400, one line, at most 16 KiB; giving the value as well is refused as ambiguous; the value is never printed or journaled (the journal says only that a file was used). The manifest declares the two file parameters and `scripts/artifact-manifest.mjs` fails when a secret has no `NAME_FILE`.

### Fixed
- Dashboard: `reconciliation.drift` was a warning on a new installation, where the inventory has no servers yet and every node of the panel is "not in the inventory" (13 nodes: "13 differences"). That is where everyone starts, not a drift, so while it is the only difference the item is `info`; one difference of any other kind (a host that points nowhere, a server the panel does not have, a duplicate) keeps the warning, and so does an inventory that has even one server. The reconciliation counts the nodes with no server apart (`unmanaged`, over every row, not only the kept ones) and the memory of the last run keeps it with the number of servers; nothing changes in the API description. Tests: the count (`packages/conventions`), the rule (`attention.test.ts`), and the whole path from a reconciliation to the feed on a running API (empty inventory with differences of the panel's own, empty inventory with nothing else, one server).
- Found by running phase 3 against a real panel, read only (ADR 0041, 0043 and 0044, notes of 2026-11-22): four results the fake panel could not show were false. (1) The list of subscription templates of the panel has no bodies (`templateJson` and `encodedTemplateYaml` are null for every template; the body is in `GET /api/subscription-templates/{uuid}` only), so `template.body-present` called every template unreadable, the console showed empty bodies, and no snapshot, diff or impact calculation could see an edited body: templates are now read with their detail (`subscriptionTemplatesWithBodies`, bounded concurrency, GET only), the views say whether the body was read (`bodyLoaded`, not part of the hash), a body that was not read is `not_loaded` and never "missing", the memory of the server no longer answers a read of the bodies with the list-only views that the first probe of a connection seeded it with, and the node plugins are read the same way (`configLoaded`); the fake panel now answers like the real one. (2) `profile.inbound-port-clash` compared all inbounds of a profile, but a real profile holds one inbound for each node (twelve on port 443) and every node activates one: it now compares the inbounds that one node has active together, and only warns (`possible_clash`) where no node has any active. (3) `host.duplicate` reported the intended layout of one host for each subscription template (31 rows): two hosts are duplicates only when everything that selects what a client gets is equal (the remark, position and uuid are not part of it). (4) Review of the other rules: `template.unused` leaves out the `Default` template of each type and `host.sni-explicit` leaves out a host on an inbound without security; "Real shapes" in `docs/en/conventions.md` and `docs/ru/conventions.md` lists what a rule author must know about a real panel. OpenAPI 0.29.0.
- Installer 1.0.2 (ADR 0036, 0040): the `ssh` step closed root login as soon as the `sudo` group had any member; on a real server an account of the hosting provider sat in the group without a key and root login was closed with nobody able to log in. Root login and password login are now closed only when an account can really log in as an administrator, one function for both: it exists and is an ordinary account (not root, not `certsync`), `sshd -T -C user=NAME` lets it in with a key (public-key login on, no more than a key asked for, `AllowUsers`/`DenyUsers`/`AllowGroups`/`DenyGroups` do not exclude it), it is not disabled (real shell, not expired, a locked password only with PAM), sshd would read a valid key that gives a shell (the key file, `~/.ssh` and the home belong to the account or root and are not group or world writable; no `command=`, no `restrict` or `no-pty` without `pty`; `AuthorizedKeysFile` followed) and it can become root (sudo installed and allowed, a password or `NOPASSWD`). The step prints who counts and, for every other candidate, why not, before it closes anything, and a refusal names them all (exit code 1 as before); `verify` has the check `SSH: administrators with key login` (34 checks now). 71 new tests cover the rules, the modes, the sshd settings, the user phase, verify and the file parameters; 59 of them fail against 1.0.1 (the rest are the cases that must go on passing). Run for real on a disposable Ubuntu 24.04 server (ADR 0040, follow-up).
- Found by running phase 2 against a reset Ubuntu 24.04 server (ADR 0040): a pinned host key of another type than the one the server shows first (an RSA key pinned, then an ed25519 key added to the server) was taken for a changed key by every operation and by the scan, and is now preferred in the key exchange (`HostKeyPolicy.keyTypes`, `hostKeyAlgorithmsPreferring`); cancelling or removing a detached step through sudo on a login that is not root looked in root's home (sudo resets `HOME`), so a cancelled run kept running, was marked cancelled and left its step directory behind; a push or a check of a system artifact failed with `stat failed: Permission denied` when `/var/lib/swellwright` was root-only (the step layer makes it 0700), and is now asked as root with the directory chain opened (0755); installer 1.0.1: `apt_wait` no longer waits up to 15 minutes on every apt call for the always-running watcher of unattended-upgrades or PackageKit's daemon (it asks the lock files), a line added to `/etc/hosts` or `authorized_keys` is no longer glued to a last line that has no line break (`append_line`), and `rename` backs up and rewrites only the files it changes. The in-process servers and the stand-in sudo of the tests learned what a real server does and they did not (several host keys, a root-only directory, a sudo that resets `HOME`).
- The cancel test of the commands against a real shell (`stops a script that sleeps, with TERM to its whole process group`) counted every `sleep 60` of the machine with `ps | grep` and then waited a fixed 300 ms. Other test files, and the SSH package that turbo runs beside them, run `sleep 60` of their own, so the count was not the script's (it failed once in CI on 22 November; that this was the cause is not proven, and 12 repeats of the whole test run, six of them with the machine kept busy, did not reproduce it). The script now says the pid of its sleeper, the test waits until that process is gone and says which one, and a `sleep 60` that belongs to nobody there is left running next to it: the old check failed on it in CI, the new one does not.
- `SshConnection.close()` could leave a socket open for ever when the peer was gone: its backstop called `Client.destroy()` of ssh2, which does nothing once `end()` has made the socket unwritable; the socket is now destroyed directly (a pooled connection to a vanished server kept the process from exiting).
- SSH layer, the intermittent `does not start a step twice` (a step ran twice; it failed CI on real sshd in several runs, and 6 of 80 replicas of the test in one diagnostic run): the cause is found and fixed. The launch and the wrapper claimed a step with `mkdir`, and the coreutils of Ubuntu 25.10 and later (uutils, also on the current GitHub runner) answer success to both of two `mkdir` calls that race for one path (344 of 600 tight races on the sshd image, 173 of 600 on the runner; the shell's exclusive create `set -C`, a symbolic link and a hard link: none in 600), so both launches owned the step and both wrappers ran the script (the earlier `.claimed` directory could not help for the same reason). The owner is now whoever creates `.owner` (launch) or `.claimed` (wrapper) with the shell's own exclusive create; an existing directory is never adopted, so a step directory that was never completed still ends as `incomplete`. `script.sha256` is written aside and renamed, so a launch that lost the race can never read it half written and report a false conflict. Two regression tests replace `mkdir` with one that tells both racers they made the directory; they fail against the old scripts and pass now.
- `SshPool`'s acquire-timeout test (`gives up waiting for a free connection after the acquire timeout, and recovers`): `acquireTimeoutMs: 150` bounded establishing the first connection too, not just waiting for a busy one, and a real SSH handshake occasionally exceeded 150ms on a loaded, shared CI runner (reproduced 4 times in a row); raised to 1000ms (the held connection's hold time to 3000ms, same ratio).
- SSH layer and command runs, the last line of a run's output could be missing (the flaky CI test `follows a script that writes over time, and reads the end once it has finished` saw `first\nsecond\n` for `first\nsecond\nthird\n`): the status script measured the size of `out` and `err` before it looked at the exit marker, and the command runner reads no further than that size. A script that wrote its last line and ended between the two looks was reported as over with the size from before that line, and the line was never read. The sizes are now measured after the state is decided, so a step reported as over carries the size it finished with (a step still running may be a little short, and the next look is exact). A test makes `wc` end the step right after it has counted: the old order reports `exited` with 6 bytes of 11; reproduced with a POSIX shell on the author's machine as well as in CI.
